## 0. 一句话

**把数据、模型、配方、训练任务都变成「可 fork 的对象」，让一个人、一个团队、一群陌生人，
像用 Git 一样协作训练模型。**

更短的一句：**GitHub 之于代码，正如本系统之于 AI 资产。** 区别只有一条——
**这里的「仓库」自己能跑起来训练。**

### 0.1 本文相对 01~14 新增了什么（先看差异，再看全文）

01~14 把**引擎**讲透了（IR、内容寻址、联邦、公地、账本），但那是"模型的制造工艺"。
本文补的是**产品那一层**，其中六件是全新的：

| 新增 | 是什么 | 为什么必须有 |
|---|---|---|
| **Recipe（配方）** | "基座 + 数据 + 策略 + 预算 + 评测"的**可发布方法**，与模型/数据平级 | 它是"发布训练任务"的对象化形态；也是**"数据不出本地还能协作"的钥匙** |
| **DataDiff（数据补丁）** | 对数据集的可寻址**变换**，不搬原文 | 直接回答你那句"别人怎么对我的数据做修改再发布" |
| **Proposal（提议）** | 相当于 Pull Request：一组改动 + 证据，过闸门后合并 | 把 11 §3.2 的 merge 从"一个算法"变成"一个可评审的流程" |
| **三档同构 + 升格（Upgrade）** | 私人 / 团队 / 公共，是**同一个对象模型**的不同可见范围 | 冷启动机制：公共网络不是另做一个产品，而是"我的房间被公开" |
| **联邦 = fork/merge 循环** | 一轮联邦训练本就是一次"分叉 → 合并" | 让用户**只学一套心智**，不必理解"联邦"和"分支"是两个东西 |
| **Agent 是一等用户** | 每个用户挂一个 agent；界面的第一消费者是 agent | 04 §1 的产品落点：写代码/操界面的人在变少 |

> 诚实边界（先说在前面）：本文是**产品草案**，不改变 01~14 的任何技术承诺。
> 凡是本文与 01~14 冲突处，以 01~14 为准，回来改本文。

### 0.2 三条基线（2026-10-08 用户拍板，优先于本文其余部分）

| 基线 | 内容 | 对设计的影响 |
|---|---|---|
| **B1 · 产品即协议** | 交付物是**开放规范 + 参考实现**，**不是平台**；任何人不经许可就能开发自己的工具，不依赖特定平台（互联网 / 共享 / 开源 / 自由） | 新增 [16 协议与规范](16-协议与规范.md)；**本文所有"界面 / 形态"都只是"参考实现之一"**，不是定义 |
| **B2 · 第一位用户是自己** | 第一个用户就是**作者本人**；**让自己这个小白用舒服了，就成功一半** | 优先级全面前移到 **第一档（我的设备）+ 对象卡 + 血缘图**；砍掉一切"先做给陌生人用"的需求 |
| **B3 · 暂不考虑付费** | 先不想商业模式，先把产品与规范做对 | §3.2 团队档的"付费点"仅作**价值论证**保留，不作为优先级；§9 激励层整体降到"未来" |

> 由 B2 派生的一条硬约束：**任何功能，如果作者自己日常用不上，就不进第一版。**
> agent 层的规范见 [17 通用 Agent 任务模型](17-Agent任务模型.md)。

## 1. 核心洞察：Git 的协作模型可以无损搬到 AI 资产上

### 1.1 为什么这个类比不是修辞，而是结构事实

Git 能成立，靠的是一个前提：**内容寻址的内容 DAG**（blob → tree → commit，一切由哈希定名）。
本项目的权威物恰好也是这个前提：

| 本项目已经有 | 内容寻址？ | 来源 |
|---|---|---|
| Spec IR（模型结构） | ✅ `specHash` | 03 §2 |
| 权重 / 适配器 | ✅ 哈希定名、可增量 | 11 §3.1 |
| 数据集（指纹 + 分片表） | ✅ `datasetHash` | 11 §2.2 |
| 数据管线（变换） | ✅ `pipelineHash` | 11 §2.3 |
| 快照（参数 + 数据进度） | ✅ `Snapshot` | 14 §2.3 |
| 训练记录 / 结论 | ✅ `TrainingTrace` / `ProbeResult` | 11 §3.4 |
| 贡献 | ✅ 可验追加账本 | 11 §4 |

**结论：Git 的全部协作语汇（fork / branch / diff / merge / PR / review / blame / release）
可以无损移植过来——我们不需要发明新机制，只需要把已有对象"暴露成人能点的东西"。**

### 1.2 逐条映射表

| Git | 本系统 | 备注 |
|---|---|---|
| blob / tree | 权重分片 / 数据集分片 / Spec IR 节点 | 内容寻址的最小单位 |
| **commit** | **Snapshot**（参数 + `DataCursor`，恢复后可续训） | 只有参数的快照**不合法**（INV-13） |
| branch | 一条派生路线（模型分支 / 配方分支） | |
| **fork** | `ModelArtifact.parents` / `Recipe.parents` | 带父许可（11 §2） |
| clone | 从公地拉对象 | IR 是 KB 级，几乎瞬间 |
| remote | 公地 registry / 团队 registry | 可完全分布式，见 11 §3.3 |
| **diff** | `ir.diff`（结构）+ 权重 Δ + **DataDiff**（数据） | 三种 diff 统一在"对象卡"里 |
| **merge** | Task Arithmetic 等谱系（11 §3.2），**必须过 Probe 闸门** | 默认最简单的那个（ADR-022） |
| **pull request** | **Proposal（提议）** | 本文新引入 |
| **CI** | **Probe 闸门**（机器）+ 人类评审（可选） | 评测统计铁律 INV-21 |
| issue | 「缺口 / 招募 / 研究问题」 | 也是任务市场的入口 |
| log / blame | `TrainingTrace` + 溯源链（可验追加） | INV-20 |
| tag / release | 模型版本（`specHash` + 权重哈希） | 不可变 |
| license | SPDX 前置 + fork 携带父许可 | 公地准入前提 |
| submodule | adapter 挂载 | 秩异构（11 §3.2） |
| merge conflict | Δ 冲突（TIES / DARE 处理） | 默认 Task Arithmetic 更稳 |
| **`.gitignore`** | **本地数据永不进仓库**（原始数据不出本地） | 11 §2.1 |

### 1.3 三个"统一"，这是整套设计最省心的地方

```
统一①  派生与联邦是同一件事
        一轮联邦 = 各节点在 base 上分叉训练 → 聚合 = 合并。
        掉队节点 = 未合并的分支（异步档可 cherry-pick）。
        ⇒ 用户学一套「分叉/合并」，就同时懂了「联邦」。

统一②  合并闸门 = CI
        Proposal 想过闸门必须跑 Probe，正如 PR 必须过 CI。
        ⇒ 质量把关是"流程的一部分"，不是"额外的审计系统"。

统一③  账本 = commit log
        贡献可验追加（Merkle 锚点），正如提交历史不可静默改写。
        ⇒ 声誉与署名有客观依据，不需要中心机构背书。
```

## 2. 一等对象：这个产品里只有九种"东西"

用户世界里**只存在九类对象**。所有界面、所有操作，都是在这九类上做文章。

### 2.1 资产（可发布、可 fork、可进公地）

| # | 名字 | 英文 | 一句话 | 能否 fork |
|---|---|---|---|---|
| 1 | **数据** | Dataset | 登记在册的数据集：指纹 + 元数据 + 许可，**原文可留本地** | ✅ |
| 2 | **模型** | Model | 结构 + 权重 + 血统 | ✅ |
| 3 | **适配器** | Adapter | 可叠加的增量（LoRA…），几 MB 就能传 | ✅ |
| 4 | **配方** | **Recipe** | **基座 + 数据 + 策略 + 预算 + 评测** 的可发布训练方法 | ✅ |

| 6 | **探针** | Probe | 评测套件（本身也是资产，可 fork，见开放问题⑮） | ✅ |

### 2.2 过程（运行时，有生命期）

| # | 名字 | 英文 | 一句话 |
|---|---|---|---|
| 7 | **现场** | Room | 配方的一次**执行**：有成员、轮次、账本、实时曲线 |
| 8 | **记录** | Trace | 一次执行的完整凭据：快照 + 日志 + 探针 + **结论** |

### 2.3 度量与容器

| # | 名字 | 英文 | 一句话 |
|---|---|---|---|
| 9 | **账本** | Ledger | 贡献、份额、声誉、积分（非货币） |
| — | **团队** | Team | 一组人 + 一组共享仓库 + 权限（容器） |
| — | **身份** | Identity | `peerId` → 未来的 DID/VC（开放问题⑤） |

### 2.4 一张"对象卡"长什么样（所有对象共用同一张脸）

每个对象在界面上都是一张卡，卡上永远有这五块：

```
┌───────────────────────────────────────────────────────────┐
│  [类型徽章] 名字 · 版本(hash 前 8 位)         [信任等级徽章] │
│  ───────────────────────────────────────────────────────  │
│  ① 它是什么     结构摘要 / 数据规模 / 参数量 / 策略         │
│  ② 它从哪来     父对象（parents）+ 作者 + 许可              │
│  ③ 它有多好     探针曲线 / 能力雷达 / **统计功效**          │
│  ④ 谁在参与     贡献者 + 账本 + pinning 存证                │
│  ⑤ 能做什么     fork / merge / 起房间 / 提议 / 下载 / 引用  │
└───────────────────────────────────────────────────────────┘
```

> ①③④ 是 11 §2.4 的 `Probe`/账本、10 §4 的溯源链的直接投影。
> **"③ 它有多好"必须带置信区间与功效**——否则公共账本的判定就是噪声驱动（INV-21）。
> ⚠空白：卡片信息密度很高，如何在手机上折叠？需要一次专门的移动端信息设计。

## 3. 三层世界：同构的三档协作（本文的核心）

这是你要的"单人多设备 / 多人团队 / 陌生人公共"三件事。
**关键设计决定：它们不是三个产品，而是同一个对象模型的三种可见范围。**

| | 第一档 · 我的设备 | 第二档 · 我们的团队 | 第三档 · 大家的公地 |
|---|---|---|---|
| **谁** | 我一个 | 一个团队（熟人） | 陌生人 |
| **信任** | L0 全信 | L1 半信 | L2/L3 不信/敌对（10 §5） |
| **数据** | 全在本地 | 各成员本地，不出内网 | 本地 + 可选公开分片 |
| **协作语言** | 「同步」 | 「评审 + 合并」 | 「提议 + 声誉 + 治理」 |
| **产品形态** | 私人工作台 + 私人房间 | 团队空间 + 共享仓库 | 公地 + 开放房间 + 任务市场 |
| **门槛** | 打开网页 | 邀请码 | 无（但有信任分级） |
| **独立价值** | 把散设备拼成一块"虚拟显卡" | 数据不出内网也能联合训 | 长尾算力 + 公共模型 |
| **对应技术** | 现状即可（M-N0/N1） | P7 联邦 + 11 公地 | P8 + 信任层 L2/L3 |
| **治理复杂度** | 无 | 轻（团队规则） | 重（Ostrom 八原则，11 §6） |

### 3.1 第一档 · 我的设备（Solo Cluster）

**用户想干嘛**：我有公司电脑、家里台式、一台手机，都想丢进来训同一个模型。

**产品形态**：**私人房间**。
- 一台设备点「开房间」→ 出一个二维码 / 6 位码。
- 其它设备扫码 → 自动发现、自动分配角色（谁聚合、谁算、谁只评估）。
- 断线自愈、离线排队、手机随时进出（弹性成员已实现，见 `docs/共同训练方式选型.md` §1.7）。

**关键机制**：
- **降级阶梯**（07）：慢设备不是被抛弃，而是换角色——反传 → 前向 → 局部 → 零阶 → **仅评估**。
- **最弱设备也有位置**：北极星的"能力下限"这一项就在这里兑现（01 §4）。

**它凭什么独立成立**：不用任何网络、任何人协作，它就是"一块拼起来的虚拟显卡 + 一个训练台"。
**这是冷启动的起点**（01 §6.4 第一步）。

### 3.2 第二档 · 我们的团队（Team Space）

**用户想干嘛**：律所 3 个律师 + 2 台服务器，各自手里有一批卷宗，**数据不能出内网**，
但要合起来训一个所内问答模型。

**产品形态**：**团队空间** = 私有 registry + 共享仓库 + 成员权限 + **自建信令**。
- 每个人各自 fork 一条分支，用自己本地数据跑。
- 出自己的 **Proposal**（一组 Adapter/更新 + Trace 证据）。
- 团队 **review**（机器 Probe 先行，人再裁决）→ merge 进团队主干。
- 全程数据不出各自机器（只传 Update / Adapter，11 §2.1）。

**关键机制**：
- **权限模型**：谁能 push 主干、谁只能提议、谁能改配方。
- **私有 registry**：团队的模型库不外泄。
- **自建信令**：合规要求（境内、内网）下可完全自托管。

**它凭什么独立成立**：即使永不对外开放，它就解决了"数据不能出门，但大家想一起训"这个真实刚需。
（价值最清晰，但按基线 B3 **暂不作为优先级**——先服务好"作者自己"这一档。）

### 3.3 第三档 · 大家的公地（Public Commons）

**用户想干嘛**：一个陌生人在公地发现某方言模型很弱，想改进它，但没算力、也没数据。

**产品形态**：**公地（Commons） + 开放房间 + 任务市场**。
- 他 fork 那个模型的**配方**，贴上自己的 **DataDiff**（几行"对数据做了什么"）。
- 发一个 **Proposal**（还只是提议），并把配方**公开成一个开放房间**招募算力。
- 志愿者点「加入」贡献闲置算力，账本记贡献（11 §4）。
- 训完出改进版 → 过 Probe 闸门 → merge 回主干 → **账本留下每个人的贡献**。

**关键机制（这一档才是 09/10 信任层真正上场的地方）**：
- **信任分级徽章**：房间标 L1/L2/L3，用户一眼看到"我在跟谁协作"。
- **可信度披露**：探针的置信区间、评测污染披露、公地资产可用性（11 §2.5/§2.8）。
- **治理**：Ostrom 八原则自检（11 §6），**fork 即退出**兜底。
- **激励**：声誉 + 积分（优先级/治理权重/署名），**不发币**。

**它凭什么独立成立**：它给出一个**不归任何人所有的公共 AI** 的可行形态。
⚠空白：陌生人网络的**治理与争议解决**目前只有兜底（fork 即退出），没有裁决位（11 §6 三条 ⚠️）。

### 3.4 三档之间不是墙，是**升格（Upgrade）**

```
   私人房间 ──[一键]──► 团队房间 ──[一键]──► 公开房间
      ▲                                          │
      └────────────── fork 出来私有化 ◄───────────┘
```
因为三档共用同一对象模型，"扩大可见范围"只是一个开关，**不是一次产品重做**。
这条是**冷启动的关键机制**：公共网络的第一个房间，就是某人自己的房间被公开。

### 3.5 房间角色目录：**设备 ≠ 角色**（★ 2026-10-08 原型反馈新增）

> 来源：原型反馈——"设备与角色应该脱离"。

**这是一处结构修正**。早期稿把"房主 / 节点"当成同一种东西，但它们是两件事：

| | 是什么 | 数量关系 |
|---|---|---|
| **设备 Device** | **能力供给**（算力 / 内存 / 网络 / WebGPU / 在线时长） | 一台设备可在不同房间当不同角色 |
| **角色 Role** | **房间的需求**（要干的活） | 一个角色槽位可由多台设备分担 |

**角色目录（首批 9 个）**：

| 角色 | 职责 | 门槛 | 可兼任 | 必需 |
|---|---|---|---|---|
| **房主 Owner** | 定义房间（配方/数据/验收/预算/规则）、开关轮、签账本 | — | 否 | ✅ |
| 管理员 Admin | 房主授权管理成员与设备 | 房主授权 | 可 | 可选 |
| **聚合端 Aggregator** | 执行聚合与广播（"干重活的机器"） | 稳定在线 + 带宽 | 可与房主同机 | ✅（默认=房主设备） |
| **训练节点 Trainer** | 用分到的数据产出 `Update` | 能跑所选策略 | 可 | ✅（≥1） |
| **评估节点 Evaluator** | 只做前向与评测（**最弱设备的位置**） | 极低 | 可 | 可选 |
| **验证节点 Verifier** | 独立复算他人提交（09 §6 验证义务化） | 中高 | **否（须独立于执行者）** | L2+ 必需 |
| 存储节点 Pinner | 为公地资产持久化（11 §2.8） | 有存储 | 可 | 可选 |
| 数据提供 DataProvider | **只登记数据指纹，原文不出本地** | 有数据 | 可 | 可选 |
| **观察者 / 游客 Observer** | 只看曲线 / 账本 / 血缘，**随时可转参与者** | 无 | 可 | 可选 |

**三条推论**：

1. **房主 ≠ 聚合端**：房主是"定规则的人"，聚合端是"干重活的机器"；默认同机，但可分开派给算力更强的设备。
2. **游客是一等角色**，不是"未登录用户"——它是最低门槛入口（比注册还轻），也是"先看看再决定"的心理缓冲。
3. **数据提供 ≠ 算力提供**：只登记数据、不出原文，本身就是一种贡献（11 §2.1）。

**权限边界（重要）**：房主能看到成员设备的**清单 / 角色 / 状态**（协作必需），
但**不能操作别人的机器**——只能**请求**。产品上做成两种设备卡：**"我的"（可操作）/ "别人的"（只读 + 请求）**。

### 3.6 小白 / 专业 双模：同一个房间，两种深度

> 来源：原型反馈——"专业的找不到专业用法，小白也用不明白"。

**解法不是把两拨人放进一个界面，而是同一个页面的两个深度档**：

| | 小白档（默认） | 专业档 |
|---|---|---|
| 能做什么 | **「一键加入（按房主设置）」+「我只是看看（游客）」** | 全部本地旋钮 + 角色兼职 + 阶段细粒度 |
| 看到什么 | 3 个数字（进度 / 我的贡献 / 还剩多久） | 9 阶段时间轴 + 每节点心跳 + 通信预算 |
| 配置 | 只读展示"房主定了什么" | 可改"我这台机器怎么干活" |

**关键分界（这条是硬约束，值得反复引用）**：

```
房主锁定（全网必须一致，谁都改不了）      节点自由（只影响自己那台机器）
· 模型结构 specHash                      · 本地策略档位（反传/LoRA/零阶/评估）
· 字符表                                 · 本地步数与精度
· 聚合语义（FedAvg + 步数归一化）         · 压缩方案（须带误差反馈）
· 验收探针与阈值                          · 是否兼职聚合/验证
· 数据指纹                               · 带宽上限
```

> 为什么这样分：**只要有一台设备的结构 / 字符表 / 聚合语义不一致，权重就无法聚合**（02 INV-6）。
> 所以"一致性"必须锁死，而"怎么省资源地干活"必须放开。**小白照房主设置走，就是走在这条线之内。**

### 3.7 从某个 check 开房：fork 的入口（★ 原型补充）

```
公地/分支树上的任意 check
   └─[从这开房]─► 向导：起点(锁) → 配方(继承/改一处) → 数据(本地+公地) → 验收(继承探针)
                                  → 可见性(L0~L3) → 角色需求 → 预算
                        └─► 创建房间（成为房主）→ 发布招募 → 训练 → 出 check → 发布
```

- **起点固定**：新房以该 check 为 `base`，训练完成为分支树添一根新枝（§7 的 fork→…→merge 全流程）。
- **验收继承**：默认继承父的探针套件，保证不同分支的分数**可比**（否则回归就没法判断）。
- 这就是你原话："公开的可以从它的某个版本或者 check 开始，然后开自己的训练房，开始训练，并且可以发布。"

## 5. 三个剧本：把它走一遍

### 剧本 A · 一个人，三台设备

2  手机扫码加入（同 WiFi）；公司电脑开链接加入

**验收对齐**：接入步骤数 ≤ 3（01 §4 北极星）。

### 剧本 B · 一个小团队（律所）

```
1  管理员建 Team Space，邀请 3 人 + 接入 2 台内网服务器，起自建信令
2  各成员把本地卷宗登记为 Dataset（只登记指纹，原文不出机器）
3  团队主干模型 = 一个公共基座（进私有 registry）
4  成员 A fork 主干 → 用自己的数据微调 → 出 Proposal（附 Trace + Probe）
5  机器先跑 Probe 闸门 → 人工 review → merge 进团队主干
6  每人的贡献进团队账本（谁贡献多少可查）
```

**关键**：**第 2 步是全部意义所在**——数据没出门，但模型学到了。这是 `webllm` 相对
"HuggingFace 上传数据集"的结构性优势。

### 剧本 C · 陌生人公共协作

```
1  陌生人在公地发现「闽南语-1.5B」在医疗问句上很差
2  fork 配方 → 本地贴一个 DataDiff（+12k 条医疗方言，来自他持有的语料）
3  发 Proposal + 把配方公开成一个 L2 开放房间
4  志愿者加入贡献算力（账本计量）；系统用鲁棒聚合 + 验证义务化防作弊
5  训完 → Probe 闸门（含后门探针、污染检测）→ merge 回主干候选
6  账本记下 17 个节点的贡献；发起人获得署名与声誉
```

**注意第 5 步**：这才是 09/10 那一整套拜占庭防御/后门探针/统计铁律**真正被用户看见**的地方。

## 6. DataDiff：回答"别人怎么改我的数据再发布"

这是你原话里最具体、也最难的一条需求，单开一节。

### 6.1 难题

- 数据要**像 git 一样可被他人 fork、修改、发布**；
- 但 11 §2.1 又规定**原始数据不出本地**。

这两条看似矛盾。解法是：**协作发生在"变换层"，而不是"文件层"。**

### 6.2 三档数据协作

| 档 | 机制 | 数据动不动 | 适用 |
|---|---|---|---|
| **A 配方协作** | 只共享 `DataPipelineSpec` + 由它产出的统计/Update | ❌ 不出门 | 敏感数据（默认档） |
| **B 快照协作** | 数据可公开的，出内容寻址快照，可 fork/改/发 | ✅ 出门 | 开源语料 |
| **C 派生协作** | 基于公共模型生成的合成数据，带 `syntheticOf` 溯源 | ✅ 出门但可追 | 合成/蒸馏 |

### 6.3 DataDiff 的数据结构（产品层）

```
DataDiff := {
  diffHash,
  base:   datasetHash | { recipe: recipeHash, slot: <数据槽名> },
  ops:    [                                 // 有序变换，本身可寻址
    { op: 'add-shards',   from: datasetHash },
    { op: 'drop-where',   filter: <表达式> },
    { op: 'reweight',     field, curve },
    { op: 'relabel',      ... }
  ],
  stats:  { tokensΔ, distributionΔ, qualityΔ },   // 由 DataPipelineSpec 产出
  provenance: { author, license, syntheticOf? }   // 合成数据必须带（INV-22）
}
```

- **它不搬原文**：只有"对数据做了什么"。可以在别人的机器上、对**各自的本地数据**执行。
- **可以 review**：像看代码 patch 一样看"你往训练池里加了什么、删了什么"。
- **可以合并**：两个 DataDiff 可叠加 → 新的 `pipelineHash`。
- **公开数据可一键落地**：若 base 是公开分片，`ops` 可直接应用出新的公开快照。

> 定位：**DataDiff 是 11 §2.3 `DataPipelineSpec` 的"面向人"版本**——
> 同一个东西，机器看的是算子序列，人看的是"补丁"。不新增机制，只新增视图。

### 6.4 一个必须承认的边界

若 base 数据是"仅本地"（档 A），**别人拿不到原文，也就无法独立复现你的 DataDiff 效果**——
他们只能复现"变换"，不能复现"数据"。这是隐私的必然代价，
**产品上必须显式标注**（"此数据集仅本地，效果不可被第三方独立复现"），
否则就成了"看起来可复现、实则不可"的过度承诺。

## 7. Proposal：把 merge 从"函数"变成"流程"

### 7.1 结构

```
Proposal := {
  target:     recipeHash | modelRef | datasetRef,   // 想改进什么
  changes:    { irDiff?, adapters?, dataDiff?, recipe?, strategy? },
  evidence:   [ProbeResult, TrainingTrace],          // ← 证据（可复算）
  proof:      { aggregationRuleId, pairedSeed, ci }, // ← 统计铁律（INV-21）
  cost:       { credits, compute, bytes },
  review:     { machine: pass|fail, humans: [...], discussion: [...] },
  decision:   rejected | merged | fork-only
}
```

### 7.2 生命周期

```
fork ─► 本地实验(Studio) ─► 产出 Update/Adapter/Trace
                                   │
                                   ▼
                              发 Proposal
                                   │
                   ┌───────────────┴───────────────┐
                   ▼                               ▼
          Probe 闸门（自动 CI）              人类评审（可选）
          · 能力原子对比（配对 CRN）          · 团队必开
          · 后门探针 / 污染检测               · 公共可开
          · 统计功效检查（EVAL_UNDERPOWERED）
                   └───────────────┬───────────────┘
                                   ▼
                         merge（默认 Task Arithmetic）
                                   │
                                   ▼
                          进 registry / 主干
```

- **`decision = fork-only`** 是一种合法结局：**合并被拒 ≠ 你的成果消失**，
  它可以作为一条 fork 分支继续存在（这也承接了 01 §6 的"fork 即退出"）。
- **机器评审永远先于人类评审**——人只看机器已经算过的东西（01 §4 的效率原则）。

## 8. 冷启动：洋葱式渐进（每一步都独立有价值）

```
第 1 层  单机也爽         打开网页就能训我的模型、出模型卡     ← 不依赖任何人
第 2 层  我的多设备       手机扫码即加入，散设备拼成一块显卡    ← 只依赖我自己
第 3 层  熟人/团队        数据不出内网也能联合训                ← 一个小圈子
第 4 层  公共公地         陌生人贡献算力、公共模型可 fork        ← 需要规模
```

**设计约束：每一层是前一层的超集，且不依赖下一层成功**（反脆弱，`docs/公共AI网络-规划.md` §6.4）。
技术上的保障就是 §3.4 的"升格"——**第 4 层不是新盖的楼，是第 3 层把门打开了。**

## 9. 激励与声誉（非货币）

| 层 | 内容 | 用途 |
|---|---|---|
| **声誉** | 由账本 `effective` 份额 + `probeDelta` 累积，**不可转让** | 优先调度、抽检频率、信任分级 |
| **积分** | 记账单位（非货币），`credits ← γ·EMA(probeDelta) + (1−γ)·effective` | 优先级、治理权重、适配器署名 |
| **署名** | 每个对象卡上的贡献者列表 + 溯源链 | 学术/职业价值 |

- **明确不发币、不承诺兑换**（11 §4、`docs/公共AI网络-规划.md` §6.3）。
- **只索取不贡献的节点两项皆零并逐步降权**（10 §6）。

> ★待定：公地是否需要"任务市场"（有人挂悬赏找算力/数据/评测）？
> 我的倾向：**先不做悬赏，只做"公开房间 + 署名"**。悬赏会立刻引入"验证先于激励"的难题
> （`docs/公共AI网络-规划.md` §4.3）。

## 10. 推理与 Agent：产品里的另一半

`webllm` 不只有"训练"。用户要的还有**推理**和**agent**。产品上它们是：

### 10.1 推理（把模型用起来）

| 形态 | 说明 | 现状 |
|---|---|---|
| **浏览器内推理** | 打开网页就跑，零成本、数据不出本地 | ✅ 已有 `sample()`，待接 KV cache |
| **可分享的应用** | 把模型 + 一个 prompt 模板打包成一个链接 | ❌ 未做 |
| **服务化（API）** | 某个节点把模型暴露成 API（收费或免费） | ❌ 未做（规划 §3.5） |

> ★待定：服务化是"公地里的模型谁都能自己跑"，还是"允许节点出租算力做 API"？
> 后者会牵出经济与合规问题。

### 10.2 Agent（智能体）

**定义（产品层）：一个 Agent = 一个可发布的包。**

```
Agent := {
  agentHash,
  model:    specHash | 'host-provided',      // 用哪个模型
  skills:   [skillHash],                     // 会哪些工作流（04 §6.1）
  tools:    [toolRef],                       // 能调哪些工具（04 §4）
  recipe?:  recipeHash,                      // 如果需要继续训练
  license, author
}
```

- Agent 是**公地的一等资产**：可 fork、可组合、可署名。
- **AI 是一等用户**（04 §1）：产品界面的第一消费者是 agent，人做 L2 决策（04 §6）。
- 于是"发布一个 agent"= 发布"一个能自主完成某类任务的配方 + 技能 + 工具包"。
- ⚠空白：Agent 的安全边界（它能花多少算力、能发什么提议、能不能自己 merge）**还没设计**。

## 11. 信任与安全的"产品语言"

技术层的信任分级（10 §5）必须翻译成**人一眼能懂的东西**：

| 徽章 | 含义 | 用户该有的预期 |
|---|---|---|
| 🟢 **自家** | L0，全是你自己的设备 | 无防御，最省资源 |
| 🔵 **熟人** | L1，同一团队/WiFi | 账本 + 效应审计 |
| 🟡 **公开** | L2，陌生人可加入 | 有防御，但**在 f/n 阈值内**才成立 |
| 🔴 **敌对** | L3，完全开放 | 最高防御 + 经济抵押（未实现） |

**三条"诚实披露"必须进 UI**（否则就是过度承诺，见 01 §6）：
1. **可信度随 f/n 变化**——不是"绝对安全"，是"容忍不超过阈值的恶意"。
2. **统计功效**——探针池不够大时，展示"这个结论不显著"（INV-21）。
3. **评测污染 / 资产可用性**——模型卡强制标注（11 §2.5/§2.8）。

| P⑧ | 服务化（出租推理 API）做不做？ | 先不做（§10.1） |
| P⑨ | 产品名？ | 倾向「织造 / Weave」（§12） |
| P⑩ | **Agent 的权限边界？** | 已在 [17 §3](17-Agent任务模型.md) 给出规范落点（`authority` 四权 + 逐层衰减 + 深度上限）；仍是 ★待定。**运行时强制**是缺口（17 §8.4） |
| P⑪ | 角色目录够不够（首批 9 个）？游客要不要再细分？ | 先 9 个；**游客是一等角色**（§3.5）已定 |
| P⑫ | 双模（小白/专业）默认哪档？房主能否强制专业档？ | **默认小白档**；**房主不可强制**——强制就退回"两边不讨好" |
| P⑬ | 数据提供者能否"只出数据不署名"？ | 可以，但需在署名权与账本可审计性之间给出显式选择（§3.5 推论 3） |

## 15. 产品级验收线（可检查）

| 编号 | 标准 |
|---|---|
| PROD-V1 | **3 步接入**：新设备从打开链接到成为参与节点 ≤ 3 步（对齐 01 §4） |
| PROD-V2 | **一键升格**：私人房间 → 团队 → 公开，对象与账本无损迁移 |
| PROD-V3 | **任意对象可 fork**：模型/配方/数据/技能/探针五类均可在 UI 内 fork 并看到 parents 链 |
| PROD-V4 | **血缘图可读**：从任一模型上溯到所有祖先，且能回答"哪条数据/哪次改动带来了这个能力" |
| PROD-V5 | **Proposal 闭环**：提议 → 机器闸门 → 人审 → merge / fork-only，全流程有据可查 |
| PROD-V6 | **DataDiff 可评审**：只看 diff 就能判断"训练池被加了什么"，无需原文 |
| PROD-V7 | **边界诚实**：任何对象卡都能回答"这个结论的可信度是多少"（CI + 功效 + 污染 + 可用性） |
| PROD-V8 | **单机也爽**：断网状态下，第一档全部功能可用 |
| **PROD-V9** | **设备与角色解耦**：同一台设备可在不同房间担任不同角色；一个角色槽位可由多台设备分担；房主可改派设备角色而不影响房间规则（§3.5） |
| **PROD-V10** | **双模不互相污染**：小白档只暴露 ≤3 个动作、≤3 个数字；专业档的全部旋钮**不触碰**房主锁定项（§3.6） |
| **PROD-V11** | **从任意 check 开房**：分支树上任意公开节点可一键开房，新房间的起点、验收套件被正确继承（§3.7） |

## 16. 一句话总结

> **技术层已经证明"能造"。产品层要做的是让"造"这个动作，像 push 一次代码一样轻。**
>
> 三档协作不是三个系统，是同一个内容寻址对象图的三种开放程度；
> 而它们的公共语言只有一个词：**fork。**
>
> 而这件事**不该由我们垄断**——所以产品的最终形态是
> [16 一族开放规范 + 参考实现](16-协议与规范.md)，
> agent 层的规范是 [17 通用任务模型](17-Agent任务模型.md)，
> 而第一个用户，是写这份文档的人自己。
