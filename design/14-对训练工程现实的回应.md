# 14 · 对训练工程现实的回应

> 前置：全部。
> 背景：一篇被广泛认同的行业分析（bigpunch，知乎）系统列出大模型训练的七类真难点：
> ① 大规模并行通信开销 → MFU 崩塌；② 硬件故障是常态、Straggler；
> ③ 容错与异步 Checkpoint / 热启动；④ 数据是原油（清洗/去重/配比/**测试集污染**）；
> ⑤ Loss Spike 与两周一次的超参反馈周期；⑥ 评估难（榜单虚高、judge 有偏、
> 内部评测集才是护城河）；⑦ 人才断层（要同时懂 CUDA+NCCL+IB+Transformer+分布式）。
>
> 本章逐条回应。原则：**不吹、不躲、不含糊**。三类判定：**结构性回答**（范式优势）、
> **部分回答**（有机制但欠设计）、**未回答**（承认缺口，给出补法 or 承认不补）。

---

## 1. 先给总判定

| # | 痛点 | 判定 | 一句话 |
|---|---|---|---|
| ① | 通信 → MFU 崩塌 | **部分回答** | 换了计量方式（低频同步+低通信策略），正面战场认输 |
| ② | 硬件故障 / Straggler | **结构性回答** | 软同步屏障：掉线不停摆 + 降级而不踢出 |
| ③ | 容错 / Checkpoint / 热启动 | **部分回答** | round 边界=天然快照点 + content-addressed snapshot（本章补设计） |
| ④ | 数据质量 / 去重 / 配比 / 污染 | **污染=结构性回答；质量与配比=承认缺口** | datasetHash 让"测试集泄漏"变成**可静态判定** |
| ⑤ | Loss Spike / 长反馈周期 | **部分回答** | 溯源链可定位、可 quarantine；但静态分析**不能**预测效果 |
| ⑥ | 评估难 | **未回答（机会已识别）** | evaluator-only 角色使众包评测在结构上可行，但未设计 |
| ⑦ | 人才断层 | **结构性回答** | 这正是本设计要**消灭**的人才形态 |

> **这篇分析整体上是我们的战略背书**：它证明了中心化大规模训练是
> 「算力+数据+工程+评估+人才」**任何一环都不能有短板**的消耗战，壁垒高到只剩巨头能玩。
> 所以问题从来不是"我们的 WebGPU 打得过 2000 张 H800 吗"（打不过），
> 而是"**除了这张赌桌，还有别的桌子吗**"。

## 2. 结构性回答（我们的范式红利）

### 2.1 软同步屏障：故障不是停摆（痛点②）

文章的核心恐惧是**同步大锅饭**：2000 卡里 1 张 PCIE 松了，全体停下查日志。
联邦范式的本质差别是**软屏障**：

```
同步训练：每步 all-reduce ⇒ 一卡坏/一卡慢 ⇒ 全任务阻塞 ⇒ 半夜两点爬起来查 PCIE
联邦训练：每节点本地 localSteps 后上报 ⇒ 掉线/慢 = 少一份 Update
                            ⇒ 漏报只计数不拉黑（既有 MAX_MISSES）
                            ⇒ 12s 上报窗到点即开跑，如实界定参与集合
```

这不是"容错做得好"，这是**把同步点从"每步"移到"每轮"**以后，
单点故障的影响面自然塌缩。再叠加 07 的**降级阶梯**与 **INV-11**
（降级不改变 specHash）：慢节点不配被停下，它换一个便宜的角色继续贡献同一个 θ。

> 代价（诚实）：浏览器端故障更频繁（切后台、杀浏览器、切网络），
> 且**房主单点**是真债（R-09）。我们的立场是"故障更频繁但单点影响更小"的取舍，
> 不是"故障更少"。

### 2.2 round 边界 = 天然一致性快照点（痛点③）

集中式训练的困境：存太勤 IO 爆，存太稀回滚到两天前。
**联邦的每轮聚合点，天然就是一个"免费的一致性快照点"**——聚合完成才广播 θ，
不存在"一半节点在新权重一半在旧权重"的中间态（这正是既有
"中途加入必须 sync 对齐到当前全局权重"不变量的意义）。

于是 Checkpoint 的成本模型被改变了：

| | 集中式 | 联邦（本设计） |
|---|---|---|
| 快照时机 | 需精心选频率（工程难题） | **每轮结束即一致点**，无需选择 |
| 回滚粒度 | 数小时前 | 最近一轮 |
| 替换节点 | 拷贝数十 TB world state | 只需 latest θ（几十 MB） |

### 2.3 content-addressed snapshot：checkpoint 就是 fork（痛点③·补设计）

模型是内容寻址的 ⇒ checkpoint 的表示与模型表示**是同一个东西**：

```
Snapshot := {
  specHash:   string,            // 结构（不变）
  round:      int,
  θRef:       contentHash,       // 参数内容哈希（去重/可校验/可增量）
  dataCursor: DataCursor,        // ★ 数据进度（§6.1：Steel-LLM 教训，v1 漏了）
  dataVersion: string,           // ★ 数据池版本（§6.2：追加/变动时的锚点）
  datasetHash: string,
  compressionState?: contentHash, // ★ 误差反馈残差等跨轮压缩状态（第四轮 INV-24 / ADR-032）
                                 //   压缩开启而此字段缺失 ⇒ 检出为 COMPRESSION_STATE_MISSING
  participants: [nodeId],         // 本轮有效贡献者
  mergePolicy: string,            // 本轮聚合语义的快照
  createdTs:   ISO8601
}

DataCursor := {
  // 精准到"哪几条数据训过了"——不是迭代轮数（见 §6.1 为什么轮数不够）
  trained:  Bitmap | [shardId, localIdx],   // 已消费位置
  rngState: RNGState,                       // shuffle/sampler 的状态
  epoch:    int
}
```

三档快照，对应三种能力（降级阶梯的存储版）：

| 档 | 内容 | 适合 |
|---|---|---|
| **L1 round-snapshot** | 每轮聚合后写 θRef | 一切节点（PC/手机） |
| **L2 step-snapshot** | 步级 θRef（plan() 按 churn 估计间隔） | 强节点 |
| **L3 adapter-snapshot** | 仅 LoRA/adapter 参数（几十 KB） | **移动端友好**，通信量降一个量级 |

**恢复路径**（= 既有 sync 不变量的自然延伸）：
```
节点 rejoin ⇒ 取 latest Snapshot(按 θRef 拉取，内容寻址去重)
        ⇒ specHash 校验（INV-9：同哈希才准续）
        ⇒ 以本地策略续训（降级可换策略，F-INV-3：specHash 不变）
```

> **这里有一个集中式做不到的性质**：因为快照是内容寻址的值，
> "hot restart" 不需要世界状态拷贝，只需要拉取一个哈希 —— 天然的**断点续训**。

### 2.4 溯源链：可定位、可 quarantine（痛点⑤）

Loss Spike 最痛的是"**哪一片梯度有毒**"。2000 卡同步 SGD 里，
梯度已 all-reduce 混在一起，**定位问题等于海底捞针**；只能停训、回滚、猜。

联邦 + 溯源链把这件事变成**可寻址的**：

```
每个 Update 带 { nodeId, strategy, seed?, fitness?, weight, specHash, baseSyncId }
  ⇒ Loss Spike 时可回溯到"这一轮谁贡献了多少"
  ⇒ 单节点 quarantine（降权/暂停）而不停全任务
  ⇒ 换 bad-data 段：让该节点用"跳过该数据段"的续训策略重跑
```

同一机制服务三件事：**工程排障**（Loss Spike）、**安全**（伪造 Update，09 §6）、
**数据审计**（§2.6）。这是"模型即数据"带来的复利。

> **定位粒度升级（★ 2026-10 第二轮评审）**：溯源链把问题定位到**轮级/节点级**；
> 训练数据归因（TDA：TracIn/TRAK/TrackStar）能进一步到**分片/样本级**——一阶形式
> `influence(z, θ) ≈ ⟨∇L(z; θ_c), θ − θ_c⟩` 只需 checkpoint 与逐样本梯度点积，
> 2024 年已在 8B 模型/160B token 语料上验证可行。本设计所需的输入
> （内容寻址的 Snapshot + 每节点 Update + 数据分片表）**本来就要存**——
> 因此 TDA 是零新增数据面的离线能力：bad-shard 定位、探针增益 φ_i 的连续版、
> "哪片数据毒害了模型"的事后审计，三者共用同一计算。定位：P8 起可算，不进协议承诺。

### 2.5 可静态判定的数据污染（痛点④）

> 「你的测试集可能早就混在训练集里被模型看过了……要从几万亿 token 里
> 把这几千条测试题找出来剔除，这工程量你品品。」

中心化：几 PB 里无法审计，只能靠诚实。
公地版：**数据集内容寻址 + ModelMeta 带 datasetHash + 许可准入** ⇒

```
污染检查 := evalSetHash ∈ provenance.datasetHash 的并集 ?
            （n-gram/规范化哈希指纹比对，离线静态可判）
```

这把"考试前透题"从**不可审计的诚信问题**变成**可自动检测的属性**。
评测集本身也内容寻址并公开 ⇒ 任何人都能对任何模型跑同一套检查。
（这是"内部评测集才是护城河"的**反向翻转**的可能入口，见 §3.3。）

### 2.6 人才结构的重组（痛点⑦）

文章定义的那种人（CUDA + NCCL + IB 拓扑 + Transformer + 分布式 + 几千行
shell/Python 混合代码查 Bug）**正是本设计要消灭的岗位形态**：

| 文章的人才要求 | 本设计的答案 |
|---|---|
| 懂 CUDA/NCCL 写算子 | `defineOp` 是**受信贡献**（05 §4），不是使用门槛；组件库覆盖 90% |
| 懂分布式切分（TP/PP） | `plan()` 编译期自动分片（06 §2），人只给约束 |
| 几千行混合代码查 Bug | 结构化诊断（03 §5）+ 自动 passBreak（06 §3）替代人肉 |
| 手工管 checkpoint/权重文件 | content-addressed snapshot（§2.3） |
| 判断"哪个节点的数据把模型带坏了" | 溯源链定位 + quarantine（§2.4） |

> 残余风险（诚实）：WGSL/驱动层 Bug 仍需要稀缺人才。我们把这种人的
> **需求量**压到少数贡献者，而不是假装他们不存在。

## 3. 承认的缺口（以及补不补）

### 3.1 Checkpoint 频率 vs IO 成本（移动端）— **补：纳入 P8**

移动端 IndexedDB 写入慢、配额小。快照策略必须被约束而不是自由：

```
plan() 的 churn 模型：churn(node) ⇒ 建议 snapshot 间隔 + 是否只存 adapter
存储预算：每节点快照配额进 Capability 画像；超出即淘汰最旧 L1
```

状态：**机制已在 §2.3 定义，参数化与配额策略待 P8 实现时标定**。

### 3.2 数据质量自声明（痛点④的质量部分）— **补：抽检协议**

联邦下数据在各节点本地、自声明，没有中央洗数据。既有"持有证明"
（`datasetHash` + 抽检对拍）只防**假持有**，不防**持有真但很脏**。补：

```
AuditProbe := {
  datasetHash,                       // 被检节点声明的数据集
  probeSetId,                        // 公地维护的公开探针集（多领域/多语言）
  metrics: { [probeId]: number },    // 该节点在其数据模型上的探针表现
  sampleFingerprints: [hash],        // 抽样，供对拍
}
```
- 节点周期性上报探针表现 ⇒ 可比、可降权（接入 09 §6 静态校验与声誉层）。
- 探针集是公开资产 ⇒ **顺带给评估公地（§3.3）打了地基**。

状态：**设计草案，实现随 P7/P8**。

### 3.3 评估公地（痛点⑥）— **未设计，只识别机会**

我们的现状只有 `profile()` 结构化指标 + 每家族收敛曲线 + 模型卡，**远不足以**
回答"模型好不好"。文章说"各家内部评测集是护城河"——这在公共网络里是个悖论：
如果没有可比的公共评估，公地模型的好坏无法定价。

**结构性机会（不是承诺）**：07 的降级阶梯里有 **evaluator-only 角色**
（最弱设备也能贡献）⇒ 若存在公开评测集 + 内容寻址的评测记录：

```
EvalRecord := { modelHash, suiteId, metric, score, ts, nodeId }
```
⇒ 任何节点都能评任何模型，记录内容寻址、可复算 ⇒
**众包竞技场（LMSYS 竞技场模式的联邦版）在结构上可行**。

状态：**列为开放问题⑪，不在 P0–P9 的承诺范围内**。不做这个，公地只有"能跑"
没有"好坏"，激励机制（11 §4）缺一半输入。

### 3.4 明确不参与的战斗

| 不争 | 理由 |
|---|---|
| **MFU / 绝对算力** | WebRTC vs NVLink、浏览器 vs A100，差数量级；争即是烧光预算 |
| **数据配比玄学** | 文章自己说是玄学；我们只保证**配比可复现**（进 datasetHash 与 manifest 指纹），不提供配方 |
| **Loss Spike 预测** | 静态分析回答"形状/预算/能力"，回答不了"会不会降"；只做**事后定位与隔离** |
| **中心化数据清洗管线** | 数据不出本地（F-INV-2）是信任根基，不做中央原油炼厂 |

> **MFU 校准基准**（来自 §6 的实证）：单机 8×A100 做足算子融合的现实上限是
> **MFU 43%→63%**（Steel-LLM 实测）。这是我们"不争"的那个数字的参照点——
> 我们不在这个数量级上竞争，但引用它作为"什么叫优化过的单机训练"。

## 6. 小规模实证：Steel-LLM 的教训（第二篇，第一手报告）

> 来源：战士金《从零训练 Steel-LLM》汇总（2024-2026，知乎 + GitHub）。1B 参数、
> 1.1T token、2 epoch、1M step，**借用**的 8×A100 训到 200k step 时**算力被收回**，
> 项目险些烂尾，靠一位老师借出的 H800 续了一个多月才完成。8 个月断断续续，
> 最终 ceval 38 / cmmlu 33，**超过若干大它几倍的机构早期模型**。
>
> 上一篇是"规模化的疼痛清单"，这一篇是"**真的做成了，但代价在哪**"。
> 它对本设计的意义：**它是本项目目标用户的原型**。逐条对设计做校验。

### 6.1 教训一：checkpoint 必须存"数据进度"，不只是参数（★ 设计缺口）

原文的实测细节：

- TinyLlama 的恢复方式是"记录迭代轮数，加载后跳过已迭代的轮数"——
  作者明确指出：**这种方式要求预训练过程中数据不能有变动**。
- 作者的改进：**保存所有数据文件名 + 每条数据的索引**，实现数据进度的精准恢复。
- 并且：**追加数据时，新数据索引要与老数据中未训练的索引重新 shuffle**，
  防止新老数据分布差异过大影响后续训练。

**对本设计的冲击**：§2.3 的 `Snapshot` 最初只存 `θRef`——**这是错的**。
参数 checkpoint 没有数据游标，恢复后要么重复训（浪费）要么跳过（漏训），
且**一旦数据池变动（追加/移除），"跳过 N 轮"立即失效**。

在联邦/公地里这个问题**比单机严重得多**：节点进出、数据池随时增删、
每个节点的本地数据子集都不同。所以：

```
DataCursor（已补进 §2.3）:
  trained  = 精准到条的已消费位置（Bitmap / [shardId, localIdx]）
  rngState = shuffle/sampler 的 RNG 状态（否则恢复后数据顺序不可复现）
  epoch
dataVersion = 数据池的内容版本（追加/移除都产生新版本，Snapshot 锚定它）
```

**铁律（新增 INV-13）**：`Snapshot` 必须同时含 `θRef` 与 `DataCursor`；
只有参数的快照**不是合法快照**。

### 6.2 教训二：数据版本与"追加数据"是一等问题

作者为此专门实现了"新老未训练索引重新 shuffle"和"用哈希检测数据块是否被重复追加"
（对 1.6GB 文件做 MD5 要 9 秒，所以**只哈希头部和尾部**）。

对公地（11）的直接推论：

- **数据池是版本化的**：`dataVersion` 进 `Snapshot` 与 `ModelMeta`，
  任何模型都能回答"你在哪个版本的数据池上训到哪"。
- **追加必须可检测**：内容寻址天然防重复追加（同一块数据同一哈希）；
  但注意原文的务实妥协——**全量哈希太慢**，于是用头尾哈希。
  我们的 `datasetHash` 必须同样务实：**分层哈希**
  （全量内容哈希为权威；头尾哈希为快速预筛，且**必须承认它不是内容哈希**，
  会漏判改写中间部分的数据 → 只在预筛层使用，不进入 specHash）。
- **追加后的分布漂移**：新老数据混训要 reshuffle，这在公地里对应
  "新节点带来新数据"的常态——`plan()` 的数据调度必须把 reshuffle 当默认行为，
  而不是特例。

### 6.3 教训三：数据处理管线本身是未被承认的工程量（★ 新增设计）

原文最被低估的一段：

- pipeline **不是端到端**的，"格式1""格式2"都要回落硬盘 ⇒
  同一份数据存多份不同格式拷贝，需要 **3~4TB 硬盘**；
- 想几小时处理完要开多进程 ⇒ **100GB+ CPU 内存**；
- 用了阿里的 data-juicer，把每个处理步骤抽象成算子、用 yaml 配置自定义流程——
  但**中间缓存占了几百 GB**。

**这是本设计此前完全空白的一层**：我们设计了"模型是数据"（M1），
却没说"**数据管线也是数据**"。而 data-juicer 的"算子 + yaml"恰好证明了
这条路是对的——它已经是数据管线的声明式 DSL。

⇒ **新增 `DataPipelineSpec`（进 11 章）**：

```
DataPipelineSpec := {
  pipelineHash:  contentHash,      // 管线本身可寻址、可复现、可审计
  operators:     [{ op, params }], // 去重/过滤/配比/规范化…（注册表管理）
  inputs:        [datasetHash],
  outputs:       [shardHash],      // 产物同样内容寻址
  resources:     { diskGB, cpuGB, estHours },  // 与 op 契约同构的成本注解
  reproducibility: { seed, versions }          // 否则"复现"是空话
}
```

收益直接对上 M1 的四能力：**管线可寻址**（谁都能复现同一份干净数据）、
**可验证**（`infer()` 可判算子序列合法性/配比越界）、**可分发**（发 spec 不发 PB）、
**可审计**（模型的数据血缘 = datasetHash + pipelineHash）。

> 诚实边界：我们**不做**中心化炼油厂（§3.4），但每个节点本地跑
> `DataPipelineSpec` 是**必要**的——否则"数据不出本地"就等于"数据不清洗"。

### 6.4 教训四：预训练全程掺 SFT 数据 → 四不像

原文实测：预训练里加对话数据，结果"对话和续写的能力都不是很理想"；
作者复盘：少量 SFT 数据会**淹没**在海量原始文本里；正确做法是
**退火阶段才加**（MiniCPM 路线）。而 Steel-LLM **没有退火阶段**，
理由是"高质量的定义模糊、开源数据基本都已清洗过"。

对 07/08 的推论：**数据调度（何时喂什么）是策略层的一部分**，
不只是模型结构问题。`TrainerSpec.schedule` 应能表达"阶段×数据配方"：

```
schedule := {
  stages: [
    { name: 'bulk',   until: 0.9, data: dataVersion('raw') },
    { name: 'anneal', until: 1.0, data: dataVersion('hq') }   // 退火
  ]
}
```

⇒ 这正好接上 §6.2 的 `dataVersion`：**配方是版本化的，进 snapshot、进溯源**。
"配比玄学"我们不解决（§3.4），但**配比必须可复现、可归因**——这是能做到的。

### 6.5 教训五：自证的测试集污染（ch14 §2.5 的活案例）

原文明确承认：因为要在 ceval/cmmlu 上测，所以 **SFT 阶段把 wanjuan 中文选择题
"回炉重造"**；并且做了刷榜实验——把 cmmlu 塞进 SFT 数据，cmmlu 33%→36%，
ceval 几乎不变，结论是"死记硬背答案也没那么容易"（标签只有一个选项字母，
若带解释可能更有效）。

**这是 §2.5「污染可静态判定」的活教材**：

- 在集中式流程里，这种事靠自觉，外人**无法审计**；
- 在公地里，`evalSetHash` vs `provenance.datasetHash` 的并集
  **自动就能标出"该模型的 SFT 配方里含与 benchmark 重叠的数据"**。
- 而且原文还给出了一个微妙的事实：污染**不一定**带来大幅提升（33→36，
  另一项毫无变化）——所以"检出污染"的价值不只是抓作弊，
  更是**让"提升"可归因**：到底是能力还是背题。

⇒ 建议 11 章把这条列为公地的**强约束**：`ModelMeta` 若与已知评测集指纹重叠，
模型卡必须**显著标注**，而不是悄悄算过。

### 6.6 教训六：结构创新的实证成本（soft-MoE 三版才成）

原文：soft-MoE 试了三版（第一版慢且费显存、第二版 loss 收敛不到正常水平、
第三版才可用）；且作者**没有算力再训一遍基线做消融**，
所以无法证明结构改动是好的。另外 RecurrentGemma 的 PyTorch 实现
"慢了几十倍"直接放弃——Google 是在 TPU 上做了工程优化才可接受。

对设计的双重意义：

- **正面**：这正是 08 章家族压测要解决的"变体可表达"问题——
  soft-MoE / SENet 在我们的 IR 里是 `Fan`+`Gate`+组合原语的组合，
  不需要新引擎。但**注意**：作者卡住的第一版问题是"慢且费显存"，
  这恰恰是**内核/融合层**问题——印证 05 章"新算子仍需 WGSL 工作，
  逃生门存在但不免费"的诚实边界，以及 06 章融合验收线的必要性。
- **反面（诚实）**：第二版"loss 收敛不到正常水平"——**静态 `infer()` 永远抓不到**。
  本设计能压缩的是**表达与验证成本**（变体可写、可静态体检、可 A/B、可 fork），
  **不能**压缩"这个变体到底行不行"的实证成本。§3.4 的边界在此再次成立。

⇒ 但有一件事本设计**确实**能做而原作者做不到：**把三版实现连同曲线
内容寻址地存进公地**，让后面的人不用重新烧一遍就能比较。这是"算力断供"式
个人项目的结构性补救。

### 6.7 教训七：单机 8 卡的稳定性 vs 2000 卡的故障常态（校准）

原文：单机 8×A100 "训练还是比较稳定的，没有出现过啥 error"，
唯一故障是**机器网断了**（wandb 卡住）。而上篇（§1）说 3000 卡规模下
"硬件故障是常态"。

**校准结论**：故障率是规模的函数。§2.1 的"软同步屏障"优势
在 8 卡时几乎不存在（同步 SGD 也很稳），**它的价值随规模上升**。
必须诚实：我们的联邦网络在**浏览器 churn**（切后台/杀浏览器/省电断网）上
比 8 卡更容易掉线，但**单点影响面更小**。这是"更频繁但更不致命"的取舍，
不是全面更优。

### 6.8 教训八：算力断供是本项目最好的广告

项目差点死于"朋友搞到的 A100 被供应方收回了"。作者自己总结：
"随着开源数据不断增多、算力价格不断降低，个人或小机构正经预训练一个小型号
LLM 并不是遥不可及"——但**他的成立靠的是运气+人情**（借到 H800 的老师）。

这正是 01 §2 第一幕论点的最强实证：

> 个人已经**有能力**训模型（数据开源、技术公开），却**没有能力保证算力持续**。
> Steel-LLM 用 8 个月 + 两次借卡 + 一次险些烂尾，换来 ceval 38。
> 一个公共联邦网络的价值不是"更快"，而是**把"再借一个月卡"这件事
> 从求人变成几十台闲置设备的自然聚合**。

⇒ 建议把这条写进 01 §4 北极星指标的注解，作为**为什么要做公共网络**的
实证注脚（而不是抽象论证）。

### 6.9 教训九：SFT 数据分布错配的实证

原文：Infinity-Instruct 700w 条里 **90% 是英文**，与预训练分布（20% 英文）
严重不符 ⇒ ceval 33%；改抽 70w 中文并糅合其他三份 ⇒ 38%。

⇒ 这印证了 §6.4 的"配方可复现可归因"必要性，也印证 11 章的
**数据集指纹 + 分布元数据**（lang/domain/tokens）必须是登记项——
否则"换一份 SFT 数据"这种关键决策无法被记录和复现。

## 7. 小规模实证第三篇：ZGCM-1 —— AI4AI 的实证边界

> 来源：北京中关村学院 7 名博士生（2 人工智能、2 网络，另 3 人分别来自化学、生物、网安）
> 用一个暑假从零训练 7B 模型 ZGCM-1，并开放各阶段数据与配方、权重、训练代码、
> **中间 checkpoint 与日志**。通用评测与 Qwen3-8B 同规模相近，部分数学/搜索评测
> 可与 Qwen3-235B-A22B、GLM-5.1 比较。研发方式：**几人调度几百个 Agent**，
> 分数据/实验/评测子团队，自研 ZGent 平台沉淀共享上下文与可复用 Skill。
>
> 这一篇的意义与前两篇不同：**它验证的正是本设计 M2 护城河（AI 原生编写）本身**，
> 并且给出了我标注为"未回答"的评估缺口的一个**可用参照实现**。

### 7.1 「loss 还在降，模型却退步了」——INV-13 的第二个独立实证

ZGCM-1 遇到的一次事故：训练曲线正常、loss 仍在下降，模型能力却明显退步。
最终定位到**底层数据分片与 shuffle 环节**：实际喂进训练的数据比例发生了波动，
"模型吃进去的东西，并不总是他们以为的那份配方"。

**这是 Steel-LLM §6.1 同一个坑的第二次独立出现**：

| 团队 | 规模 | 症状 | 根因 |
|---|---|---|---|
| Steel-LLM | 1B | 续训恢复/追加数据困难 | 数据进度只记轮数，数据一动即失效 |
| ZGCM-1 | 7B | loss 降但能力退步 | **数据分片/shuffle 导致实际配比漂移** |

两个团队、两种规模、同一个根因类：**"配方"与"实际吃到嘴里的"之间没有可验证的绑定**。

⇒ **升级判定**：这不是 R-19 那种"中概率风险"，而是**已被两次独立证实的必然发生的问题**。
本设计的对策（`DataCursor` + `dataVersion` + 追加后强制 reshuffle + 配方进 `Snapshot`）
因此从"应有"升级为"**必须有**"，且必须在 P0/P8 就落地，不能等。

另外注意他们的补救措施组合，恰好对应本设计的两件事：
**更密集地保存中间 checkpoint**（= 我的 L2 step-snapshot）+ **追踪能力变化**
（= §7.2 的探针评测）。

### 7.2 ACE 原子能力评测：填上 §3.3 的评估缺口（★ 本篇最大收获）

我在 §3.3 把"评估"判为**未回答**、只识别了机会。ZGCM-1 给出了一个**已跑通的参照实现**：

```
ACE 原子能力评测体系：
  能力原子化    18 类 / 183 项
  探针          2503 个
  评测方式      内部分布式评测系统
  一轮诊断      ~2-3 分钟
  用途          "一次修改让哪里变好了、哪里退步了，下一步该查数据还是训练方法"
```

三个可直接吸收的设计点：

1. **能力要原子化，不能只看总分**。他们因此知道"并非每项能力都同步受益"
   （§7.6 的 SFT 质量筛选也是这样：整体提升但非全面受益）。
   ⇒ 我的 `EvalRecord` 必须按**原子能力**记录，而不是单一分数。
2. **诊断必须快**（2-3 分钟/轮）。慢的评估无法进入"改→测→判"的回路。
   ⇒ 评估要能被 `plan()` 调度成低开销任务，且 **evaluator-only 角色**
   （07 降级阶梯里最弱设备那一档）正好承接它——**最弱设备也能参与评估**。
3. **探针是资产**：183 项 × 2503 探针是可复用、可版本化、可复算的。

⇒ **统一设计（重要简化）**：`AuditProbe`（§3.2，数据质量）与 `EvalRecord`（§3.3，模型质量）
本质是**同一个原语**——**可复用、内容寻址的能力/质量探针**，只是施加对象不同
（数据集 vs 模型）。统一为：

```
Probe := {
  probeHash:   contentHash,        // 探针集本身可寻址/可复算
  target:      'dataset' | 'model' | 'update',   // 施加对象
  atoms:       [{ id, capability, items: [itemHash] }],   // 能力原子化
  suiteHash:   contentHash,        // 归入哪个评测套件
  cost:        { estSeconds, deviceClass },        // 供 plan() 调度
  evalSetHash: contentHash         // 用于污染检测（11 §2.5）
}
ProbeResult := { probeHash, targetHash, scores: { [atomId]: number }, ts, nodeId }
```

这把 §3.2/§3.3 两个半设计合成一个，且顺带解决了 11 §2.5 的污染检测
（`Probe.evalSetHash` vs `provenance.datasetHash`）。

### 7.3 Agent 自主性的实证边界：L1-L5 分级（★ 直接修正第 04 章）

ZGCM-1 让 9 名核心参与者按 L1-L5 给 11 类研发任务评级，结论非常具体：

| 任务 | 实测自主性 | 含义 |
|---|---|---|
| 实验监控与部署 | **L4** | 人给目标与约束后，Agent 可独立规划、执行、据反馈调整 |
| 模型架构与学习算法设计 | **L2** | 主要是帮助实现已有方案、运行预设实验 |
| 研究什么 / 关键设计怎么选 | **L1-L2** | 仍需人主导 |

**这直接修正我在 04 章的写法**。我在 LANG-V3/V4 写的"agent 生成 08 任一家族的合法 IR"
暗示 AI 能独立做**建模**；实证边界是：**AI 在"执行/监控/编排"上已达 L4，
在"架构与算法设计"上只有 L2**。

⇒ 04 章必须把验收线改写为**分层承诺**，而不是笼统的"AI 能写模型"：

| 层级 | 任务 | 承诺 |
|---|---|---|
| **AI 主导（目标 L4）** | IR 生成与修复、静态诊断、成本优化、实验编排、日志监控、故障定位、评测执行 | 可无人值守迭代 |
| **人机协作（目标 L3）** | 在既定家族内改结构/换策略/调配方 | AI 提议，人审 |
| **人主导（目标 L2，不承诺更高）** | 研究什么、选哪条技术路线、关键设计取舍 | AI 只辅助实现 |

> 这个校准**提升**了可信度：与其宣称"AI 自动做研究"（会被第一个失败打脸），
> 不如宣称"AI 把 L4 的执行层接到 L2 的架构层上"——这正是 ZGCM 7 个人能干完的原因。

### 7.4 ZGent：Skill 沉淀 —— 注册表要加"经验层"

ZGCM 的关键基础设施不是"几百个 Agent"，而是 **ZGent**：
把会议讨论、研发决策、计划积累成**共享上下文**；把**验证过的脚本、工作流、debug 经验
沉淀为可复用的 Skill**；后加入的 Agent 接着此前的经验做事。

⇒ 这补上了我 04 章注册表缺的一层。我设计了 op schema（**语义词汇表**），
但没有设计**经验词汇表**：

```
Skill := {
  skillHash:  contentHash,
  kind:       'workflow' | 'debug' | 'script' | 'playbook',
  provenance: { validatedOn: [specHash], author, reviewId },
  body:       结构化步骤（同样可寻址/可审计/可分发）
}
```

并且这直接扩展了 11 章公地的**资产类别**：不只是数据/模型/适配器，
还有 **Skill（可复用工作流与排障经验）**。对"公共网络"的意义很大：
新节点不用从零踩坑，直接继承别人验证过的 debug 经验。

### 7.5 开放"建造记录"：TrainingTrace 作为一等公地资产

他们开放的不只是最终权重，而是**各阶段权重、中间 checkpoint、训练代码、数据配方和日志**，
理由是：让其他研究者"**追踪能力如何形成，检查一个改动究竟带来了什么**"。

这与我 11 章的模型公地是同一件事，但我要补一个明确的资产类：

```
TrainingTrace := {
  specHash,                 // 结构
  stages:   [{ name, θRef, dataVersion, schedule }],   // 阶段权重 + 当时配方
  snapshots:[Snapshot],     // 中间 checkpoint（内容寻址）
  logs:     [contentHash],  // 训练日志
  probes:   [ProbeResult],  // 能力演化曲线（7.2）
  findings: [Finding]       // 条件性实证结论（7.6）
}
```

> 值得注意：**Steel-LLM 作者与 ZGCM 团队独立地说出了同一句抱怨**——
> "读技术报告时想知道却看不到的细节"。两批人、不同规模、同样指向
> **训练过程不可追溯**这个缺口。这是本设计 M1 护城河最硬的实证：
> 我们要做的不是"又一个训练框架"，而是**让建造记录本身成为可寻址的公共资产**。

### 7.6 效率即实验数量；结论是有条件的

两条实践哲学，都直接对应本设计的取舍：

1. **"省下的卡，拿来多试几个想法"**：局部+全局混合注意力把上下文 16K→64K→256K，
   256K 下吞吐 ~3.94×、KV Cache ~1/6；Muon+FP8+延迟缩放+TWEO，
   16K 预训练同 loss 相比 BF16/AdamW 基线 ~4.2×。
   ⇒ 我从不争 MFU（§3.4），但这条给出了**争它的真正理由**：
   不是为了快，是为了**让"试一个假设"的边际成本下降到可以多试几个**。
   本设计在同一方向上的杠杆不同但同向：静态体检（不跑就排错）、
   低通信/前向-only 策略（弱设备也能试）、公地复用（不用重烧别人的失败）。
2. **"一个方法在什么条件下有效、需要付出什么代价"**：他们的实战发现全是条件句——
   SFT 更严质量筛选让样本减少 44.9% 整体反而提升（**但并非每项能力都同步受益**）；
   长思维链比例过高会**损害指令遵循**；Agent 数据**不能脱离通用能力单独训练**。
   ⇒ 公地若只存"模型/数据"，这些**条件性结论**会再次丢失。
   `TrainingTrace.findings` 因此不是可选项：**公共网络最该积累的资产是
   "什么条件下什么方法有效"**，而不是又一个 7B 权重。

另外他们的 SFT 数据处理流程明确包含**「评测去污染」**一步——又一次印证 11 §2.5
应把"去污染"设为 `DataPipelineSpec` 的**一等算子**，而不是可选项。

### 7.7 人才论点的最强实证

7 个人里只有 2 个是人工智能方向，另外 5 人来自网络、化学、生物、网安，
用一个暑假从零训出 7B。支撑它的是：几百个 Agent 分工 + ZGent 的 Skill 沉淀 +
人类只负责目标/约束/关键判断。

⇒ 这是 ch14 §2.6「消灭稀缺复合型人才」论点从**推论**变成**实证**。
但也要诚实：他们的成功建立在**已有开源底座**（数据、框架、基线方法）
+ **足够的启动算力** + **强指导老师**之上。本设计能补的是第三项
（把"启动算力"从申请变成公共聚合，见 §6.8），前两项正是公地要提供的资产。

### 7.8 渐进式上下文扩展：开放问题②的一个具体案例

他们把上下文在训练过程中从 16K 逐步扩展到 64K、256K。这不是"任意动态 shape"，
而是**调度驱动的形状增长**。

⇒ 开放问题②（动态 shape 的符号维边界）由此获得一个明确答案方向：
**只支持"schedule 声明的阶段性形状"，不支持任意数据相关形状**。
前者可静态推导（`schedule.stages[].shape`），后者退化为运行时检查。
这比"全静态 or 静态+运行时兜底"的二选一更准确。

## 8. 前沿规模实证：Marin —— 我的机制被独立实现了一遍

> 来源：Marin 项目（500B+ MoE 前沿模型训练平台，开源）。本文列出它与玩具训练的
> 十维鸿沟：PB 级数据流水线（DataKit + Zephyr）、跨大洲异构集群调度（Iris + 联邦路由）、
> MoE 工程实现、反应式训练过程（Tootsie Roll）、缩放定律（Delphi）、80 个 Agent 实验筛选、
> 秒级遥测（Finelog）、系统性去污染、严格可复现（Artifact 系统）、开放开发。
>
> **这一篇的价值与前两篇都不同：它不是"痛点清单"，而是"别人已经把我设计里的
> 好几个核心机制工程化了"。** 逐条对照，可以看到哪些设计被外部独立验证、
> 哪些细节我没想到、哪些我仍然是空白。

### 8.1 Artifact 系统：我的 specHash 规范化规则被独立实现（★ 最强验证）

Marin 的 Artifact 系统用**内容哈希**标识每个 pipeline 步骤的输入输出：
"只要输入不变，输出就从缓存读取，不重新计算"，"跨地区复制数据时，相同的输入
产生相同的输出路径"。核心约束原文：

> 步骤的 `hash_attrs` 必须包含它读取的每一个参数，且**不能包含任何地区特定的路径**。
> 违反这条规则，同样的数据在不同地区会得到不同的输出路径，缓存就废了。

这正是我在 03 §4 定的规范化规则（**排除不确定字段**：`device`/`shard`/`precision`/
`createdTs` 不进 `specHash`），Marin 独立得出了同一条规则，**并且记录了我没有写的
具体失效模式**：把环境特定信息混进哈希 ⇒ 同数据不同机得到不同寻址 ⇒ 缓存/去重全废。

另外它用 **uv.lock 锁定全部依赖版本**，避免"库升级导致缓存失效"——
这给我的开放问题①（IR 版本化）与 op 契约的 `version` 字段提供了具体答案：
**依赖版本必须进哈希，且必须可锁定**。

⇒ **改动**：03 §4 补入 Marin 的失效模式作为"为什么必须排除不确定字段"的实例；
op 契约与 `DataPipelineSpec` 增加 `depVersions`（锁定依赖）。

### 8.2 LCG shuffle 会保留局部结构 ⇒ 必须用无局部结构置换（★ 我没设计到）

Marin 在 32B 训练中发现 GSM8k 被污染，根因之一是 **LCG shuffle 保留局部结构**，
导致评测数据混入后仍以"近似原文"形态存活。修复用 **Feistel 置换**替代 LCG。

**这条直接击中我的设计漏洞**：我的 `DataCursor.rngState` 只说了"存 RNG 状态"
（为了恢复后顺序可复现），却没规定**用什么置换**。如果实现时顺手用了 LCG：

- 数据顺序会保留局部结构 ⇒ 近重复样本在 batch 内相邻 ⇒ 过拟合风险（Steel-LLM 教训同源）；
- 污染数据会以近似原文形态存活 ⇒ 我的 11 §2.5 污染检测可能被绕过；
- 跨设备"同 seed 同顺序"也不成立（LCG 的实现细节/周期在不同位宽下不同）。

⇒ **新增 INV-14**：数据 shuffle/采样必须用**无局部结构的 counter-based 置换**
（Philox/Feistel），**禁止 LCG**。与 INV-10（RNG 跨设备可复现）是同一条要求的一体两面。

### 8.3 容量不跨后端累加 + 预留账本（★ 我 ch09 的两个具体缺口）

Marin 联邦路由的两条精妙细节，直接对应我 09 章 `plan()` 的缺口：

1. **容量不跨后端累加**："8 卡作业不能拆成 4+4，因为所有卡需要在同一个高速互联域内通信"。
   ⇒ 对我的分片设计是**决定性约束**：peer 之间的 WebRTC **不是一个互联域**
   （带宽差 3-4 个数量级、无集合通信原语）⇒
   **跨 peer 的张量并行应被禁止，只允许层/流水线/专家分片**。
   我把这条写成 09 的硬约束（此前只说了"层切分/张量切分/专家切分"可选，太乐观）。
2. **预留账本**：心跳 30s 一次但 tick 更频繁，若不记录"自上次心跳以来已分配多少"，
   同一空闲容量会在一个心跳窗口内被反复分配 ⇒ 超分配。
   ⇒ 我的 `plan()` 集群调度必须引入**预留账本**（有效容量 = 上报可用 − 已预留），
   这是 Capability 协商（09 §3）缺的一环。

### 8.4 Tootsie Roll：反应式多阶段训练（★ 我 `schedule.stages` 的参照实现）

Marin 8B 的五个阶段**没有一个是预先计划的**：
Kestrel（DCLM + WSD-S）→ Ocelot（**获得新硬件 ⇒ 迁移、batch +50%、换调度**）→
Jellyfish（**DCLM 用完 ⇒ 冷却，折叠高质量数据**）→ Phoenix（**发现还有时间 ⇒ 重新加热**）→
Starling（**时间又不够 ⇒ 二次冷却**）。

这正是我从 Steel-LLM 退火教训推出的 `TrainerSpec.schedule.stages`（07 §7.1），
Marin 给出了**最完整的真实参照**：阶段切换的触发条件是**反应式**的
（新硬件 / 数据耗尽 / 时间预算变化），每个阶段可换 数据版本 + batch + 学习率调度。

⇒ **改动**：07 §7.1 以 Tootsie Roll 为参照案例；并明确 `stages` 的触发条件
（`until` 不只是进度比例，还应支持 `on: 'data-exhausted' | 'time-budget' | 'hardware-change'`）。
这也再次印证 INV-13：每个阶段都锚定自己的 `dataVersion`。

### 8.5 80 个实验漏斗 + 开放开发（★ 我公地设计的最强实证）

Marin 的 MoE 改进筛选：**80 个小规模实验（d512-d2048）→ 16 个有效、32 个明确排除、
13 个混合、9 个有前景**。原文结论："80% 的想法失败，但失败排除了错误方向"。

它的开放开发四件套，与我的设计几乎一一对应：

| Marin 的做法 | 我的设计 |
|---|---|
| 每次实验（**成功和失败**）记 GitHub issue | `TrainingTrace` + 开放问题⑰「失败实验全记」 |
| 每个设计决策有设计文档，记录**为什么选 A 不选 B** | 13 §3 决策日志 **ADR** |
| 每次事故有事后分析（Echo 知识库） | `Skill`（debug 经验） |
| 每个训练阶段有回顾文章，包括犯过的错 | `Finding`（条件性实证结论） |

原文说这种透明度"在前沿模型训练中极其罕见。大多数团队只发布最终结果，
隐藏所有失败和弯路。但正是这些失败和弯路，构成了最有价值的过程知识"。

⇒ 这是 **R-26 / 开放问题⑰** 的实证依据：**公地最该积累的是"失败+条件"，不是又一个权重**。
Marin 的 80→16 就是这个主张的量化版本。

### 8.6 「小规模有效的架构，大规模可能崩溃」（第三个数据点）

Marin 32B 在 70k 步损失爆炸，重启失败、换 Muon 失败，最终靠 **Qwen3 架构的 QK-Norm**
（对 Q/K 做 RMSNorm，防深层注意力 logits 爆炸）才稳定。教训原文：
**"8B（32 层）没问题，32B（64 层）就崩溃了"**。

这是我在 §6.6（soft-MoE 三版）/ §7.6（ZGCM 的条件性结论）之后的**第三个数据点**，
而且它给出了具体机制（深层注意力 logits 爆炸）和具体解（QK-Norm）。

⇒ 两处改动：① op 注册表把 **`Attn.qkNorm`** 与 **`ZLoss`** 正则提为一等
（Marin 冷却阶段用 Z-Loss 防 logits 爆炸）；② R-23 的"合法但训不动"从
"中概率"上调——**已有三个独立实证**，且它给出的启示是：`infer()` 的静态检查
必须包含**深度/宽度相关的稳定性启发式**（如层数超过阈值时提示考虑 QK-Norm）。

### 8.7 Finelog：可观测性的三条可迁移原则

Rust 实现、不可变 Parquet 段、`.fidx` 分段索引（三元组布隆/倒排/值计数/覆盖投影）、
命名空间隔离、后台压缩。三条原则可直接迁到我的 `profile()`/诊断/日志设计：

1. **不可变追加段 + 派生索引**：索引是源的派生数据，源变则索引凭**校验和**失效
   ⇒ 与内容寻址同构，也保证联邦场景下日志可审计、可重放。
2. **测量数据与决策数据分离**（Finelog vs SQLite），各自独立优化
   ⇒ 我的结构化诊断（03 §5）应与 trace/遥测分离：诊断是**决策**数据，
   trace 是**测量**数据。
3. **命名空间隔离**（`iris.worker/task/profile`）⇒ 联邦场景必须按
   nodeId/round/specHash 分域，避免跨房污染（与 10 §7 存储分域一致）。

### 8.8 Delphi：`plan()` 缺"用小数预测大数"（我的空白）

78 个 IsoFLOP 扫描点（3×10¹⁸ ~ 10²³ FLOPs），每点二次拟合，幂律 `D* ~ A × C^α`，
**外推 300 倍**，用几小时小实验预测数百万美元训练的最优配置。

我的 `plan()` 只有**静态成本模型**（FLOPs/显存估计），没有"从小规模实验外推最优配置"
的能力。这是一个真实空白，但它是研究级的。

⇒ **立场**：`plan()` 预留 `scalePredict()` 接口（输入小规模实测点，输出大规模建议），
**不进 P0-P9 承诺**，列为开放问题⑱。它与 ZGCM"省下的卡多试几个想法"是同一方向：
让小实验**更有信息量**，而不只是更便宜。

## 9. 演化维度：AXLearn —— 「代码复杂度」被做成了系统指标

> 来源：Apple MLSys 2026 Industry Track《AXLearn: Modular, Hardware-Agnostic
> Large Model Training》。它把**模块化与硬件无关**提升为与性能、扩展性并列的系统目标，
> 并提出 **LoC-Complexity**：新增功能时，**现有接口修改量**随模块数 N、变体数 M
> 如何增长（O(1) / O(N) / O(NM)）。
>
> 本篇与我设计的关系最特殊：**它从"代码演化成本"这个方向，独立论证了我
> 「模型即数据」的同一个结论**——而且给出了一个我当时没有的量化指标。

### 9.1 组合而非继承：我的 IR 结构上就是 O(1)（★ 对 M1/M2 的量化验证）

AXLearn 的核心诊断：子类继承会把局部变化沿调用链向上扩散。
"把 Transformer 的 FFN 换成 MoE 可能只需改几行实例化代码"，
但真实工程里要先继承父层、再让更高层知道新子类和新参数。
论文案例：DeepSpeed 的 QwenV2→QwenV2-MoE **仅接入就需要 200+ 行**（不含 MoE 层本身）；
在 20 个模型变体 × 10 个注意力变体的假设规模下，估算 **DeepSpeed 约 4000 行接口修改，
AXLearn 为 0**（复杂度 O(1)）。做法是用**组合式配置**：递归 Config Modifier 约 10 行
遍历配置树完成替换，同一段逻辑已用于 1000+ 实验配置。

**这正是我 Spec IR 的形态，而且我比它更彻底**：

| | AXLearn | 本设计 |
|---|---|---|
| 表达单位 | Python 配置 + 模块类（**仍有继承可用**） | **纯数据树**（结构上不可能继承） |
| 换 FFN→MoE | 递归 Config Modifier ~10 行 | **替换一个数据节点的值**（`ir.diff` + fork） |
| 接口修改量 | 0（需靠"严格封装"纪律保证） | **0（由数据形态保证，不依赖纪律）** |
| 复杂度 | O(1)（论文论证） | O(1)（结构性） |

⇒ **关键差异**：AXLearn 的 O(1) 是**纪律性**的（要靠严格封装 + 分层配置约束团队），
我的 O(1) 是**结构性**的（IR 是数据，没有继承链可扩散）。
论文自己承认代价："模块化也会牺牲短期随意修改 Python 执行代码的自由，
开发者需要先把新思想抽象成参数化模块"——我的设计从第一天就付了这个代价。

⇒ **吸收**：把 **LoC-Complexity 采纳为正式验收指标**（见 §9.6），
替代 v2 起用的"每家族 ≤100 行"这种粗略说法。

### 9.2 Invocation Context：我缺的那一层状态机制（★ 本篇最大技术收获）

AXLearn 遇到一个我**没有正面回答**的问题：JAX 要求被 `jit`/`grad` 的程序保持函数式，
但训练天然有状态（参数、PRNG key、训练摘要、共享嵌入、模块输出）。
"如果要求每个模块手工接收和返回这些侧输入/侧输出，模块就会重新感知整棵状态树，
**严格封装随之失效**。"

它的解法 **Invocation Context**：父模块调用子模块时，系统自动把子模块状态与上下文
**压栈**、**拆分 PRNG Key**、为摘要和输出创建独立集合；子模块返回后上下文出栈、
结果汇总到父模块。用户可以按命令式方式写层逻辑，底层仍保持函数式。
**关键细节：Context 持有模块引用，但模块不反向持有 Context。**
于是 Optax 优化器等模块树之外的调用也能访问状态；权重共享由系统层遍历上下文完成，
无需模块间多层属性查找。

**这正好补上我设计里三个一直含糊的机制**：

| 我的现有设计 | 缺什么 | Invocation Context 的答案 |
|---|---|---|
| `Bus`（provide/inject）我说"只读快照 + build 期报环" | **没有说清谁持有状态** | **上下文栈持有**；节点不反向持有 ⇒ 天然只读、天然不成环 |
| INV-10/14 的 RNG"每个 op 声明 counterScope" | **key 如何沿层级拆分**没有机制 | 调用即**自动拆分**，父子各得独立 key 段 |
| `tie="embed"` 我说"backward 末尾按参数 ID 归并" | 归并是补丁，不是机制 | 权重共享由**系统遍历上下文**完成，节点间不做属性查找 |

⇒ **新增设计（进 03 章）`Invocation Context`**：

```
Ctx := {
  stack:   [Frame],            // 调用栈；父→子压栈，返回出栈
  prng:    (path) → Key,       // 按栈路径派生 key（INV-10/14 的落地机制）
  outputs: { [collection]: TensorRefs },   // 摘要/输出集合，按帧隔离
  params:  ParamTable          // 共享参数（tie）在此登记，grad 按 ID 归并
}
铁律（INV-15）：Context 持有节点引用，**节点不得反向持有 Context**
                 ⇒ 侧通道只读、拓扑无环、层级无关性成立
```

> 这条"单向引用"铁律是我从本篇拿到的最有价值的一行：它同时解决了
> Bus 的耦合问题、RNG 的拆分问题、参数共享的归并问题——**一个机制，三个老问题**。

### 9.3 Mesh Rule：硬件差异集中在规则层（验证我的 plan() + Capability）

AXLearn 的硬件无关性建立在 XLA + GSPMD 上，但论文明确说"仅依靠编译器不足以获得
峰值性能"。它的做法是 **Mesh Rule：把"硬件类型"映射到一组 Config Modifier**，
使平台相关优化**集中在规则中，而不是散落到模型代码**。

注意力是典型例子：同一个 Flash Attention 模块，GPU 上优先 cuDNN、稀疏场景回退
Pallas 内核；Trainium 上调 AWS Neuron 的 NKI 内核；TPU 上用 Splash Attention。
**上层模型仍只看到统一注意力接口。**

论文的原话精确地表达了我 05/06 章的立场：
"AXLearn 实现的是'**模型和训练配置不绑定硬件**'，而不是'所有硬件共享完全相同的
底层 Kernel'。"——即：契约统一、内核分后端、逃生通道保留。

⇒ 我的 `plan()` 就是 Mesh Rule 的一般化（它同时决定后端/策略/分片/精度/RNG），
我的 `Capability` 画像就是"硬件类型"的扩展（还含策略与网络）。
**吸收点**：把"硬件→Config Modifier 映射表"作为 `plan()` 的显式输出项
（`backendRules`），并把上表这个注意力后端选择例子写进 06 §6 作为参照。

### 9.4 AOT 同一代码路径（对我的 infer→plan→emit 是强验证）

"让用户在单机环境提前分析显存和 FLOPs，发现分片错误或 OOM，无需先申请大规模集群。
**由于 AOT 和正式训练走同一代码路径**，本地编译通过的程序更可能在大规模环境
正常运行，减少昂贵的空跑和排队。"以及"Golden Configuration 测试，让配置变化
形成可审查差异"。

这就是我的 `infer() → plan() → emit()` 管线 + `ir.diff` 可审查差异 + ADR。
⇒ **新增 INV-16**：静态编译路径与运行路径**必须是同一套代码**；
不允许"编译时一套近似模型、运行时另一套"（否则静态结论不可信）。
这条对我的 06 章是硬约束，也回敬了 Marin 的 Artifact（缓存有效性依赖同路径）。

### 9.5 Goodput、异步检查点与热替换（校准我的 Snapshot 与北极星）

| AXLearn 机制 | 对本设计的意义 |
|---|---|
| **Goodput**（资源真正用于有效训练的比例） | **比 MFU 更适合当指标**。联邦里 churn/等待吃掉的是墙钟时间，Goodput 直接度量"有效训练占比"⇒ 应进 01 §4 北极星与 06 profiling |
| 异步检查点写 S3/GCS，**训练不必等序列化**，后台 GC 旧版本 | 与我 L1/L2/L3 三档快照一致；补一条：**快照写入必须异步**，不得阻塞训练步 |
| Watchdog 监控 step 时间 + 硬件利用率，异常可重启/通知/转储调用栈 | 结构化诊断（03 §5）应含 watchdog 事件；与我"诊断与 trace 分离"原则合流 |
| 恢复时"数据并行副本已有相同权重，**从健康副本广播状态**" | **这就是我的 rejoin sync + 聚合**。联邦场景更自然：θ 本来就在聚合端 |
| 持久化编译缓存避免重启后重编译 | = 我的 **CompileOnce-Reuse**（ENG-V1） |
| **32768 TPU 真实故障：热替换 4 分钟 + checkpoint 恢复 9 分钟 = 21 分钟有效损失** | **我的 Snapshot 验收线的量化参照**（SNAP-V2/V3） |
| K8s 切片级热替换 + **预留健康副本**接替故障节点 | 与 Marin 的预留账本（09 §5.2）合流 ⇒ 联邦里"预留副本"= 预留节点 |

### 9.6 训练→推理复用：KV cache 封装在模块内

"KV Cache 被封装在注意力模块内部，系统可以替换为更适合推理的缓存布局，并接入
连续批处理、Prefill/Decode 分离、分页 KV Cache，**而不需要重新实现整套模型**。"

⇒ 验证我 03 §7 的「同一 IR 多用途」与 `Cache` 组件 + `phase=prefill/decode` 设计。

从"原则"变成"组件替换"。

## 10. 调度维度：FlexPipe —— 「换一个坐标系」的同一动作

> 来源：上海AI实验室 DeepLink 团队 FlexPipe（arXiv 2510.05112）。把流水线调度
> 写进十行代码，并让大模型训练最高加速 2.28×。核心洞察：**调度 = stage 放置 +
> 两个遍历优先级**（先算 forward 还是 backward；多 stage 同设备时先算谁）。
> 参数化之后，1F1B / Interleaved 1F1B / Chimera / Hanayo / ZB-H1 全部能用几行表达，
> 枚举即可秒级到分钟级搜出新调度。
>
> **这篇与我设计的关系是"同构动作"：它和我做的是同一件事——换一个坐标系。**

### 10.1 「换坐标系」是可迁移的方法论（★ 本系列最强的一条元结论）

FlexPipe 的总结原话："关键并不在于发明了某一个新调度，而在于**换了一个刻画调度的
坐标系**：流水线调度的本质不是一张张手绘的时序图，而是'stage 放置 + 两个遍历优先级'
这寥寥几个自由度。"

这正是本设计对**模型定义**做的事：模型的本质不是一段带副作用的 Python 代码，
而是**一棵可寻址的数据树**。两个领域、同一个动作：

| | 原坐标系 | 新坐标系 | 坍缩效果 |
|---|---|---|---|
| FlexPipe（调度） | 手绘时序图 | 放置 + 2 个优先级 | 1F1B 从 ~700 行降到 11 行；搜索从"逐时隙求解"（Tessel 8 卡即失败）降到 32 卡 9 分钟 |
| 本设计（模型） | 继承式 Module 代码 | Spec IR 数据树 | 换 FFN→MoE 从 200+ 行降到替换一个节点；接入成本从 O(NM) 降到 O(1) |

⇒ **可迁移的设计原则（立为 ADR-009）**：面对"手工雕琢 + 空间爆炸"的问题，
先找**低维参数化**，让搜索与编程同时坍缩。判据是 FlexPipe 的原话：
**"空间小而稠密——里面几乎全是结构合理的调度，这是搜索开销远低于逐时隙求解的
根本原因。"** 我的 `plan()` 决策空间必须按同一判据构造（见 §10.2）。

### 10.2 plan() 搜索空间的构造原则（★ 直接可用的配方）

FlexPipe 的 Auto-tuner 给了可复用的具体配方：

```
参数空间：  (pp, dp, mbs, 放置策略, fstp, bstp, ctp)
剪枝规则：  interval 仅在环形放置时启用；ctp 默认不取 fwdfirst；调度单元默认 1
profiling： 采集结果落盘复用，避免重复采集
```

⇒ 本设计 `plan()` 的对应构造（06 §2）：

1. **参数化而非枚举时序**：把"调度决策"表达为少数有语义的自由度
   （分片方式 / 通信策略 / 精度 / recompute / 在途 micro-batch 数），
   **不**去枚举指令表。
2. **剪枝规则内置**：非法/无意义组合在**搜索前**排除
   （"跨 peer 禁张量并行"就是一条剪枝规则，09 §5.1）。
3. **profiling 落盘复用**：与 ENG-V1（CompileOnce-Reuse）同源；
   内容寻址使 profiling 结果本身可缓存、可跨会话复用。
4. **空间必须"小而稠密"**：若搜索空间里大量点结构非法，
   说明参数化选错了轴——这是判据，不是感觉。

### 10.3 调度必须模拟「不可见远端状态」（★ 对联邦设计的关键约束）

FlexPipe 的 **Local Buffer**：每个 actor 把当前调度步状态写入本地缓冲，
调度步结束后统一提交——原文说这是"**用来模拟分布式环境中'同一时刻看不到远端状态'
的现实约束，保证生成的调度在真实分布式环境中可执行**"。

**这条对 09 章是必需的**：我的 `plan()` 在聚合端生成全局执行计划，
但联邦场景下**任何时刻都没有人能看到全部 peer 的真实状态**。
若计划假设"我同时知道所有节点在做什么"，它在真实集群里不可执行。

⇒ **新增约束（进 09 §3）**：`plan()` 生成的执行计划必须满足**可调度性**——
每一步只依赖**已确认**的信息（上一轮上报的能力/进度/预留），
不得依赖"当前瞬时状态"。这与 Marin 的预留账本（09 §5.2）是同一约束的两面：
一个防超分配，一个保可执行。

### 10.4 气泡填充：等待 peer 时做有用功（★ 新的联邦优化，直通 Goodput）

FlexPipe 的**梯度分离算法**：检测到气泡 → 定位被阻塞指令 → 回溯已调度的 backward、
把**权重梯度计算**暂存 → 让关键依赖链尽早执行 → 暂存的计算再插回后续气泡。
原文说这"相当于把 Zero Bubble 的核心思想泛化成对**任意调度类型**都适用的自动优化"。

⇒ 联邦版的同构优化（我此前没有）：流水线里等 peer 的时间就是**气泡**，
而等待期间有大量**非关键路径工作**可做：

```
等待 peer 上报时，可填充：
  · 本地 recompute / optimizer offload（省显存）
  · Probe 评测（evaluator-only 也能贡献，07 降级阶梯末档）
  · 快照写入（L1/L2/L3，SNAP 已要求异步）
  · 下一轮的 kernel 预编译（ENG-V1 编译缓存复用）
```

⇒ 这直接提升 §9.5 的 **Goodput**——把"等"变成"干有用的事"，
比降低单步延迟更贴合联邦场景。
**验收**：`profile()` 的 goodput 损耗分解里，`waiting-for-peers` 应能被
上述填充项部分抵消（ENG-V8）。

### 10.5 放置与调度必须联合搜索（负载失衡的教训）

FlexPipe 的实证：词表 1M 时**最慢 stage 比最快慢 5.63×、显存多耗 4.87×**；
解法是新的**放置策略**（沿词表维度把 Embedding 切到流水线组内多设备），
但"新的放置策略套用预定义调度后，会因为新增的数据依赖（Embedding 的 AllReduce）
产生额外气泡"——**所以放置与调度必须一起搜**。

⇒ 对 09 §5.1 的 sharpen：我原先把分片（放置）与调度当成两步。
异构联邦里这一步差得更狠：手机与 PC 在同一条流水线里，stage 时间差
可能远大于 5.63×。因此 **`plan()` 必须联合搜索 (分片, 调度)**，
而不是"先切分再套固定调度"。这与 §10.2 的参数化是同一件事：
分片方式和调度优先级本就是同一组自由度的不同投影。

### 10.6 「没有一个调度能包打天下」（条件性结论的第四次呼应）

原文：调度的优劣**与模型输入有关**——batch 较小时 Interleaved 1F1B 优于 1F1B，
batch 较大时通信更少的 1F1B 反而更优；硬件资源规模也会改变最优解。

⇒ 这是"**方法有效性是有条件的**"第四次独立出现
（soft-MoE 三版 / ZGCM 条件性结论 / Marin 小规模有效大规模崩溃 / 现在是调度）。
⇒ 对 `plan()` 的结论：**必须 per-(model, input shape, cluster) 自动调优**，
任何内置默认调度只是起点不是答案。这与 07 章 `chooseStrategies` 按集群画像
决策是同一 pattern——**策略与调度都不该有全局最优解**。

### 10.7 渐进披露的第三处独立验证

FlexPipe DSL 的三档，与我 03 章三粒种子逐字对应：

| FlexPipe | 本设计 |
|---|---|
| 写惯例调度**只需设参数** | 组件（组合，覆盖 90%） |
| 深度定制写**函数**（三个"手动挡"） | 叶原语（算子） |
| 注册**新指令**（`register_new_inst` + 依赖 + 绑定操作） | `defineOp` 受信逃生门 |

原文："**用户按需取用：写惯例调度只需设参数，做深度定制才需要写函数。
复杂度是渐进暴露的。**"⇒ 渐进披露不是我的偏好，是**可编程系统的普遍结论**。

### 10.8 生成的调度必须带可机读诊断

原文列手工实现三座大山，第三条是**可调试性**："极易出错（死锁、错序、精度问题），
且缺乏中间调试信息"。

⇒ `plan()` 生成的执行计划应能**静态**检测并报出这些问题，
扩展 03 §5 的诊断码：

| 新 code | 检测内容 |
|---|---|
| `SCHEDULE_DEADLOCK` | 计划中存在循环等待（跨 peer 的激活/KV 依赖成环） |
| `SCHEDULE_STARVATION` | 某节点在所有调度步都无有用功可做（纯等待） |
| `SCHEDULE_UNSCHEDULABLE` | 计划依赖了不可见的远端瞬时状态（违反 §10.3） |

### 10.9 FlexPipe 的诚实边界

1. 它**只做流水线并行**：未来工作才包含重计算、显存卸载、更多通信优化——
   我的 `plan()` 若要覆盖这些，是**我的**工作量，不是借来的。
2. "十行代码"是**表达 1F1B** 的代码量，不是"实现一个调度系统"的工作量。
3. 加速比都是**针对特定基线、特定硬件**（64×A800）：
   vs Megatron-LM 最高 2.28× 发生在 16.1B + 1M 词表的极端失衡场景；
   多模态仅 1.18×–1.29×。**不是普遍 2.28×。**
4. 搜索空间含 (pp, dp, mbs, 放置, 优先级) 但**不含张量并行维度**——
   与本设计"跨 peer 禁张量并行"（09 §5.1）恰好互相印证：
   张量维度不适合放进这种参数化搜索。

## 11. 容错维度：我的联邦设计原生就活在「就地恢复」层

> 来源：知乎问题《大模型分布式训练还有必要通过 checkpoint 进行容错吗？》的高赞回答
> （sans 等）。核心事实：万卡集群 **MTBF 降到分钟级**（LLAMA3 公开数据：16,000 GPU
> 约每 2.78 小时一次硬件故障）；175B 模型完整 checkpoint **>700 GB**，
> 同步写入要数分钟到数十分钟；业界用 **ETTR = 实际计算时间 / 作业占用总时间**
> 度量，优秀万卡集群需 **ETTR > 0.9**。
>
> 回答给出**四层容错阶梯**：协议/硬件自愈 → 通信库透明恢复 → 应用层就地恢复 →
> 全局重启恢复，"始终追求以最低的成本来化解问题"。
>
> **这篇给我最大的启发是一个自我认知：我的联邦设计，原生就活在第三层。**

### 11.1 四层容错阶梯 ↔ 本设计映射（★ 自我认知）

集中式同步训练的默认形态是**第四层**（失败即全局重启），要艰难地往上爬；
而联邦训练的默认形态**本来就是第三层**。

| 层 | 集中式的做法 | 本设计的对应 | 我的默认所在层 |
|---|---|---|---|
| ① 协议/硬件自愈 | HPN 双平面、UB-Mesh 链路重试、光模块备用通道 | `Transport` 层的重连/重试（10 §2） | 第①层 |
| ② 通信库透明恢复 | VCCL/ICCL **主备 RDMA 队列对**，故障时自动切换，**对上层完全透明**（实测维持 ~76.6% 吞吐，NCCL 直接失败） | **主备 peer 路径**（预建备用路由，自动切换） | 第②层 |
| ③ 应用层**就地恢复** | 排除故障成员、健康成员继续前进（难点：world_size 变化的一致性） | **联邦的默认形态**：少一份 Update 而已（软同步屏障，§2.1） | **第③层（原生）** |
| ④ 全局重启恢复 | torchrun + Rendezvous 自动重组 + 从最近 checkpoint 恢复 | `Snapshot` + rejoin sync（§2.3） | 第④层（兜底） |

⇒ **可写进设计的主张**：集中式框架必须用复杂的工程（NCCL Shrink、组级别容错、
状态冗余、动态重构）才能从第④层爬到第③层；**联邦范式天生就在第③层**，
第④层只是兜底。这不是"我们做得更好"，而是**范式起点不同**——
但它是可以说清楚的比较优势，且与 §2.1 的软同步屏障是同一件事的两种表述。

### 11.2 组级别原子性：分片的 peer 集合是原子单位（★ 补 INV-11）

文章的核心难点剖析：TP/PP 组内单点故障会**破坏计算图完整性**
（8-way TP 丢 1 卡，矩阵乘法直接无法完成），所以现实路径是
**组级别容错**——"将一个功能完整的并行组视为一个原子单位，
组内任一成员失败，系统直接将整个组排除，视为数据并行维度上少了一个副本"。

⇒ 对我的 sharpen：**一个 shard 的 peer 集合必须是原子单位**。
若某 shard 由 3 个 peer 分担（层/流水线/专家分片），其中 1 个掉线：
**不能**只把掉线那个的工作"分给别人"（那会改变分片拓扑 ⇒ 违反 INV-11 的
specHash 不变性），而应**整个 shard 重新分配**（换一组 peer 或降级为更少分片）。
这与 09 §5.1"分片与调度联合搜索"合流：成员变化 ⇒ 重新 plan()，而不是局部打补丁。

### 11.3 故障共识：单一权威判定，禁止脑裂（★ 新约束）

文章把"**快速且一致的故障检测**"列为就地恢复第一要求，并明确指出：
"如果出现误判或'**脑裂**'（不同成员对故障列表有不同看法），将导致后续的恢复流程
彻底混乱"，需要"带超时的集体通信或外部的强一致性协调服务（如 etcd）"。

⇒ 本设计对应约束（进 09 §3）：**故障列表必须由单一权威（聚合端/房主）判定并广播**，
各节点**不得自行判断**谁掉了。联邦场景里这天然有解（聚合端本就是权威），
但必须写成显式约束，否则多聚合端或房主迁移时会脑裂。
（这也与 09 §5.2 预留账本、09 §5.3 可调度性同属"集群状态必须单一真相源"。）

### 11.4 快照必须支持 resharding：「按 A 拓扑存、按 B 拓扑读」（★ 我的 Snapshot 缺口）

文章讲高效 checkpoint 时提到 PyTorch `torch.distributed.checkpoint` 支持
**多 rank 并行保存**与**加载期重分片（load-time resharding）**，
"允许'**按 A 拓扑存、按 B 拓扑读**'"。

**这是我的 `Snapshot` 设计缺口**：我说过"rejoin 只需拉 θRef"，
但没说**下次训练的 peer 集合几乎必然不同**——联邦里谁在线是动态的，
所以快照必须能在**不同的分片拓扑下加载**。

⇒ **改动（进 14 §2.3 / 09）**：`Snapshot` 除 `θRef`/`DataCursor` 外，
必须能在加载时 reshard：`θRef` 是**逻辑上完整**的模型状态（内容寻址、可分片存储），
加载时按**新拓扑**重新切分，不要求旧拓扑仍在。
验收增 **SNAP-V5**：同一 `Snapshot` 在两套不同分片拓扑下加载，
数值对拍一致（容差内）。

### 11.5 数据覆盖必须随节点集合重算（★ 补 DataCursor）

文章列 world_size 变化的三连锁反应，第一条就是数据并行一致性：
"框架必须动态调整用于梯度平均的分母。同时，它还需要通知数据加载器
（如 DistributedSampler）成员数量已变，以确保整个数据集在新的成员规模下，
仍然能够被**完整、无重复地遍历**。"

⇒ 这正是我 `DataCursor` 缺的一半：我只说了"记录谁训到哪"，
没说**节点集合变化后如何保证数据集仍被完整且无重复地覆盖**。

⇒ **改动（进 14 §6.1 / 03 §2.2）**：`DataCursor` 增**覆盖簿**（coverage ledger）：

```
coverage := { [shardId]: { trained: Bitmap, claimedBy: nodeId } }
规则：节点进出 ⇒ 未训分片重新分配；已训分片不重训（除非显式要求）
      ⇒ 任意时刻 ∪trained ∪ claimed == 全集，且交集为空（无重复、无遗漏）
```

这比"跳过已迭代轮数"（Steel-LLM 的旧做法）强得多，且是 INV-13 的必然推论。

### 11.6 主备 peer 路径：VCCL 的 QP 对在联邦里的对应（★ 进 10 章）

VCCL/ICCL 的核心：为每对需要通信的 Rank **预建两条独立 QP**（主用 + 冷备用），
监控主用健康，出错即自动切换，**对上层层训完全透明**；实测网卡端口故障下
集合通信仍维持 **~76.6% 吞吐**，而标准 NCCL 直接失败。

⇒ 本设计对应（进 10 §2）：**主备 peer 路径**——每对常通信 peer 预建第二条
独立通道（不同 DataChannel / 经不同中继 / 或经第三个 peer 中转），
主路径健康监测 + 自动切换，对上层（联邦编排）透明。

浏览器场景的现实约束（诚实）：WebRTC 无法像 RDMA 那样零成本冷备，
备用路径要么占带宽要么经中继增加延迟。所以定位是**关键路径才用**
（如流水线分片的相邻 stage 之间），不是全网格建主备。

### 11.7 SDC：静默数据损坏 = 我的共识探针（★ 给已有机制命名）

文章指出除崩溃外还有两类隐性问题：**慢节点**与**静默数据损坏（SDC）**。
SDC 不报错、不崩溃，只是**算错了**——这是比崩溃更危险的故障。

⇒ 本设计里对应的正是 09 §6 的**共识探针**（每 N 轮抽 1 节点用同一批公开探针
数据复算，比对 θ 收敛方向）。此前我只把它当"防作弊"，
现在应明确它**同时是 SDC 检测器**：
- 防作弊面对的是"恶意伪造 Update"；
- SDC 面对的是"诚实但算错"（驱动 bug、显存位翻转、浏览器后台降频导致数值漂移）。

⇒ 而且 ZGCM 的"loss 还在降、模型却退步"正是 SDC 类症状的**可观测表现**——
再次说明 11 §2.4 的原子能力 `Probe` 是发现它的手段（总分看不出，原子能力看得出）。
**一个机制同时服务：防作弊 + SDC 检测 + 能力归因。**

### 11.8 冗余计算作为一等容错：浏览器 peer 就是 Spot 实例（★ 论点升级）

回答里 iyacontrol 提到 Bamboo（NSDI23）：**用冗余计算提升容错性，
从而可以使用低成本的 Spot 实例**。

⇒ 这是一个**直接升级我论点**的类比：**浏览器 peer 本质上就是 Spot 实例**——
随时被系统回收（切后台、省电、杀浏览器）、无法信任其持续时间。
中心式云要用"冗余计算 + 精妙的 checkpoint"才能用 Spot；
联邦范式**天然就跑在 Spot 上**，所以冗余应该是**一等容错手段**而不是补丁。

⇒ 本设计对应（已部分存在，现升为一等）：**冗余评估/冗余计算**——
同一份工作可派给多个 peer，取多数/容差一致者（这正是共识探针的泛化）；
evaluator-only 角色天然是冗余评估的载体（最弱设备也有用途）。
这与 07 章 ES 策略的"群体"也是同构的（pop 个扰动天然是冗余）。

### 11.9 ETTR ≡ Goodput，以及 >0.9 的校准基准

文章的 **ETTR = 实际计算时间 / 作业占用总时间**，与我从 AXLearn 吸收的
**Goodput**（06 §7.1）是**同一个指标**的两种命名。

⇒ 统一术语：本设计用 **Goodput**，注明"业界亦称 ETTR"，
并引用其校准基准：**优秀万卡集群 ETTR > 0.9**。
这给我的验收线一个外部参照——联邦场景的 Goodput 会更低
（等待 peer、重连、降级重分配都是额外损耗），但**损耗分解必须可归因**
（`waiting-for-peers / reconnect / reshard / checkpoint-io`），
这正是 06 §7.1 已要求的。

### 11.10 快照的分层存储：本地快 → 后台异步落盘

Alluxio 的回答给出工程配方：把本地内存 + NVMe 池化成分布式缓存，
checkpoint "秒级"写入缓存，**后台异步多线程**刷入 S3/OSS/HDFS，
对训练框架而言保存动作"瞬间完成"；实测单次保存耗时降低 **93%–99%**。

⇒ 本设计对应（补 14 §2.3 的三档快照）：浏览器端的存储层级应是
**内存/OPFS（快）→ IndexedDB（中）→ 可选公地 blob（慢，后台）**，
写入必须止步于第一层即返回（异步），后台再逐层下沉。
与 AXLearn 的"快照写入必须异步、不阻塞训练"合流，并补上**分层**这一维。

## 12. 对 M5 护城河的压力测试：非反传方法的真实成熟度

> 来源：用户提供的 2026 年研究综述（ES/ZO/FF/局部损失/FA-DFA/目标传播/Hebbian/预测编码
> 八大路线的现状）。核心结论：
> **"目前没有任何方法能在'从头预训练超大规模 LLM'这一核心场景上挑战 BP 的效率与稳定性。"**
> ICML 2026 的对比研究给出量化代价：同等内存下，**带激活检查点的 BP 准确率高 31.1%、
> 收敛快 34.8%**；ZO 随模型增大**更不稳定**。
>
> **这是对整个 design/ 最直接的一次反驳，因为它打的正是我的 M5 护城河。**
> 诚实的处理方式不是辩解，而是**把 M5 的 claim 收窄到它真正成立的范围**。

### 12.1 八大路线的真实成熟度（逐条对照我的策略表）

| 路线 | 已被证实的规模/场景 | 关键量化结论 | 对应我的策略 | 我的立场 |
|---|---|---|---|---|
| **进化策略 ES** | **十亿参数级已成功**；全参数、无需降维的微调；长程奖励容忍度与训练稳定性**优于 RL** | — | `es` | **场景级：成立**。最适合"无梯度 + 大规模并行" |
| **零阶 ZO** | **低内存微调**为主 | 同等内存下 BP+检查点 **准确率 +31.1%、收敛快 34.8%**；**模型越大越不稳定** | `spsa` | **场景级但有规模上限**：适合小模型/微调/弱设备小分片，**不适合大模型预训练分片** |
| **前向-前向 FF** | **优势在分布式并行，而非替代 BP** | **分布式 FF 3.75× 加速且保持精度** | `forward-forward` | **场景级：成立，且正是我的用例**（低通信跨设备） |
| **局部损失/分块** | 后训练中降低内存的探索 | **贪心分块局部学习"可能丢弃下游所需信息"** | `local` | **研究级 + 已知缺陷**：要用就必须处理信息丢失 |
| **反馈对齐 FA/DFA** | 理论分析触及大规模微调，**大规模实证不足** | — | （未单列，归 `local`） | **研究级** |
| **目标传播 TP** | **在语言模型上表现不佳** | 普遍不如 BP | （未单列） | **不采用**（除非只为可表达性） |
| **合成梯度** | 可解耦层间训练，**无证据表明能扩展到有竞争力的模型** | — | （未单列） | **不采用** |
| **Hebbian** | **ImageNet 级（卷积网络）**，最高 50× 训练加速；**与 Transformer 差异巨大** | — | `local` 的一种 rule | **研究级 + 架构不匹配** |
| **预测编码** | Transformer LM 上**性能可与 BP 相当，但规模仍中小型** | — | `equilibrium-prop` 的近亲 | **研究级：最有希望的非 BP 路线** |

### 12.2 这不推翻 M5，但要求把 claim 收窄（★ 重要的自我修正）

我原来的 M5 表述暗示"非反传是一等公民"，容易被读成"非反传同样好"。
综述的结论要求我改成**三个更窄但更站得住的 claim**：

| | 原 claim（过宽） | 收窄后（可辩护） |
|---|---|---|
| **M5-a** | 非反传方法是一等公民 | **参与权平等，效果不平等**：BP 仍是生产默认；非反传的价值是**让本来无法参与的设备/系统能够参与** |
| **M5-b** | 训练算法无关是护城河 | 护城河是**「异构参与」与「不可微系统」**，不是「效果更优」——前者不依赖任何研究赌注 |
| **M5-c** | 策略层让非反传变一等公民 | 策略层让它们**可表达、可协作、可被选择**；**是否采用由 `plan()` 按场景决定**，不由宣称决定 |

⇒ **关键澄清**：一个手机跑不动反传，它用 ES/SPSA 贡献更新，**比它完全不参与好**——
这个论证**不需要** ES 打得过 BP。这正是 M5 真正的力量来源：
它把"能不能参与"从"能力竞赛"变成"结构问题"。

### 12.3 但有一条必须记下的风险：ZO 随规模更不稳定

综述明确"**ZO 随模型增大还更不稳定**"。这直接冲击我 07 章
"手机跑 SPSA"的故事——如果手机分到的是**大模型的一个 shard**，
ZO 的不稳定性会被放大。

⇒ **约束（进 07/09）**：`ZO/SPSA` 策略仅允许用于
**小模型整体**或**小分片**（层数少、参数量低于阈值）；
大模型分片上的弱设备应降级为 **evaluator-only**（贡献前向评估/Probe），
而不是硬上零阶。这把"降级阶梯"的最后一格从"零阶"改成
"零阶（限小分片）→ 仅评估"。

### 12.4 FF 的分布式优势，正是我 ch09 的实证支撑

综述说 FF 的"**优势在分布式并行，而非替代 BP**"，且
**分布式 FF 3.75× 加速且保持精度**。

⇒ 这恰好是我 09 §5 的选择：低带宽/高延迟场景偏好**低通信策略**
（局部规则/forward-forward）。此前那是设计推断，现在有实证数字：
**FF 的层独立性 ⇒ 天然流水线并行 ⇒ 跨设备 3.75×**。
这把"低通信策略"从"我们只能用这个"变成"**这条路本来就有独立的价值**"。

### 12.5 收窄后 M5 的诚实边界（写进 07 章）

1. **生产默认永远是 BP**（有梯度且算得动时）——07 §3.2 已说，现升级为硬规则。
2. **ES/ZO/FF 是场景级**：各自有已被证实的 niche（无梯度并行 / 低内存 / 分布式），
   但**都不宣称在同等条件下优于 BP**。
3. **EqProp/预测编码/Hebbian/合成梯度是研究级**：只为**可表达性**而留在 IR 里，
   `plan()` 默认不选，除非显式开启实验档。
4. **目标传播在 LM 上表现不佳 ⇒ 默认不选**（收进 `local` 的可选 rule，不提位）。

## 14. 八篇合起来的一句话总结

> 第一篇（规模化）证明**赌桌的残酷**：每一环都不能有短板，于是只剩巨头能上桌。
> 第二篇（Steel-LLM）证明**个人已经能训模型，却不能保证算力持续**——成功靠运气和人情。
> 第三篇（ZGCM-1）证明**7 个非 AI 为主的人 + 几百个 Agent 就能从零训出 7B**，
> 且他们和第二篇作者**独立地说出同一句抱怨**：技术报告里看不到"究竟发生了什么"。
> 第四篇（Marin）证明**前沿团队也独立地工程化了"内容寻址 + 过程开放"**，
> 而它自己说这种开放"极其罕见"，且"正是这些失败和弯路构成了最有价值的过程知识"。
> 第五篇（AXLearn）证明**"代码如何持续演化"可以被做成可分析的系统指标**，
> 而 Apple 用 O(1) 接口修改量论证的事，我的设计**结构性地**成立：IR 是纯数据。
> 第六篇（FlexPipe）证明**"换一个坐标系"是可迁移的元方法**——
> 它和我做的是同一个动作，只是对象不同：它换掉"手绘时序图"，我换掉"继承式代码"。
> 第七篇（容错专题）证明**集中式框架要艰难地从"全局重启"爬到"就地恢复"**，
> 而**联邦范式天生就住在"就地恢复"那一层**——失败只是少一份 Update。
> 第八篇（非反传研究综述）给了我最狠的一击，也给了最贵的一条教训：
> **没有任何非反传方法撼动 BP 在大规模预训练的地位**——
> 所以我必须把 M5 从"非反传更好"收窄成"**参与权平等，效果不平等**"。
>
> 八篇指向同一个结论：**缺的不是算力、不是方法、不是人才，
> 而是"过程可追溯、资产可复用、参与有结构、演化不失控、决策可搜索、故障可容忍"的公共层。**
> 而"模型即数据"是这一切唯一可能的地基——
> 软同步屏障换故障容忍（原生就在"就地恢复"层）、content-addressed 快照（含数据游标
> 与覆盖簿、可 resharding）换续训经济学、溯源链换可定位性、可寻址数据换可审计性、
> counter-based 置换换数据秩序、Invocation Context 换封装不被状态渗透、
> LoC-Complexity 换演化不失控、参数化决策空间换"搜索与编程同时坍缩"、
> 气泡填充换 Goodput、原子能力探针同时换"改动究竟带来了什么"的答案与 SDC 检测、
> AI 原生编写 + Skill 沉淀换掉那批稀缺的复合型人才。
>
> **我们在 MFU 上认输，也在"非反传更优"上认输；
> 我们在可参与性、可追溯性、可演化性、可搜索性与容错性上下注。**
> 而第三到第七篇告诉我们：这个赌注的五分之一——7 个人 + 几百个 Agent、
> 把失败全部公开的前沿平台、把演化成本做成指标的模块化系统、
> 把调度空间换成几个自由度的可编程流水线、以及用四层阶梯艰难爬到"就地恢复"的集中式集群——
> **都已经被人用别的方式各赢过一次了。我们做的，是把这五半合成一个谁都能参与的结构。**
> 第八篇则提醒我们：**连这个结构的价值，也要靠"不依赖研究赌注"的方式去论证。**

## 15. 第二轮学术评审：信任/激励/法律层的新证据（2026-10-07）

八篇之外，本轮按"设计缺口的对手文献"补了九条检索线，结论全部转成
`docs/设计评审记录-2026-10-07-第二轮.md` 里的修订（R-39~43 / ADR-018~023 /
FED-V15~17 / COMMONS-V11~15 / INV-20）。只记与设计判断直接冲突的部分：

| 线 | 打穿的原判断 | 新判断 |
|---|---|---|
| 鲁棒聚合（FLTrust→FoggyTrust） | "clip+L2 就是信任规则" | 加权平均对尺度攻击零防御；探针窗兼任 root dataset 后可零成本获得信任锚，但 **root≠客户分布时会误伤诚实 non-IID**（FoggyTrust 实证）⇒ TS 只降权不放大 |
| 隐私攻击（DAGER/Grab/ReCIT/TIGER） | "数据不出本地 ⇒ 隐私结构性成立" | 梯度反演在 LM 上已实用化且**攻破 DP-FL**（TIGER 2026）⇒ 隐私是分层开关不是结构性结论；SecAgg 与鲁棒聚合互斥（Meta-FL） |
| 贡献评估（Shapley 系 + 脆弱性论文） | "账本记样本份额就是贡献计量" | Shapley 是唯一四公理分摊但 O(2^N)；一阶 LOO（probeDelta）全网一次反向即可复算；**贡献分随聚合架构变化且可操纵** ⇒ 必须记 `aggregationRuleId`，禁单轮定生死 |
| 数据归因（TracIn/TRAK/TrackStar） | "溯源链定位到节点/轮级就够了" | 8B/160B-token 规模的一阶归因已可行 ⇒ "哪片数据让模型退步"应做到**分片/样本级**；数据面（Snapshot+Update 内容寻址）我们本来就有，缺的是把它声明为归因输入 |
