# 03 · Spec IR 与类型系统

> 前置：02 架构总纲（R1/R2/INV-8/INV-9）。
> 后置：04 语言层、05 算子层、06 编译层、09 联邦协议（都以本文件的 IR 为数据契约）。

---

## 1. 定位

Spec IR 是**本项目的"汇编语言"**：一切的上层（JSX、AI 生成、联邦分发、编译）都以它为
唯一中间表示。它必须同时满足四类读者：

| 读者 | 要求 |
|---|---|
| **人** | 树形、一眼可读、可 diff |
| **编译/类型系统** | 可静态推断 shape/dtype/能力/效应 |
| **AI** | 自描述（无需外部文档即可理解）、可校验、可增量编辑 |
| **网络** | 可规范序列化 → 内容寻址 → 安全分发 |

## 2. 完整数据模型

```
Model := {
  schemaVersion: "1.0"                  // IR 版本（§6）
  graph:   ModelNode                    // 纯计算根节点
  trainer: TrainerSpec                  // 学习策略（与 graph 正交，见 07）
  meta:    ModelMeta
}

ModelMeta := {
  author?:   string
  created?:  ISO8601
  parentHash?: string                   // 溯源：由谁 fork/派生
  datasetHash?: string                  // 训练用数据集指纹（全网一致的前提）
  license?:  string                     // SPDX 表达式（公地用）
  tags?:     string[]
}

TrainerSpec := {
  strategy:   StrategyId                // backprop | forward-mode | spsa | es |
                                       // reinforce | local | forward-forward |
                                       // equilibrium-prop | variational | custom
  params:     Props                     // 超参（pop/sigma/eps/lr/horizon/…）
  requires?:  OpCapability[]            // 由 strategy 推导；IR 可显式声明以提前校验
  schedule: { localSteps: int, syncEvery: int, precision: "fp32" }
}

ModelNode := {
  id:        NodeId                     // 稳定标识；用于增量编辑与 diff
  op:        OpRef                      // 指向注册表中的 op（含契约）
  props:     Props                      // 结构化超参（可为表达式：见 §3.4）
  children?: [NodeId]                   // 有序子节点（组合原语使用）
  wiring?:   [Edge]                     // 数据/状态/信号边（非树结构用）
  slot?:     { [port: string]: NodeId } // 命名输入插槽（CrossAttn cond 等）
  annot?:    Annot
  meta?:     { note?: string, span?: SourceSpan }   // 回指 JSX/DSL 位置
}

Edge := {
  from: NodeId, fromPort: string,
  to:   NodeId, toPort:   string,
  kind: "tensor" | "state" | "signal"   // state=KV/ScanState；signal=门控
}

Annot := {
  phase?:    Phase | Phase[]            // train/prefill/decode/sample/rollout/nudge/free
  device?:   "auto" | DeviceId          // auto 表示交 plan() 决定
  shard?:    ShardSpec                  // 分片声明（09）
  precision?: "fp32" | "fp16" | "int4" | "bf16"
  recompute?: boolean                   // 反向时重算以省激活显存
  effects?:  "pure" | "effectful"       // 默认 pure；Tool/Env 必须 effectful
  cost?:     { flops?: string, memPeak?: string }   // 声明式成本注解
}

ShardSpec := { plan: "layer" | "tensor" | "expert" | "auto", peers?: int }
```

### 2.1 设计约束（为什么长这样）

| 决策 | 理由 |
|---|---|
| 每个节点 `op` 指向**注册表**而非内联实现 | 能力位/契约/版本都在注册表一处维护；`specHash` 不含实现细节 |
| `props` 是结构化数据，不含函数 | 函数不可序列化、不可寻址。行为差异用**不同的 op** 表达 |
| `children` 与 `wiring` 并存 | 树（90% 场景）简单可读；图/求解/循环需要显式边 |
| `annot` 单列而非塞 props | **执行策略与语义解耦**：同一模型可换 `phase/device/shard` 而不改语义 |
| `trainer` 在 `Model` 顶层而非节点上 | 训练策略是**模型级**关注点，不是某层的 |
| `id` 稳定且可手写 | 增量编辑与"补一个节点"是 AI 的常见操作路径 |

### 2.2 Invocation Context：状态、RNG 与参数共享的唯一持有者（★ 来自 AXLearn）

IR 是**数据**，因此节点不可能"持有"运行时状态——但这不等于没有状态。
训练需要跨调用传递：KV/ScanState、PRNG key、摘要与输出集合、共享参数（`tie`）。

**反面模式**（AXLearn 踩过并写进论文的）：如果让每个节点手工接收/返回这些侧输入输出，
"模块就会重新感知整棵状态树，严格封装随之失效"。

⇒ 由**上下文栈**统一持有，节点只被调用、不感知全局：

```
Ctx := {
  stack:   [Frame],                          // 父→子压栈，返回出栈
  prng:    (path) → Key,                     // 按栈路径派生；父子各得独立 key 段
  outputs: { [collection]: TensorRefs },     // 摘要/输出按帧隔离
  params:  ParamTable                        // 共享参数（tie）在此登记
}
Frame := { nodeId, locals: StateMap, parent: Frame? }

**`DataCursor` 的覆盖簿**（coverage ledger，14 §11.5）：联邦里节点集合随时变化，
必须保证数据集仍被**完整且无重复地遍历**（集中式靠通知 DistributedSampler
重算采样；我们靠覆盖簿静态维护）：

```
coverage := { [shardId]: { trained: Bitmap, claimedBy: nodeId } }
不变量：任意时刻  ∪trained ∪ claimed == 全集，且彼此交集为空
        （无遗漏、无重复；节点进出 ⇒ 只重分配未训且未认领的分片）
```

⇒ 这比"跳过已迭代轮数"强得多：后者在数据池或节点集合一变就失效
（Steel-LLM 的旧做法），覆盖簿则是**集合变化下的正确性保证**，
与 INV-13 是一体两面。
```

**铁律（INV-15）**：`Ctx` 持有节点引用，**节点不得反向持有 `Ctx`**。
由此三个老问题同时有解：

| 老问题 | 旧说法 | 现在的机制 |
|---|---|---|
| `Bus` 跨层耦合 | "只读快照 + build 期报环"（没说什么持有状态） | 栈持有 ⇒ 节点天然只读、拓扑天然无环 |
| RNG 拆分 | "每个 op 声明 counterScope"（拆分机制缺失） | 调用即按栈路径派生 key（INV-10/14 落地） |
| `tie` 参数共享 | "backward 末尾按参数 ID 归并"（补丁） | `params` 表登记，grad 按 ID 归并是**机制**而非补丁 |

附带收益（同样来自 AXLearn）：优化器等**不在模型树内**的调用也能经 `Ctx` 访问状态；
模块因此是**层级无关**的——同一个 `Block` 在第 2 层还是第 20 层行为一致
（这对 AI 生成与公地复用都是必要的）。

## 3. 类型系统

### 3.1 基础类型

```
Tensor := < shape: DimList, dtype: DType, layout: Layout >
DimList := ( DimConst | DimSym )*        // DimSym 支持 B/T/… 动态维
DType  := f32 | f16 | bf16 | i32 | i64 | u32
Layout := dense | blocked | sparse(Scope)

State  := < kind: "kv" | "scan" | "buffer" | "memory", shape, dtype >   // 显式生命周期
Dist   := { family, params: TensorRefs }         // 提供 sample()/logprob()
Pure   := { }                                     // 无副作用
Effectful := { effects: [string] }                // Tool/Env，必须显式列出
```

**动态 shape**：符号维（`B`、`T`）在 `infer()` 里做**符号求解**；无法静态确定的
（例如 `T_effective = T - kernel + 1`）由 `infer()` 尝试约束传播，失败则报
`DYNAMIC_SHAPE_UNRESOLVED` 并退化为运行时 shape 检查（不阻塞）。

### 3.2 能力位（类型系统的第四维）

类型只描述**数据形状**，不描述**可训练性**。所以每个 op 额外携带能力位：

| 能力位 | 含义 | 被谁查询 |
|---|---|---|
| `forward` | 能算 `f(x;θ)` | 一切（必需） |
| `vjp` | 反向模式 VJP | Backprop |
| `jvp` | 前向模式 JVP | Forward-mode |
| `logprob` | 输出对数概率 | REINFORCE / VI |
| `localGrad` | 层内局部梯度 | Hebbian / target-prop / DFA / FF |
| `perturbable` | 可对 θ 扰动重估目标 | ES / SPSA |
| `invertible` | 可由输出重建输入 | EqProp / flow |
| `nondiff` | 明确**无任何梯度** | 黑盒 Tool / 离散 / 符号 |

类型规则举例：
- `Strategy=backprop` ⇒ 损失路径上所有节点必须有 `vjp` 或 `localGrad`（局部规则链）。
- `Strategy=es` ⇒ 全图只需 `forward` + `perturbable`（因此 `nondiff` 节点**允许**出现）。
- `effects=effectful` 节点不得出现在同质档的纯计算子图里（INV-8）。

## 3.3 表达式 props（受控可编程性）

props 允许**受限表达式**以支持循环/条件/参数绑定，但表达式**必须可静态求值**：

```
props.value := Literal | Ref("meta.B") | BinOp | Range | Cond
// Cond(x, a, b) 条件在 build 期求值 → 生成不同子图
// 禁止：lambda、闭包、外部调用（那属于 defineOp 的贡献范畴）
```

这样"模型里写 for/if"保留（v2 的正确直觉），但**不会**出现不可序列化的函数。

### 3.4 源位置与 JSX 回指

`meta.span` 让诊断可以指回 JSX 源码行列（IDE 可用）；纯 JSON IR 无 span 时
降级为 `node.id` 指认。

## 4. 规范序列化与 specHash

联邦按"同哈希=同结构"聚合，所以序列化必须是**规范的**（canonical）：

1. **Key 排序**：所有 map 按 key 字典序输出。
2. **无空白**：紧凑 JSON（或等价的 canonical binary）。
3. **去不确定字段**：`meta.created`、无 `id` 的手写顺序、注释，
   全部排除在哈希之外（保留在可读层）。
4. **归一化**：默认值不写入（`annot.effects="pure"` 不序列化）；
   等价表达式折叠到同一形式。
5. **后端无关**：`device="auto"` 与分片计划**不进** `specHash`
   ——否则换设备就断了聚合（INV-11）。

```
specHash := SHA-256( canonical( Model \ {meta.created, meta.id_suffix, annot.device, annot.shard} )
                     + TrainerSpec.strategy + schemaVersion )
```

**实现提示**：`TrainerSpec.strategy` 进哈希、`strategy.params`（如 pop 大小）不进，
保证"同结构不同超参仍可对齐"。

### 4.1 为什么必须排除不确定字段（Marin 的失效模式）

第 3/5 条不是洁癖，是**被前沿工程验证过的硬规则**。Marin 的 Artifact 系统
（内容哈希标识每个 pipeline 步骤的输入输出）写着同一条约束（14 §8.1）：

> 步骤的 `hash_attrs` 必须包含它读取的每一个参数，且**不能包含任何地区特定的路径**。
> 违反这条规则，同样的数据在不同地区会得到不同的输出路径，缓存就废了。

即：**把环境特定信息混进寻址 ⇒ 同一份东西在不同机器上得到不同身份 ⇒
内容寻址、去重、跨设备复用全部失效。** 我们的对应物是 `device`/`shard`/`precision`/
`createdTs`（第 5 条）。

另一条来自 Marin 的规则：**依赖版本必须进哈希，且必须可锁定**（它用 uv.lock
固定全部依赖，避免"库升级 ⇒ 缓存失效"）。对应到我们的 op 契约与
`DataPipelineSpec`：两者都要带 `depVersions`（算子实现版本 + 依赖版本），
否则"同一个 op"在不同部署里行为不同，`specHash` 的同一性就是假的。

⇒ `specHash` 实际输入扩展为：

```
specHash := SHA-256( canonical( Model \ {meta.created, meta.id_suffix,
                                          annot.device, annot.shard} )
                     + TrainerSpec.strategy + schemaVersion
                     + Σ(opRef → op.version, op.depVersions) )
```

## 5. infer()：静态分析与诊断

### 5.1 输出结构

```
InferResult := { graph: TypedGraph, diags: [Diag], caps: CapsSummary }

Diag := {
  level: "error" | "warn" | "info",
  code:  DiagCode,
  node?:  NodeId, port?: string,
  message: string,                  // 面向 agent 的自然语言（中英双份）
  fix?:   AutoFix,                  // 机器可读的修复建议
  at?:    SourceSpan
}

AutoFix := { kind: "insert-op" | "change-prop" | "re-wire" | "switch-strategy" | "add-annot",
             to: string, at: NodeId | Edge }
```

### 5.2 诊断码全表

| code | level | 触发场景 | 典型 fix |
|---|---|---|---|
| `SHAPE_MISMATCH` | error | 边两端 shape 不兼容 | insert-op `Reshape/Transpose` |
| `DTYPE_MISMATCH` | error | dtype 不兼容 | insert `Cast` |
| `MISSING_PARAM` | error | props 缺必填 | change-prop |
| `UNDEFINED_SLOT` | error | 引用不存在的插槽 | re-wire |
| `BUS_CYCLE` | error | Bus provide/inject 成环或未配对 | re-wire / add Provide |
| `PHASE_LEAK` | error | 训练期相位用了仅推理组件（如 KV cache 未声明 phase） | add-annot phase |
| `EFFECT_IN_PURE` | error | effectful 节点出现在纯子图 | switch-strategy / 移出 |
| `DYNAMIC_SHAPE_UNRESOLVED` | warn | 符号维无法静态确定 | 无（运行时检查） |
| `CAPABILITY_MISSING` | error | 策略要求的 caps 图里有节点不具备 | switch-strategy |
| `STRATEGY_INCOMPAT` | error | trainer.strategy 与 trainer.requires 矛盾 | switch-strategy |
| `UNREPRODUCIBLE_RNG` | error | 策略需要 RNG 但无可用 RNG 配置 | add-annot rng spec |
| `BUDGET_EXCEEDED` | error/warn | 估算 FLOPs/显存超 plan() 给定预算 | change-prop / 降精度 |
| `SHARD_INFEASIBLE` | error | 分片计划无法满足（形状不可切/设备过小） | 改 shard plan |
| `PARAM_REUSE_CONFLICT` | error | `tie` 参数形状不一致 | change-prop |
| `TRAP_PATH` | warn | Bus 跨层跳数过大（可能乱耦合） | info |
| `ORPHAN_NODE` | warn | 节点无下游路径 | 无 |
| `SCHEDULE_DEADLOCK` | error | 计划中存在循环等待（跨 peer 的激活/KV 依赖成环） | re-wire / 改分片 |
| `SCHEDULE_STARVATION` | warn | 某节点在所有调度步都无有用功可做（纯等待） | 改分片/角色分配 |
| `SCHEDULE_UNSCHEDULABLE` | error | 计划依赖不可见的远端瞬时状态（违反 09 §5.3 可调度性） | 改为只依赖已确认信息 |
| `STABILITY_HINT` | warn | 层数/宽度超阈值而未启用 `QKNorm`/`ZLoss`（05 §5.3：深层网络 logits 爆炸的静态提示） | insert-op `QKNorm` |
| `EVAL_UNDERPOWERED` | warn | 探针池 item 数不足以支撑所声明的原子能力差（INV-21；最小可检出效应 MDE 见推导 13） | 扩探针池 / 缩小声明 |
| `BACKDOOR_SUSPECT` | error | 触发行为探针（11 §2.4 `backdoor` 原子类）在正常输入上检出触发器响应 | quarantine 该节点（09 §6） |

**验收线（P0）**：构造 20+ 个错误模型，`infer()` 必须全部报出**正确的 code + 可机读 fix**，
零崩溃、零漏报、零误报（warn 允许）。

## 6. 版本化与向后兼容

```
schemaVersion := "major.minor"
1.x 内：仅新增可选字段、新增 Diag code、新增 op —— 全向后兼容
2.0：允许不兼容变更，但必须提供 migrator: IR(1.x) -> IR(2.0)
```

- `specHash` 含 `schemaVersion`，不同 major 不混聚（INV-9）。
- 公地里的历史模型永不失效：migrator 是纯函数，可离线重算哈希。
- **开放问题 ①（见 13）**：minor 版本差异是否允许混聚？默认立场：**允许**
  （结构相同即形状一致；migrator 可在宿主侧静默完成）。

## 7. 三种投影（同一 IR 的三个视图）

| 投影 | 用途 | 规范性 |
|---|---|---|
| **JSON / binary** | 传输、寻址、AI 生成 | **权威** |
| **JSX** | 人类书写、git diff 友好、类型推断加持 | 糖（可 round-trip 回权威 IR） |
| **图形化编辑器** | 可视化编辑（远期） | 糖 |

JSX→IR 与 IR→JSX 必须**双向保语义**（round-trip 测试：JSX→IR→JSX ≡ JSX）。

## 8. 验收线总结

| 编号 | 标准 |
|---|---|
| IR-V1 | canonical 序列化在 1000 个随机合法 IR 上稳定（同 IR 必同哈希） |
| IR-V2 | `infer()` 诊断码表全量通过（20+ 构造用例） |
| IR-V3 | JSX ↔ IR round-trip 保义 |
| IR-V4 | `specHash` 对 `device/shard/precision` 变更**不敏感**（INV-11） |
| IR-V5 | 迁移器：所有历史 IR 可升级到新 schema |
