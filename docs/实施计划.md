# 浏览器自研 LLM 引擎实施计划（推理 + 训练闭环）

## Context（为什么做、要达成什么）

目标：在**浏览器内**从零自研一套 LLM 引擎，不依赖 WebLLM / transformers.js 等现成框架，完成：

1. **训练**：从零预训练一个 tiny-GPT（nanoGPT 级），自研前向 + 反向 + AdamW，字符级语料。
2. **推理**：既能跑自训的 tiny-GPT，也能加载现成小模型（Qwen2.5-0.5B int4，safetensors + BPE + GQA + SwiGLU + RoPE）。

技术栈：**TypeScript + Vite**，WGSL 着色器用 `?raw` 导入。数据不出本地。

### 已实测的环境基线（硬约束，非猜测）

| 项目 | 实测值 |
|---|---|
| 适配器 | AMD GCN-5（Vega 核显/APU，共享系统内存） |

## 核心架构决策

### 1. 内存管理：Arena + 显式 offset（应对 maxBindGroups=4）

一个 kernel 最多 4 个 bind group，因此**不按张量绑定**，改为：

- `group0` = **权重 arena**（单个大 storage buffer，按名字存所有 W，用 runtime-sized array + offset 索引）
- `group1` = **激活 arena**（前向中间张量）
- `group2` = **激活/KV 备用 arena**
- `group3` = **uniform**（存放各张量的 offset、shape、超参）

各张量 offset 放 uniform，由 CPU 侧分配时写入。避免撞 `maxStorageBuffersPerShaderStage`。

### 2. 越过 2 GiB：多 buffer 分片 + grid 切分

- 单 buffer ≤ 2 GiB，超限部分拆成多块 buffer，dispatch 时在 y/z 维切 grid 绕过 `65535/dim`。
- Qwen2.5-0.5B int4 ≈ 250 MB，**单 buffer 无压力**；KV cache（ctx2048）≈ 25 MB，单 buffer 足够。
- 训练 tiny-GPT：推荐 config 全量激活约 **230 MB**，远低于上限。

### 3. 精度策略：训练 fp32，推理 f16

- **训练全程 fp32**（tiny 模型无需省内存，f16 反向易不稳定）。
- **推理**用 f16 输入 + fp32 累加（GEMM），权重可按需 int4。
- f16 路径在 M3 引入，且必须与 fp32 路径做 logits 回归对拍后才启用。

### 4. GEMM 分块（32 KB 共享内存约束下）

- tile：**BM=64, BN=64, BK=32**，workgroup = 256 线程（16×16），每线程 4×4 micro-tile。
- A/B tile 各 `64×32×2B = 4 KB`，合计 8 KB，可开 double buffer（16 KB < 32 KB）。
- fp16 global/shared 存储，**fma 在 fp32 寄存器累加**。
- subgroups 用于 norm/softmax 的 `subgroupAdd` 归约与协作加载；**不使用 subgroupMatrix**（Vega wave64 + WGSL 无此路径）。

### 5. 反向传播关键约束

- **无 fp32 atomicAdd**（WGSL atomic 仅整型）→ 权重梯度**禁止原子累加**，每个输出元素绑定唯一线程，用 `gemm_wgrad` 规约实现。
- 激活**全保存（all-save）**，不做梯度检查点（显存充裕）；重算仅作为大模型时的可选开关。

### 算子清单（WGSL kernel）

**前向**：`embed_gather` → `rmsnorm/layernorm` → `gemm`（可选 bias）→ `rope` → `attn_scores`（causal mask）→ `softmax` → `attn_apply` → `gelu/swiglu` → `residual_add` → `lm_head`（tied gemm）→ `cross_entropy`

**反向**：`ce_backward` → `softmax_bwd` → `layernorm_bwd` → `gelu/swiglu_bwd` → `rope_bwd` → `gemm_dgrad` / `gemm_wgrad` → `embed_scatter_add` → `adamw_step`

> 依赖关系：`dY` 通过 `gemm_dgrad`（对输入 X 求导）与 `gemm_wgrad`（对权重 W 求导）成对传播；norm/attn 反向按前向逆序。

## 分阶段里程碑（每阶段都有可验证产物）

### M0 基建 —— 最小可运行
- Vite + TS 脚手架；`device.ts` 做 adapter/device 初始化与 limits 协商。
- arena / uniform / pipeline 缓存骨架。
- `reference/cpu-ref.ts` 起步。
- **验证**：一个 `vec_add` compute kernel，GPU 结果与 CPU 参考一致（容差 rel<1e-5）。

### M1 前向算子（fp32）
- 实现前向全部 kernel（fp32）。
- **验证**：每个 kernel 与 CPU 参考逐一对拍；拼出完整 GPT 前向后，**单/多 token 的 logits 与 Python numpy 参考一致**（rel<1e-3）。

### M2 训练闭环 —— 核心目标
- 实现反向全部 kernel + `adamw_step` + 训练循环 + 字符级分词 + 语料 batch。
- **验证**：① **逐层数值梯度检验**（finite difference，rel<1e-3）；② 小语料过拟合，loss → 趋 0；③ 训练出的模型能采样出可读文本。
- **产出**：浏览器内完成「训练 → 采样」完整闭环。

### M3 性能优化
- f16 GEMM 路径（权重 f16、累加 fp32）、kernel 融合、workgroup 调优。
- **验证**：f16 与 fp32 logits 回归一致；报告 tokens/s、steps/s。

### M4 加载现成小模型
- `safetensors` 解析、Qwen BPE、GQA（Q head 广播到 KV head）、RoPE `theta=1e6`、SwiGLU `gate_proj`、`tie_word_embeddings`、int4 非对称反量化（group_size=128）。
- **验证**：贪心解码结果与参考实现逐 token 对拍。
- **产出**：浏览器内对话页跑 Qwen2.5-0.5B int4。

### M5 完善
- KV cache 复用、采样策略、长上下文、IndexedDB checkpoint 存取、错误处理与鲁棒性。
- **验证**：checkpoint 往返后 logits 完全一致。

> **执行顺序**：先打通 M0 → M1 → M2（自训闭环），再 M3 → M4（外部模型）。int4、KV cache、融合优化可后置。

## 主要风险与对策

1. **f16 训练不稳定** → 训练全程 fp32，f16 仅走推理，且必须先通过 fp32 对拍。
2. **无 fp32 atomicAdd** → 权重梯度用「每输出元素唯一线程 + 规约」，禁止原子累加。
3. **核显性能陷阱**（共享内存带宽、驱动 bug）→ 先跑 fp32 基线，再逐步优化；性能目标务实（tokens/s 而非追平独显）。
4. **标签页后台节流** → 训练/生成放 **Web Worker**，用 `await` 驱动循环，**不依赖 rAF**。
5. **2 GiB 硬顶** → 多 buffer 分片 + grid 切分；超限张量拒绝加载并给出明确报错。
6. **WGSL f16 细节** → 需 `enable f16` 扩展、注意 16 字节对齐。
7. **环境复测** → 最终运行浏览器用 `webgpu-check.html` 复测，确认 limits 一致。

## 端到端验证方式

1. `npm run dev` 启动 Vite，浏览器打开本地页面。
2. 打开内置「自检」页：自动跑 M0/M1 的算子对拍，页面显示全部 PASS/FAIL。
3. 「训练」页：选语料 → 开始训练 → 实时显示 loss 曲线与 steps/s → 训练后采样文本。
4. 「推理」页：加载自训 checkpoint 或 Qwen2.5-0.5B int4 → 流式输出 → 显示 tokens/s 与显存占用。
5. 每阶段结束在真实 Chrome/Edge 中重跑 `webgpu-check.html` 并记录基线。
