# 16 · 协议与规范

> 前置：02 架构总纲（分层契约）、03 IR（内容寻址）、15 产品形态与协作模型。
> 定位：把 15 的**产品形态**下沉为**规范**。本系统不是平台，是一族**开放规范 + 参考实现**。
> 状态：v0.1 讨论稿（2026-10-08）。**凡标 ★待定 的是需要你拍板的。**

---

## 0. 一句话

**我们交付的不是一个网站，是一族规范（specifications）加一个参考实现（reference implementation）。
任何人不经我们许可，就能实现自己的客户端、自己的服务器、自己的工具，并且互相能通。**

> 对照：HuggingFace 是平台，Git 是协议（+ 参考实现）。
> **我们要做 AI 协作领域的 Git，不是 AI 协作领域的 HuggingFace。**

## 0.1 用户原话（2026-10-08）

> "最好是协议、平台、规范类的，大家都创建，开发自己的工具，使用。不依赖特定平台。
> 遵循互联网、共享、开放、开源、自由等精神。"

本文就是这句话的设计回应。

## 1. 为什么这一次真的能做到"不依赖平台"

**技术前提**：本系统的权威物是**内容寻址的纯数据**（03 `specHash`、11 资产、08 账本）。
这不是口号，是结构事实：谁保存、用什么语言实现、跑在什么上，都不影响对象本身。

| | 平台模式 | 协议模式（本系统） |
|---|---|---|
| 你的数据在哪 | 在它的库里 | 在你自己的机器上（原文永不出本地） |
| 用什么格式 | 它的私有格式 | 开放、可哈希、可用文本编辑器打开的纯数据 |
| 换实现 | 数据迁不走 | 导出=一堆内容寻址对象；导入=校验哈希 |
| 谁能做工具 | 只有平台方 | **任何人**（规范公开，参考实现只是一份实现） |
| 平台停运 | 你死 | 网络即资产，无单点 |
| 信任来源 | "请相信我们" | 可验证（哈希 / 探针 / 可验追加账本） |

### 1.1 反平台化三条铁律（写死，可验收）

1. **无中心必需组件**——信令 / 中继 / registry 都是**可选加速层**，全部可自建、可离线（10 §1 G1/G5）。
2. **无专有格式**——一切对象可序列化、可哈希、可用 `cat` 打开（02 R2）。
3. **规范本身可 fork**——允许多实现并存，分歧用 **profile（档位）** 表达，不靠权威压制。

## 2. 2026 现状：通信层已经有了，**契约层**还空着（调研结论）

### 2.1 agent 协议格局（截至 2026-09）

| 协议 | 归属 | 定位 | 传输 | 身份 | 2026 状态 |
|---|---|---|---|---|---|
| **MCP** | Anthropic → Linux Foundation | agent ↔ **工具/数据** | JSON-RPC (stdio/HTTP) | 宿主托管 | 事实标准，月下载过亿 |
| **A2A** | Google → Linux Foundation | agent ↔ **agent**（跨组织委派） | JSON-RPC + SSE | Agent Card（**可签名**） | v1.0 生产可用，150+ 组织 |
| **ACP** | IBM/BeeAI | agent 间多方可编排 | REST/HTTP | HTTP auth | **2025-08 并入 A2A** |
| **AG-UI** | CopilotKit | agent → **前端**流式 | SSE/WebSocket | N/A | 生态增长中 |
| **ANP** | 社区 | **去中心** agent 网络 | DID + JSON-LD, libp2p | **DID** | 早期（研究/试点） |

> 治理：MCP/A2A/ACP 已归 **Agentic AI Foundation（AAIF，Linux Foundation）** 统一治理。

### 2.2 关键结论：五方互补，但缺一层"契约"

多份 2026 综述（如 OSSA 的协议调研）给出一致判断：

> **这五个协议都假定"agent 已经定义好、并且已经在运行"。**
> 没有任何一个回答：**我怎么可移植地定义一个 agent**（身份 / 角色 / 能力 / 治理）？
> 我怎么把它从一个平台搬到另一个？我怎么在部署前**校验**它？
> 这被明确命名为 **Contract Layer 缺口**。

**这就是本系统的位置**——我们**不做又一个通信协议**，我们做**契约层 + 执行层**：

```
┌──────────────────────────────────────────────────────────┐
│  工具 / 客户端 / 界面        （任何人实现，含我们的参考实现）  │
├──────────────────────────────────────────────────────────┤
│  契约层   ← ★本系统：对象模型 / 资产 / 任务 / 能力 / 治理     │  16 + 17
│            （可移植、可校验、内容寻址、跨平台）              │
├──────────────────────────────────────────────────────────┤
│  执行层   ← 本系统：Spec IR / 编译 / 训练 / 推理             │  03~08
├──────────────────────────────────────────────────────────┤
│  通信层      MCP | A2A | AG-UI | ANP   （已由 LF 统一）      │  ← 借用，不重造
├──────────────────────────────────────────────────────────┤
│  身份层      W3C DID / VC                                  │  ← 借用
├──────────────────────────────────────────────────────────┤
│  传输层      WebRTC | HTTP | libp2p                        │  ← 借用
└──────────────────────────────────────────────────────────┘
```

### 2.3 能直接借用的外部标准（**不重复造轮子**）

| 领域 | 已有标准 | 我们怎么用 |
|---|---|---|
| 去中心身份 | **W3C DID / VC** | 直接采用（10 §4 的 `peerId` 是其降级档） |
| agent 能力凭证 | VC + DIF 的 MCP-I / `did:trail` | 采纳方向（2026-03 捐给 DIF） |
| 数据/模型血缘 | **W3C PROV-O** | 直接采用（我们的溯源链就是 PROV 的一个剖面） |
| 数据集元数据 | **Croissant 1.1**（MLCommons，2026-02） | **`DatasetRecord` 与 Croissant 对齐**（它已内建 PROV-O + ODRL/DUO） |
| 数据质量 | **ISO/IEC 5259** 系列（2024–2026） | 作为质量过滤算子的依据（11 §2.3） |
| 许可 / 用法策略 | **SPDX / ODRL / DUO** | 直接采用（11 §2.2 的 `license` 就是 SPDX） |
| 生成内容溯源 | C2PA（EU AI Act Art.50 推动） | 参考（合成数据标记 §2.6.1 的对外兼容层） |
| 供应链证明 | SLSA / Sigstore | 参考（受信内核 `defineOp` 的证明形态，05 §4） |
| 内容寻址 | IPFS CID 格式 | 参考（可直接复用 CID 作为 hash 编码） |

> **结论：我们只在两处做真正的创新，其余全部站在已有标准上。**
> 创新点 ①：**"验收即探针"**——把任务验收写成可复算的探针（17 §4）。
> 创新点 ②：**"联邦训练即 fork/merge"**——把训练与聚合规范化为内容寻址对象（11、15 §1.3）。

命名用 `SPEC-n`，每条都要能独立实现、独立测。**每条都绑定到已有 design 章节，不新造概念。**

| # | 规范 | 内容 | 源自 |
|---|---|---|---|
| SPEC-1 | **对象模型与寻址** | 九类对象、`contentHash` 规范化、导出/导入、parents 图 | 15 §2、03 §2 |
| SPEC-2 | **Spec IR** | 模型结构的数据模型、类型系统、诊断码、版本化 | 03 全篇 |
| SPEC-3 | **执行与编译** | `infer/plan/emit/run`、arena 与不变量、多后端 | 06 全篇 |
| SPEC-4 | **更新与聚合** | `Update` 语义、FedNova、serverOpt、SyncSpec、staleness | 09 全篇、07 |
| SPEC-5 | **任务与委派** | `Task` 对象、验收、四权分离、能力匹配 | **17**（本文配套） |
| SPEC-6 | **身份、能力与信任分级** | DID/VC 剖面、能力凭证、L0–L3、门票 | 10 §4/§5 |
| SPEC-7 | **账本与贡献** | `LedgerEntry`、双份额、`probeDelta`、可验追加 | 11 §4 |

## 4. 不依赖平台：多方实现如何成立

一个规范能活，靠的不是文档写得漂亮，而是**别人能独立实现并验证自己实现对**。

| 机制 | 内容 |
|---|---|
| **参考实现只是一份实现** | 本仓库是 reference implementation，不是唯一。文档里必须写"这不是唯一实现" |
| **一致性测试套件（conformance suite）** | 任何实现只要能过套件，就是"合规实现"。**这就是 `verify-*.mjs` 的对外版本** |
| **最小实现清单** | 给出"只做 Core 档的最小实现"需要哪些模块、多少行量级（降低起步门槛） |
| **可执行的不变量** | 关键不变量以可运行断言给出（INV-1..26），不靠文字约束 |
| **数据可带走** | 导出 = 打包内容寻址对象；导入 = 逐哈希校验 + 拒绝不匹配 |

> 这条直接决定了产品的**可信度**：一个"只能由作者运行"的系统，不是协议，是平台。
> ⇒ PROTO-V2（§9）：**用第二个独立实现（可以是别的语言/别的 UI）跑通 Core 档。**

## 5. 一致性档位（Profiles）

档位让"小实现"也有合法位置——不是所有人一上来都要实现全套。

| 档位 | MUST 覆盖 | 典型用途 | 起步成本 |
|---|---|---|---|
| **Core** | SPEC-1 对象模型与寻址 + 导出/导入 | 任何工具（查看器、转换器） | 极低 |
| **Core+** | + SPEC-2/3 的只读（能读 IR、能跑推理） | 推理客户端、模型浏览器 | 低 |
| **Solo** | + SPEC-2/3/4 单机 + SPEC-7 本地账本 | 单人多设备训练（**第一用户档**） | 中 |
| **Team** | + SPEC-4 聚合 + SPEC-6 L1 + 私有 registry | 团队协作 | 中高 |
| **Commons** | + SPEC-5 任务 + SPEC-6 L2/L3 + SPEC-7 审计 + 可用性 | 开放公共网络 | 高 |

> 冷启动策略（15 §8）：**先把 Solo 档做扎实**——它不依赖信任层，却是所有上层的地基。

## 6. 扩展与版本化：怎么不被自己锁死

2026 的教训很直接：**A2A 一年内多次改版**，赌单一 wire format 是危险的。
所以规范必须内置"演化能力"：

1. **未知字段 MUST 被忽略**（forward-compatibility）——这让新字段可以无痛加入。
2. **扩展命名空间**——第三方扩展用带前缀的键，不污染核心。
3. **能力协商**——不假设对端支持什么，**先问**（02 R3/R4 的规范版）。
4. **语义化版本**——major 只在"打破纯数据契约"时升；因为对象模型是纯数据、扩展点多，major 应罕见。
5. **档位表达分歧**——实现差异写进 profile，而不是分裂成互不兼容的方言。

## 7. 规范自身的治理（开放、无单点）

治理的对象是**规范**，不是网络（网络治理见 11 §6）。参考已有先例：
Linux Foundation / AAIF（协议）、W3C（身份）、MLCommons（Croissant）——都是**开放工作组**模式。

本项目先给的**务实起点**：

| 要素 | 起步做法 |
|---|---|
| 变更 | 走公开的 **RFC 提案**（编号 + 讨论记录 + 决议），不静默改 |
| 实现权 | **任何人可自由实现**，不需要许可、不需要加入组织 |
| 分歧 | 用 **profile** 表达；允许并存，不靠权威压制 |
| 兜底 | **fork 即退出**（规范本身可 fork，11 §6） |
| 升级 | 需要正式治理时，用 Ostrom 八原则自检（11 §6，ADR-028） |

★待定：起步阶段是**作者主导（BDFL 式）**，还是一开始就建一个开放审议流程？
我的倾向：**作者主导 + 公开记录**——规范在没有用户之前搞治理是空转；
但**从第一天就把所有决策记进 ADR**，让将来移交有据可依。

## 8. 反平台化铁律（可验收的六条）

1. **无中心必需组件**——断网 / 无信令 / 无 registry 时，Core 与 Solo 档 MUST 仍可用。
2. **无专有格式**——所有对象 MUST 可序列化为有公开规范的纯数据。
3. **可离线**——本地训练闭环 MUST NOT 依赖任何网络请求。
4. **规范可 fork**——规范文本 MUST 以允许 fork 的许可发布（许可证等具体条款 ★待定）。
5. **数据可迁出**——任何实现 MUST 提供完整导出；导出物 MUST 能在另一实现中导入。
6. **实现可替换**——换实现 MUST NOT 要求重新训练或重新登记资产。

## 9. 验收线（PROTO-V）

| 编号 | 标准 |
|---|---|
| PROTO-V1 | **双实现互操作**：第二个独立实现（不同语言或不同 UI）能读、写、跑通 Core 档对象 |
| PROTO-V2 | **一致性套件可移植**：套件不依赖本仓库代码即可对任意实现运行 |
| PROTO-V3 | **离线可启动**：无网络、无信令、无 registry 时，Core+Solo 档全功能可用 |
| PROTO-V4 | **导出/导入无损**：导出一套对象 → 另一实现导入 → 逐哈希一致、可继续训练 |
| PROTO-V5 | **未知字段兼容**：注入未知字段的实现仍被接受；旧实现不崩 |
| PROTO-V6 | **借用标准的合规性**：`DatasetRecord` 为合法 Croissant 1.1；溯源可映射到 PROV-O；许可为合法 SPDX |
| PROTO-V7 | **规范可 fork**：第三方 fork 规范并做局部改动后，差异以 profile 形式可被识别 |

## 10. 诚实边界

- **规范 ≠ 实现质量**。合规实现完全可以很烂；规范只保证**互操作**，不保证**性能与正确性**。
- **不保证"同等硬件下性能"**。这与 01 §5 非目标一致。
- **内容寻址保证完整性，不保证可用性**（11 §2.8）。
- **借用标准的风险**：DID/VC、PROV-O、Croissant 的演化不由我们控制；用它们就必须接受它们的节奏。
- **"不依赖平台" ≠ "不需要基础设施"**——信令/中继/存储仍需要有人跑，只是**没有人能垄断它**。
