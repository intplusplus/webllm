## 1. 核心判断：语言设计的目标读者是 AI

v2/v3 一直在优化"**给人写的体验**"（JSX 顺不顺手、上手成本低不低）。
但一个前提已经变了：**写代码的人在变少，写代码的 AI 在变多。**

所以语言设计的约束条件应该反过来写：

| 给 AI 写的语言要什么 | 给 JSX 顺手的语言要什么 |
|---|---|
| 词汇表**有界**、可枚举 | 表达力越强越好 |
| 写错**立即可判**（不执行） | 错误堆栈可读 |
| 输出**可寻址/可 diff/可回滚** | 可读性好 |
| 迭代**便宜确定可回放** | 调试灵活 |
| 有**成本模型**可在预算内搜索 | 够用来就行 |

结论：**IR（JSON）+ schema 约束的一等公民，JSX 是糖。**
这不是"反人类"，而是把人类 IDE/交互层放在糖上，把机器接口放在权威层。

## 2. 三重编写面

```
                 ┌──────────────────────────────┐
   AI / agent ──►│ ① Spec IR (JSON)   【权威】     │◄── 传输/寻址/公地
                 ├──────────────────────────────┤
   人类/IDE   ──►│ ② JSX 糖            【糖】     │  round-trip 双向保义
                 ├──────────────────────────────┤
   AI（受限）──►│ ③ 受限解码语法(grammar) 【糖】  │  schema → GBNF/JSON-Schema
                 └──────────────────────────────┘
```

- **①**：一切路径的终点。任何其他写法最终都编译成它。
- **②**：给人写和读，类型推导 + IDE 报错指向 `meta.span`。
- **③**：给 LLM 用。由注册表 schema **自动生成**文法，LLM 解码被约束在合法集合内。

## 3. 组件注册表：AI 的词汇表

注册表是**唯一**的语义来源（op 契约、能力位、成本、组合规则）。它的每一项都是一个
**可枚举的概念**，因此总和必须小到能塞进上下文窗口：

> **验收：核心 op ≤ 30，每个 op 的 schema 说明 ≤ 15 行。**

### 3.1 schema 字段

```jsonc
{
  "op": "Attn",
  "summary": "多头注意力（global/sliding/causal 可选）",
  "props": {
    "dim":   { "type": "int",  "min": 1, "required": true },
    "heads": { "type": "int",  "min": 1, "multipleOf": "dim", "required": true },
    "kind":  { "type": "enum", "values": ["global","swa","qsa"], "default": "global" },
    "window":{ "type": "int",  "min": 1, "when": "kind == 'swa'" }
  },
  "io": { "in":  ["B","T","dim"], "out": ["B","T","dim"], "slots": ["cond"] },
  "caps": ["forward","vjp","jvp","perturbable"],
  "phase": ["train","prefill","decode"],
  "pure": true,
  "cost": { "flops": "4*B*T*T*dim", "memPeak": "O(T^2)", "activations": "O(B*T*T)" },
  "wires":  [                                   // 组合规则（AI 最需要的约束）
    "输入需 3D；heads 必须整除 dim；swa 时 window ≤ T",
    "decode 相位必须有 KV state（自动插入 Cache）"
  ],
  "badges": ["LLM","attention"]                 // 用于按任务聚类检索
}
```

### 3.2 从 schema 自动生成受限解码文法

```
schema(注册表) ──generateGrammar()──► GBNF / JSON-Schema / 结构化输出约束
```

- LLM 生成时，解码被约束在"合法 IR 树"内 → **语法错误率趋零**。
- 剩下的错误只有**语义错误**（shape 不匹配、能力缺失、预算超限），全部由
  `infer()` 与 `plan()` 静态捕获 → **不需要跑 GPU**。
- 词汇表**按任务裁剪**：`query("训一个小 LM")` 只返回相关 12 个 op，
  让约束文法更小、生成更快。

> **可行性水位（★ 第三轮评审补外部来源）**：受限/结构化解码 2024 年起已有成熟
> 工程件（XGrammar 等的"高效可移植结构化生成"、Outlines/JSON-Schema 一脉），
> 所以 LANG-V2"100% 语法合法"不是赌研究突破——是把成熟件接进 `register.query()`
> 的输出端。仍要保留的诚实边界：文法只保证**句法合法**，LLM 仍可能生成
> "语义合法但训不动"的模型（R-23），那是 infer/probe 的活，不是文法的活。

## 4. AI 编写回路（agent 工具协议）

AI 通过一组**确定性工具**与系统交互，每个工具都是纯函数或可回放命令：

| 工具 | 输入 | 输出 | 确定性 |
|---|---|---|---|
| `register.query(task, budget, devices)` | 自然语言任务 + 约束 | 相关 op schema 列表 | 是 |
| `llm.generate(schema, prompt)` | 任务描述 | Spec IR（受限解码） | 否（LLM） |
| `ir.diff(a, b)` | 两个 IR | 结构化 diff（节点增删改） | 是 |
| `ir.infer(ir, strategy?)` | IR + 可选策略 | `InferResult`（诊断+能力汇总） | 是 |
| `ir.plan(ir, cluster)` | IR + 集群能力画像 | 计划（策略/角色/分片/成本） | 是 |
| `ir.profile(ir, data)` | IR + 小数据集 | 结构化指标（吞吐/显存/曲线） | 是 |
| `ir.run(ir, data, strategy)` | IR + 数据 | trace + Update | 是 |
| `ir.emit(ir, backend)` | IR | 可执行 artifact | 是 |

### 4.1 典型回路

```
1  任务："写一个 8 层 dim=256 的 GPT，能在 512MB 显存的手机上训练"
2  register.query("GPT", budget=512MB)      → 12 个相关 op 的 schema
3  llm.generate(...)                        → IR v0
4  ir.infer(IR v0)                          → [ERROR SHAPE_MISMATCH at head.port.in,
                                              fix: insert-op Reshape]
5  AI 应用 fix                              → IR v1
6  ir.plan(IR v1, cluster=[phone,pc])       → {phone: spsa, pc: backprop, shard: layer}
7  ir.plan 报 BUDGET_EXCEEDED               → AI 把 layers 8→6 或改精度
8  ir.run(IR v2, data, strategy)            → loss 曲线
9  ir.diff / ir.fork                        → 进公地
```

**关键性质**：步骤 4/6/7 **毫秒级且不跑 GPU**。这一步让"AI 反复试错"的成本
从"分钟 × GPU"降到"次秒 × CPU"——这是 AI 原生回路**能不能成立**的分水岭。

## 5. 例子：同一个模型的三种写法

```tsx
// ② JSX（人写）
const GPT = ({ vocab, dim, layers, heads }) => (
  <Model trainer={{ strategy: 'backprop', lr: 3e-4 }}>
    <Embed vocab={vocab} dim={dim} />
    {range(layers).map(i => <Block key={i} dim={dim} heads={heads} />)}
    <RMSNorm dim={dim} />
    <Head dim={dim} vocab={vocab} tie="embed" />
  </Model>
);
```

```json
// ① IR（AI/网络看到的权威物，节选）
{
  "schemaVersion": "1.0",
  "graph": { "op": "Seq", "children": [
      { "id": "emb", "op": "Embed", "props": { "vocab": 50157, "dim": 256 } },
      { "id": "blocks", "op": "Repeat", "props": { "times": 6 },
        "children": [{ "id": "b", "op": "Block", "props": { "dim": 256, "heads": 8 } }] },
      { "id": "n", "op": "RMSNorm", "props": { "dim": 256 } },
      { "id": "h", "op": "Head", "props": { "dim": 256, "vocab": 50157, "tie": "emb" } }
  ]},
  "trainer": { "strategy": "backprop", "params": { "lr": 0.0003 },
               "schedule": { "localSteps": 8, "syncEvery": 4, "precision": "fp32" } },
  "meta": { "license": "MIT" }
}
```

```text
// ③ 受限解码文法（GBNF 片段，由 schema 自动生成）
model ::= "{" schemaVersion "," graph "," trainer "}"
node  ::= "{" "\"id\":" string "," "\"op\":" opName "," props? "}"
opName ::= "\"Embed\"" | "\"Attn\"" | "\"Block\"" | ...   ← 来自注册表，有界
```

## 6. 人类与 AI 的分工契约（★ 来自 ZGCM-1 实证校准）

04 章早期写法暗示"AI 能独立建模"。ZGCM-1 用 9 名核心参与者对 11 类研发任务
做 L1-L5 自主性评级，给出了**实测边界**（14 §7.3）：

| 任务 | 实测自主性 | 含义 |
|---|---|---|
| 实验监控与部署 | **L4** | 人给目标与约束后，Agent 可独立规划、执行、据反馈调整 |
| 模型架构与学习算法设计 | **L2** | 主要是帮助实现已有方案、运行预设实验 |
| 研究什么 / 关键设计怎么选 | **L1-L2** | 仍需人主导 |

⇒ 本章的承诺因此**分层**，不笼统宣称"AI 自动做研究"：

| 层级 | 任务 | 承诺 |
|---|---|---|
| **AI 主导（目标 L4）** | IR 生成与修复、静态诊断、成本优化、实验编排、日志监控、故障定位、评测执行 | 可无人值守迭代 |
| **人机协作（目标 L3）** | 在既定家族内改结构 / 换策略 / 调配方 | AI 提议，人审 |
| **人主导（目标 L2，不承诺更高）** | 研究什么、选哪条技术路线、关键设计取舍 | AI 只辅助实现 |

> 这个校准**提升**可信度：与其宣称"AI 自动做研究"（会被第一个失败打脸），
> 不如宣称"AI 把 L4 的执行层接到 L2 的架构层上"——这正是 ZGCM 7 个人
> （仅 2 人 AI 方向）能用一个暑假训出 7B 的原因。

### 6.1 经验层：Skill 也是注册表资产（★ 来自 ZGent）

ZGCM 的关键基础设施不是"几百个 Agent"，而是把**验证过的脚本、工作流、debug 经验
沉淀为可复用 Skill**，后加入的 Agent 接着经验做事（14 §7.4）。
⇒ 注册表除 op schema（语义词汇表）外，还要有**经验词汇表**：

```
Skill := {
  skillHash:  contentHash,
  kind:       'workflow' | 'debug' | 'script' | 'playbook',
  provenance: { validatedOn: [specHash], author, reviewId },
  body:       结构化步骤（同样可寻址/可审计/可分发）
}
```

Skill 与 op 一样内容寻址、可进公地（11 §4）——**新节点不用从零踩坑**。

## 7. 为什么 PyTorch 给不了这条回路

| PyTorch | 我们 |
|---|---|
| 模型=Python 对象；错误要**跑起来**才炸，是 traceback | 静态 `infer()`，毫秒级、结构化、带 `fix` |
| 词汇表无界（任何库的 Module 都可 import） | 注册表有界（≤30 核心 op），可枚举、可裁剪 |
| 模型不可寻址 → AI 无法"生成变体→diff→保留" | `ir.diff` + `specHash`，天然支持 A/B 与演化 |
| 无成本模型 → 无法在预算内搜索 | `cost` 注解 + `plan()` 预算校验 |
| **写 GPU kernel = 稀缺人类专家** | **KernelBench（ICML 2025）的诚实读法**：LLM 已能写**可编译** GPU kernel，但正确性/效率分布离专家远 ⇒ 05 §4 的 `defineOp` "受信贡献 + 对拍"是正确门槛，AI **起草**（缩短人类 80% 时间）+ 对拍筛掉错的是演进路径，不是承诺 |
| 生成代码=任意副作用 | 受限解码语法 + 纯 IR，**结构性无副作用** |
| 经验靠人口传 / 散落在私有脚本 | `Skill` 内容寻址，经验可继承、可审计 |

## 8. 验收线（AI 可写性，可检验）

| 编号 | 指标 | 标准 |
|---|---|---|
| LANG-V1 | 词汇表规模 | 核心 op ≤ 30 且 schema ≤ 15 行/op |
| LANG-V2 | 受限解码有效性 | 生成结果 100% 语法合法（schema→grammar 无漏洞） |
| LANG-V3 | **执行层盲测**（AI 主导层） | 只给 schema 不给示例，agent 生成 08 任一家族 IR，首轮 `infer()` 无 error 的比例 ≥ 标定值 |
| LANG-V4 | 自修复率 | 对 error 级诊断，单轮按 `fix` 修复成功率 ≥ 标定值 |
| LANG-V5 | 成本模型精度 | `plan()` FLOPs 估计 vs 实测相对误差 ≤ 标定值 |
| LANG-V6 | round-trip | JSX→IR→JSX 语义保义（08 家族全量） |
| LANG-V7 | 策略选择 | 给定能力画像，agent 选出可行策略组合并能陈述降级理由 |
| **LANG-V8** | **实验编排（L4 验收）** | 人只给目标+约束，agent 能完成"提交任务→监控日志→定位故障→调整配置→复跑"闭环，无人值守轮数 ≥ 标定值 |
| **LANG-V9** | **Skill 复用** | 新 agent 凭既有 `Skill` 复现一次 debug/工作流，成功率 ≥ 标定值 |
| **LANG-V10** | **LoC-Complexity = O(1)** | 接入新功能（RoPE/MoE/量化/新算子）时，**对既有接口的修改量保持常数**（不随模块数 N、变体数 M 增长）。度量方式见下 |

> 标定值在 P2 阶段用同一批 agent + 同一批任务跑出基线后写入（不做先验承诺）。
> **LANG-V3 只承诺"执行层"**——架构与算法设计按 §6 分层只承诺到 L2/L3，
> 不得把 LANG-V3 通过当作"AI 能做研究"的证据。

### 8.1 LoC-Complexity：为什么这是本设计最硬的指标（★ 来自 AXLearn）

Apple 的 AXLearn 把「**新增功能时要改多少既有接口**」做成可分析的系统指标：
随模块数 N、功能变体数 M 的增长是 O(1) / O(N) / O(NM)。
论文案例：DeepSpeed 把 QwenV2 接入 MoE **需 200+ 行**（不含 MoE 层本身）；
在 20 模型变体 × 10 注意力变体规模下估算 **约 4000 行接口修改，而 AXLearn 为 0**。

**本设计在这个指标上结构性地占优**，因为不存在可扩散的继承链：

| | AXLearn | 本设计 |
|---|---|---|
| 表达单位 | Python 配置 + 模块类（**继承仍可用**） | **纯数据树**（结构上不可能继承） |
| 换 FFN→MoE | 递归 Config Modifier ~10 行 | **替换一个数据节点的值**（`ir.diff` + fork） |
| O(1) 的来源 | **纪律性**（严格封装 + 分层配置约束团队） | **结构性**（数据无继承链） |

⇒ **度量方式（只在我们自己的代码库上做，不做跨框架排名）**：
接入第 k 个新功能时，统计"为使它工作而修改的**既有接口/既有节点定义**行数"，
要求该数字**不随已接入功能数增长**。0 是目标，常数是合格，线性是失败。
（论文的诚实边界同样适用：此指标只在自有代码库上有意义。）
