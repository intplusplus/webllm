# 联邦学习研究 → 本项目改进清单（2026-10）

> 结论先行：**浏览器里没有成熟的联邦学习框架**，所以「换库」不是杠杆；
> **算法**才是。你手里已有的三样东西决定了改进方向：
> ① 实测过每轮 **832 KB** 的权重交换（通信是真实瓶颈）；
> ② 设备能力差异极大（PC 有 WebGPU、手机只有 CPU）→ **client drift** 是真实问题；
> ③ 已有 `verify-fed` 这套「FedAvg vs DiLoCo 对拍」的测量基建 → 每个改进都能被量化验证。

---

## 一、按「收益 / 工作量」排序的改进项

### P0-1 权重交换 int8 量化 —— 收益最大、最便宜

**研究依据**：量化（f32→8/16-bit）+ 稀疏化 + 增量编码，平均每轮传输量可降 **>65%** 而精度几乎不掉
（Ghimire et al., 2025；FedLab/Zeng 2021 同结论）。

**对你意味着什么**：你实测 GPU tiny-GPT 满权重交换 ≈ 832 KB/轮（2 节点）。
int8 直接砍到 **1/4**（≈208 KB）。手机上行是真正的瓶颈，这一刀最实在。

**改哪里**：`src/fed/protocol.ts` 的 `encodeWeights` / `decodeWeights`。
- 每个张量独立 scale：`scale = max(|w|) / 127`，存 `[scale(f32), int8 载荷]`，解码时 `w = q * scale`。
- `RoomManifest` 加 `wire: 'f32' | 'int8'`，写进指纹 —— **全网必须一致**，跟引擎一个道理。
- ⚠️ 两个坑：
  1. `weightsDigest()` 走 encode→decode 往返，量化后摘要会变 —— 保持自洽即可，
     但**别再假设「摘要 == f32 原始摘要」**。
  2. 交叉校验（`crossCheck`）用提交权重复算探针 loss，int8 的量化误差可能超过
     `VERIFY_TOL = 1e-3`。你现在默认关交叉校验（自用设备），所以没事；
     一旦要开，就得放宽容差或只量化「增量」。

**工作量**：约 40–60 行 + 测试。**先做这个。**

---

### P0-2 FedProx —— 直接治「设备异构」的 client drift

**研究依据**：非 IID + 异构环境下，FedProx 比 FedAvg 高 7%（CIFAR-10）到 22%
（ICIAAI 2025 综述）；SCAFFOLD 更好但**通信量翻倍**（要传 control variate），
对你这种手机上行受限的场景不划算。

**对你意味着什么**：你的 shard 是语料的**连续切片**，PC 和手机算力差 3–10 倍、
每轮步数还被时间预算截断成不一样 —— 这是教科书级的 client drift 场景。

**改哪里**：本地目标函数加一项 proximal：
```
L_local = L_CE(w) + (μ/2)·‖w − w_global‖²
```
- `TrainEngine.trainBatch` 增加可选参数 `{ mu?: number; global?: NamedWeights }`
  （`src/fed/engine.ts`，两个引擎都要改）。
- μ 进 `RoomManifest`（默认 0 = 退化为 FedAvg），房主在「房间设计」里调。
- **诚实提醒**：你自己的实测是「小规模下 FedAvg 反而优于 DiLoCo」。
  μ 的收益要**轮数和步数上来之后**才显出来 —— 你刚把默认档改成中/大，正好够测。
  用现成的 `verify-fed` 对拍框架加一组 μ=0 / 0.01 / 0.1 的对照，别凭感觉。

**工作量**：接口改动 + 两个引擎各 ~10 行。第二个做。

---

### P0-3 服务端自适应聚合（FedAvgM / FedAdam）—— 你已经写了一半

**研究依据**：框架综述把 FedAdam / FedYogi / FedAvgM 列为标准同步聚合算法；
它们的本质是「服务端在聚合增量上再跑一个优化器」。

**对你意味着什么**：你的 `aggregateGlobal` 已经有「基准点 + 加权增量 + 外层动量」骨架
—— **FedAvgM 就是这套骨架在 η=1、β=0.9 时的形态**，你现在的 DiLoCo 模式稍微改下
语义就是它；FedAdam 只需在 `AggregateState` 里再加一个 vState（二阶矩）。

**改哪里**：`src/fed/protocol.ts` 的 `AggregateSpec` / `aggregateGlobal`。
把聚合方式下拉从「FedAvg / DiLoCo」扩成「FedAvg / FedAvgM / FedAdam / DiLoCo」，
文档里写清楚它们共用同一个骨架、参数怎么对应（这是你已经验证过的等价性）。

**工作量**：很小。顺手做。

### P1-1 把 CPU 引擎搬进 Web Worker（配合 Comlink）

「点训练卡死」的正解。`TrainEngine` 接口当初就设计成全异步，就是为了这一天。

**用库的理由**：[`Comlink`](https://github.com/GoogleChromeLabs/comlink) 把 Worker 的
postMessage 协议变成 `await proxy.method()`，正好套在你已有的 async 接口上，
省掉一大坨手写消息协议。这是**真正值得引入的库**。

**坑**：单文件版（`demo/fed-standalone.html`）用 esbuild 打 IIFE，
worker 打成独立文件就破坏「双击离线可用」。两个选择：
- 单文件版继续跑主线程（标注清楚），在线版走 worker；
- 或用 `?worker&inline` 让 Vite 内联 worker（体积换体验）。

---

### P1-2 迟到更新不丢弃（staleness-tolerant）

**研究依据**：异步联邦（FedAsync / FedBuff）就是为「网络延迟尖峰 + 掉队者」设计的；
综述里提到 200ms+ 延迟会造成 40% 掉队超时，异步化能救回 95% 参与率。

**对你意味着什么**：你现在是「本轮没交就记 timeout、下一轮再说」。
更进一步的改法：**迟到的权重帧别丢，进下一轮的聚合池**（按 meta.round 判断新鲜度，
太旧就不收）。改动很小（`node.ts` 的 submissions 生命周期），收益是
「手机慢半拍也能贡献上」，跟你的「随时加入退出」哲学一致。

---

### P1-3 差分隐私（DP-SGD）：可选开关，几十行

**研究依据**：训练交换的**权重本身会泄漏训练数据**（成员推断 / 数据重建攻击），
所以「数据不出本地」≠「隐私无忧」。防御分层：安全聚合（密码学掩码）→ 差分隐私（统计噪声）。

**对你意味着什么**：安全聚合（SecAgg）要做掩码交换，2–3 台自己的设备**不值得**；
但 **DP 的最简形态（裁剪 + 高斯噪声）很便宜**：
- 上报前把 Δ 裁剪到范数 ≤ C，再加 σ·N(0,1) 噪声；
- 做成「房间设计」里的开关，默认关（都是你自己的设备，关掉省精度）。
- 价值在于：将来真要对外开放（你规划文档里的「公共训练网络」），这个开关就是门票。

### P2（等前面做完再说）

| 方向 | 是什么 | 为什么先放着 |
|---|---|---|
| 个性化（FedRep / 本地微调头） | 全局模型 + 每设备本地微调 | 你只有 2–5 台设备，全局模型够用 |
| 聚类联邦 | 按数据分布分组各训各的 | 设备太少，分组没意义 |
| 稳健聚合（Krum / trimmed mean） | 防拜占庭 | 你已明确：都是自己的设备，威胁模型不成立 |
| 知识蒸馏（FedDF） | 用公共数据蒸馏 | 需要公共无标注数据集，先解决通信 |
| 增量学习 / LoRA | 只传低秩增量 | 等 GPU 模型再大一点、通信又成为瓶颈时上 |

## 二、关于「用一些库」的诚实结论

| 库 | 值不值得用 | 结论 |
|---|---|---|
| **TensorFlow.js** | 有 WebGPU 后端、量化工具、Python 模型转换 | **不建议换引擎**。你项目的核心价值就是自研 WGSL 前向/反向；换成 tfjs 等于把项目的心脏换成别人的。可作**参考实现对拍**（用 tfjs 重算一遍 loss 验证你的 WGSL 数学对不对）—— 这倒是很值。 |
| **Comlink** | Worker RPC，10 行接入 | **建议引入**，配合 P1-1 |
| **ONNX Runtime Web** | 只支持推理 | 不合适，你需要训练 |
| **Flower / FedML / OpenFedML** | Python 生态，强在服务端编排 | 架构思想可抄（它们的 strategy 抽象很干净），代码用不上 |
| **vitest** | 单测框架 | 你现在用自写 verify 脚本且跑得很顺；等测试数量翻倍再说 |

**一句话**：这个项目里「库」的杠杆很小，「算法 + 你已有的测量基建」的杠杆很大。
别人用框架是因为不想写引擎，你写引擎就是为了不被框架绑住。

## 三、建议的执行顺序

1. **int8 量化**（P0-1）—— 一个文件，通信量直接 1/4，立刻能感知
2. **FedAvgM/FedAdam 聚合选项**（P0-3）—— 你已有骨架，顺手
3. **FedProx**（P0-2）—— 接口小改，配一组 μ 对照实验
4. **Web Worker + Comlink**（P1-1）—— 解决卡死的根
5. **迟到更新进聚合池**（P1-2）
6. **DP 开关**（P1-3）—— 对外开放前再做

每一步都先在 `verify-fed` 里加对照断言，再上真机。
