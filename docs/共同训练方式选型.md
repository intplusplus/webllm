# 共同训练方式选型

> 回答「多设备一起训一个模型，有哪几种做法、我们该选哪种」。
> 结论都对着本仓库的实际情况（浏览器节点、WiFi、自有设备、小模型）给，不做泛泛的算法综述。

---

## 0. 先看一张表：五种「一起训练」到底切的是什么

| 方式 | 切什么 | 同步频率 | 对网络的要求 | 本项目适用性 |
|---|---|---|---|---|
| 数据并行 + 同步 SGD | 切**数据**，每步 all-reduce 梯度 | 每一步 | **极低延迟**（毫秒级同步窗口） | ❌ WiFi 上不现实 |
| **数据并行 + 低频联邦**（FedAvg / DiLoCo） | 切**数据**，每轮同步一次 | 每轮（几百步一次） | **只要带宽，不要延迟** | ✅ **唯一正解** |
| 张量并行 | 切**层内矩阵** | 每一层 | NVLink 级带宽+延迟 | ❌ |
| 流水线并行 | 切**层** | 每 microbatch | 高带宽低延迟 | ❌ |
| 专家并行 / MoE | 切**专家**，按 token 路由 | 每 token | 高 | ❌ |

**判据很简单：网络是「延迟敏感」还是「带宽敏感」。**

同步 SGD 每步都要所有节点在同一毫秒窗口里完成计算再 all-reduce ——
手机的算力抖动、WiFi 的排队延迟，随便哪一样都能让这个窗口崩掉。
低频联邦把「延迟敏感」换成「带宽敏感」，而带宽是可以靠压缩解决的。
这是浏览器节点唯一能走的路。

> 顺带排除一个诱人但不成立的方向：**把模型切开放不同设备**（张量/流水线并行）。
> 它要求层间激活值频繁往返，局域网 WiFi 的往返延迟比 NVLink 高 3~4 个数量级，
> 收益会被通信彻底吃掉。除非设备间有万兆直连，否则不做。

---

## 1. 候选方案逐条评估（对着本仓库说）

### 1.1 同步 FedAvg —— ✅ 已实现，当前默认

星形：一个汇聚节点（主机）开轮，各节点在本地分片上训几步，上报权重，主机按样本数加权平均，广播回去。

- 优点：最简单、最稳、已跑通（端到端 16/16、真实浏览器 14/14）
- 缺点：**straggler** —— 最慢的节点决定全局速度；每轮传全量权重
- 适用：自己的几台设备，数量少，网络稳定

### 1.2 DiLoCo（增量 + 外层动量）—— ✅ 已实现，可切换

和 FedAvg 的差别只在聚合那一步，但概念上更「对」：

```
FedAvg :  G ← base + Δ̄
DiLoCo :  M ← β·M + Δ̄ ;  G ← base + η·M
```

（`Δ̄` 是各节点相对本轮共同起点 `base` 的加权平均增量。Σω=1 时
`base + Σω(Wᵢ - base)` 恒等于 `Σω·Wᵢ`，所以 **FedAvg 就是 DiLoCo 在 β=0、η=1 时的特例** ——
两者共用同一个「基准点 + 加权增量」骨架，这也是本仓库实现里能共用一段代码的原因。）

- 优点：外层动量让跨轮更新更平滑；配合「每轮本地步数很大（大 H）」时通信量降得非常多
- **实测（本仓库自检，2 节点 / 6 轮 / 每轮 10 步 / MLP 小模型）**：

  | 聚合方式 | 探针 loss |
  |---|---|
  | 初始（未训练） | 4.182 |
  | FedAvg | **2.824** |
  | DiLoCo（η=0.7, β=0.9） | 3.310 |

  **这个规模下 FedAvg 反而更好。** 原因不神秘：DiLoCo 的外层学习率 η<1 相当于给每轮更新
  打了折扣，而轮数只有 6、每轮本地只走 10 步，折扣的损失还没来得及被「更稳的外层轨迹」赚回来。
  DiLoCo 的收益前提是**大 H + 多轮 + 通信确实昂贵**，三者缺一不可。

- 结论：**默认用 FedAvg；DiLoCo 保留为可选项**，等接上更大的模型、把每轮本地步数拉大之后再复测。

### 1.3 异步 / 抗陈旧聚合 —— 🔜 计划（M-N2 的一部分）

节点按自己的节奏上报，主机平均「最近的 K 个更新」，慢的节点不阻塞别人。

- 为什么值得做：**手机是最典型的 straggler** —— 性能弱、还可能被切后台。
  现在同步模式下，手机卡住会让主机每轮白等到超时（默认 30s，第一轮 60s）。
- 代价：更新会带「陈旧度」（基于更老的全局权重算的），需要补偿权重，收敛略慢。
- 判断：**设备数少（2~3 台）时优先级不高**；等到 5 台以上或手机经常掉线时再做。

### 1.4 LoRA 增量交换 —— 🔜 计划（M-N4，最关键的通信优化）

只交换 LoRA 的 A/B 矩阵，参数量降 ~100 倍。

- 为什么关键：这是让**浏览器参与 0.5B~3B 微调**的前提。
  100M 参数全量 fp32 = 400MB/轮，上行 5Mbps 要 11 分钟，完全不可行；
  换成 LoRA 增量 ≈ 几 MB/轮 → 几十秒，可行。
- 代价：只能微调，不能从头预训练；需要模型支持 LoRA 结构。

### 1.5 梯度/权重压缩（top-k + 量化）—— 🔜 计划，与 1.4 叠加

SparseLoCo 式：top-1~3% + 2bit 量化，通信再降 ~97%。

- 与 LoRA 正交，可以叠加。
- 注意：压缩会引入偏差，需要误差反馈（error feedback）才不掉精度。

### 1.6 分层 / 树形聚合 —— ⏸ 需要时再做

多层聚合，避免单点主机带宽成为瓶颈。自己几台设备用不上。

### 1.7 弹性成员 —— ✅ 已部分实现

主机每轮开头重发一次任务分配，迟到的节点从下一轮自动加入；掉线只跳过不阻塞。
（这条不是算法优化，但对「手机随时进来」的体验影响最大。）

## 2. 选型结论

### 现在就做（已做）

| 项 | 状态 |
|---|---|
| 数据并行 + 低频同步联邦（星形） | ✅ 已实现并验证 |
| 聚合骨架统一（base + 加权增量），FedAvg / DiLoCo 可切 | ✅ 已实现并单测 |
| 弹性成员：每轮重发分配、迟到者下一轮加入、掉线不阻塞 | ✅ 已实现 |
| 权重帧二进制传输 + 摘要校验 | ✅ 已实现 |

### 有条件再做（按触发条件）

| 项 | 触发条件 |
|---|---|
| 异步 / 抗陈旧聚合 | 设备 ≥5 台，或手机经常被切后台 |
| LoRA 增量交换 | 模型 >100M 参数（接上 WebGPU tiny-GPT 之后的第一步） |
| top-k + 量化压缩 | 单轮通信超过 ~10MB，或跨公网 |
| 分层聚合 | 单主机上行带宽成为瓶颈（约 10 台以上） |

### 明确不做

| 项 | 原因 |
|---|---|
| 张量并行 / 流水线并行 | 要求 NVLink 级互联，WiFi 上通信会吃掉全部收益 |
| 每步同步的普通数据并行 | 延迟敏感，浏览器网络做不到 |
| 专家并行 / MoE 路由 | 通信频率太高 |
| 拜占庭鲁棒聚合（Krum 等） | 用户已明确「都是自己的设备」，威胁模型不成立 |

---

## 3. 一句话推荐

**主体选「数据并行 + 低频同步联邦」，聚合用 FedAvg（当前规模实测最优），
弹性成员优先于算法优化，等模型变大再上 LoRA + 压缩。**

真正决定这套东西好不好用的，不是聚合算法有多花哨，而是：
**手机能不能随手进来、一轮能不能在几十秒内跑完、通信量是不是真的压得下去。**
