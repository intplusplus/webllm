# 性能实测记录

本文件记录解码路径优化的全部实测数据与结论。所有数据来自本项目的自检页
（`npm run dev` 后自动运行）与 timestamp-query 逐 pass 剖析
（自检项「M5 解码瓶颈剖析」），设备为 AMD GCN-5 核显（Vega APU，共享内存）。

## 1. 测量方法论（重要）

- **核显 + 浏览器的单次测量方差可达 ±30%**（同代码的 tiny-gpt 训练路径
  实测从 28723 漂到 23167 tokens/s）。单点数字只能当参考。
- **结论必须用同环境 A/B 交替验证**：git checkout 来回切换两个版本，
  让 Vite HMR 触发自检重跑，每轮间隔内环境漂移远小于两版差异。
- 干扰源排查：另一浏览器实例并行跑自检时，两条独立路径的吞吐会**同步精确
  减半**（资源对半分），以此可判定数字被污染。
- 工程坑：`encoder.finish()` 之后不能再编码 `resolveQuerySet`；
  Vite dev server 长时间运行后模块图可能不刷新（页面跑不到新注册的测试项），
  需重启 server。

## 3. CommandBatch 的 A/B 交替验证

同环境来回切换 974dd14（batch）↔ 1cbee4d（batch 前）：

| 轮次 | batch 前解码 | batch 后解码 | batch 前 prefill | batch 后 prefill |
|---|---|---|---|---|
| 1 | 6.51 t/s | 10.35 t/s | 553ms | 423ms |
| 2 | 8.98 t/s | 10.09 t/s | 462ms | 391ms |

- 解码均值 7.75 → 10.22 t/s（**+32%**），prefill **-20%**，两轮方向一致
- 对照组（加载耗时，不走 batch）漂移仅 9%，远小于提升幅度
- 机制：dispatch() 每次独立 encoder+submit 实测 ~110µs/次，解码一步 ~360 次
  dispatch ≈ 40ms 纯 CPU 开销；合并后每步仅 1 次 submit

## 4. 逐 pass 剖析之一（S≤8 时代，commit d11390a）

wall=118.5ms/步，pass=291，GPU 累计 103.5ms（87%），空隙 15.0ms（13%）。

| 投影 | GPU 总耗时 | workgroup 数 | 等效带宽 |
|---|---|---|---|
| gate/up | 42.9ms | 38 | 9.7 GB/s |
| down | 36.3ms | 32 | 5.8 GB/s |
| lm_head | 14.8ms | **594** | **18.4 GB/s ≈ 峰值** |
| q/k/v | 4.7ms | 8 | 10.5 GB/s |
| o | 3.2ms | 32 | 12 GB/s |
| 非 GEMV（norm/rope/attn/add/silu） | ~2ms | — | — |

**关键发现（推翻当时"barrier 开销"的推测）**：空隙仅占 13%；lm_head 以 594 wg
跑出接近峰值 20.2 GB/s 的带宽，而 32~38 wg 的投影只有一半 ——
**这块核显需要数百 workgroup 才能饱和带宽**。

## 5. 逐 pass 剖析之二（S≤64，目标 256 wg，commit c456a6e）

wall=110.3ms/步，pass=531，GPU 累计 95.2ms（86%），空隙 15.1ms（14%）。

| 投影 | 旧 GPU ms | 新 GPU ms | 旧带宽 | 新带宽 | wg 变化 |
|---|---|---|---|---|---|
| down | 36.3 | 30.5 | 5.8 | 6.9 GB/s | 32→256 |
| gate+up | 42.9 | 39.1 | 9.7 | 10.7 GB/s | 38→304 |
| q+o | 7.9 | ~5.2 | ~11 | ~14.7 GB/s | 32→256 |
| lm_head（对照） | 14.4 | 14.4 | 18.9 | 18.9 GB/s | 594 不变 |
| **GEMV 合计** | **101.9** | **90.2（-11%）** | **9.65** | **11.0 GB/s** | — |

## 6. 已确认的事实与推论

1. **workgroup 数与 GEMV 带宽近似线性**（594wg→18.9 / 256wg→6.9 /
   304wg→10.7）。当前 256 wg 目标仍只有峰值带宽的 1/3~2/3。
2. **K=896 的投影在 S 维度封顶 256 wg**：896/128=7（奇数），u32 对齐要求
   K/S 为偶数，S 无法取 128。突破需 64 线程/workgroup 的 kernel 变体
   （N=896 的 wgN 从 4 升到 14，×64 段 = 896 wg）。
3. **down_proj（K=4864）可直接 S=128 → 512 wg**（4864/128=38，偶数），
   是下一个单点验证实验。
4. **空隙 ~15ms/步**（531 pass × ~28µs）是第二瓶颈。方向：合并无冲突的
   相邻 pass、add+rmsnorm kernel 融合（同时省 2 pass/层与 2 次 M×C 往返）。
5. **理论天花板**：GEMV 全部跑到 18.9 GB/s ≈ 52ms + 空隙 15ms ≈ 67ms/步
   ≈ **15 t/s**（当前 942MiB f16 权重每步全量流式读取的前提下）。
6. 曾存在 **split→reduce 同 pass RAW race**（reduce 读 split 写的 partial，
   同一 pass 内 dispatch 间无内存屏障，规范上未定义行为；此前对拍通过
   仅因实现恰好串行）。已在 c456a6e 修复：split 后显式 passBreak，
   且每个 split gemm 恒占 2 个 pass（布局确定性 +4% 开销）。

## 7. M6 后训练管线实测（2026-10-06，commit 392f893）

tiny-GPT（2 层 / 64d / 33 词表字符级）上的三段训练栈，全部浏览器端：

### SFT（指令微调）

- 任务：Reverse / Sort（3 字符输入，512 训练样本，1500 步，lr 0.01）
- **loss 3.500 → 0.058**（曲线 0.500 → 0.187 → 0.126 → 0.058）
- 训练集贪心生成 **8/8** 正确；held-out 泛化 **7/8**
- 机制：`ce_softmax_bwd` 增加逐行 loss 权重（w=0 即 mask），loss 只计 completion

调试过程中的三个失败模式（对复现类似管线有参考价值）：

1. 64 样本 500 步：train loss <0.2 但 held-out 0/8 —— 样本太少在背题不泛化
2. 采样代码写成 `Array.from(8, () => sin(...))`（回调没看 index）——
   每 batch 8 条全是同一条样本，loss 完全不收敛（3.49→3.19）
3. 可变长度 3~6 字符任务对 2 层 64d 模型太难：loss 卡 0.5 边缘、生成 3/4；
   **输入固定 3 字符降难度后立即全过** —— 自检的断言对象应是「机制正确」
   （训练集正确率）而非「泛化能力」（受模型规模限制）

### IndexedDB checkpoint

- 往返：保存 → 加载 → logits **maxDiff=0**（逐位一致）
- 恢复优化器状态后继续 20 步：loss 0.0186 → 0.0022，无回弹
  （AdamW bias correction 依赖步数恢复，setStepCount 必不可少）

### DPO（偏好对齐）

- 配方：冻结 TinyGpt 作 reference；β=0.5，lr 1e-3，120 步，每步 4 对
- 标量 loss 的梯度折算成逐行 CE 权重（chosen +β(1-σ(z))/(K·N)、
  rejected -β(1-σ(z))/(K·N)），chosen/rejected 拼批一次反向
- **margin 0.137 → 4.888**（末值 5.126 nats），SFT 生成能力保持 4/4

### 全量自检

44 项全 PASS（含 M6-1 SFT / M6-2 checkpoint / M6-3 DPO 三个新项）。
