# 公共训练网络 · 产品与技术规划

> 状态：v0.1（讨论稿） · 对应代码：`src/fed/`（联邦联训核心）+ `fed.html`（Demo）
> 本文是后续共同讨论的基线。**凡标注「待定」或「开放问题」的地方，是我需要你拍板的**。
> 本文**合并了此前一轮规划调研的结论**（去中心化训练 2026 格局、验证手段分级、
> 通信压缩算法箱、治理原则），那些结论散落在对话里、磁盘上没有成文，已一并收进本文。

## 0. 一句话定位

**LLM 应当是公共产品**。我们要做的不是一个模型，而是一套**开箱即用的公共训练网络**：
任何人打开网页就能把自己的设备接进来，用别人的数据/算力一起训练模型，
训练出来的模型与数据、评测、推理（harness）全部公开可复现。

技术上的最小内核是：**浏览器 + P2P + 联邦训练 + 可信账本**。
产品上的最小内核是：**一个「训练房间」——发布任务、扫码加入、看曲线、拿模型**。

## 1. 为什么这个方向成立（以及不成立的地方）

### 1.1 成立的部分

| 判断 | 依据 |
|---|---|
| 微调需求远大于预训练需求 | 垂直场景（法律、医疗、教育、方言、企业知识库）要的是「小而专」的模型，不是又一个基座 |
| 中小企业买不起、也不会用 GPU 集群 | 一张 4090 云租一个月 ≈ 数千元，且要人搭环境；「打开网页就能微调」是真空地带 |
| 数据不能出内网 ≠ 不能参与训练 | 联邦训练让原始数据留在本地，只交换梯度/权重 |
| 长尾闲置算力巨大 | 家用显卡 + 公司闲置机器 + 手机，合起来远超任何单一大厂集群的**可用性**上限（虽然单点弱） |
| 浏览器是唯一「零安装」的交付形态 | 不需要 Docker、不需要 CUDA、不需要 Linux |

### 1.2 不成立 / 必须承认的部分

**浏览器训不了大模型。这是物理约束，不是工程问题。**

| 模型规模 | 浏览器能做什么 | 现实判断 |
|---|---|---|
| < 100M 参数 | **完整训练**（含从头预训练） | ✅ 可行 —— 本项目已有先例：WebGPU 从零实现 tiny-GPT 全流程 |
| 0.5B ~ 3B | 只能做 **LoRA / QLoRA 微调**，且要 WebGPU fp16 + 2GB 显存顶 | ⚠️ 可行但紧；手机基本没戏 |
| 7B ~ 70B | 只能贡献**数据、标注、评测** | ❌ 训练必须放到有真实 GPU 的节点 |

所以架构上必须**从一开始就把「节点」做成分级**的：
浏览器节点（长尾、小模型/微调）+ 重型节点（有 GPU 的机器，同一套协议接入）。

只做「浏览器训大模型」是空中楼阁；做「统一协议下的分级算力网络 + 公共模型仓库」是成立的。

## 2. 产品形态：不是「一个模型」，是「三层结构」

你说的「公共模型并不是指一个模型，我的模糊想法可能是公共的 HuggingFace」——
我把它具体化为三层，这是整个产品的骨架：

```
┌─────────────────────────────────────────────────────────┐
│  L3  公共模型仓库（Public Hub）                          │
│      模型卡 / 权重 / 数据指纹 / 评测榜单 / 派生关系图      │
│      —— 这才是「公共的 HuggingFace」那一层                │
├─────────────────────────────────────────────────────────┤
│  L2  训练房间（Room）                                    │
│      一次任务 = 一个房间：清单(宪法) + 成员 + 轮次 + 账本  │
│      —— 用户实际操作的界面就是它                          │
├─────────────────────────────────────────────────────────┤
│  L1  协议与网络（Protocol）                              │
│      P2P 传输 / 权重帧格式 / 聚合算法 / 信任层            │
│      —— 无中心、可自建、可共治                            │
└─────────────────────────────────────────────────────────┘
```

**关键设计取舍：房间是「任务级」的，不是「模型级」的。**
同一个模型可以有多个房间在跑（不同数据、不同阶段），
每个房间产出一个 checkpoint，这些 checkpoint 汇入 L3 形成派生关系图。
这才符合「公共 HuggingFace」的直觉：**模型是长期积累的产物，房间是一次协作的现场。**

### 2.1 三种参与者

| 角色 | 贡献 | 门槛 |
|---|---|---|
| 任务发布者 | 数据 / 算力 / 目标 | 填个表单 |
| 计算节点 | 算力 + 自有数据 | 打开网页，输房间号 |
| 验证节点 | 抽查、复算、评测 | 后续开放 |

「开箱即可」的具体标准（你的要求 4）：
**手机扫码 → 输房间号 → 点「加入」→ 自动开始训。不需要注册、不需要装东西、不需要理解联邦学习。**

## 3. 技术架构

### 3.1 训练引擎抽象（已经落地）

这是整个系统最重要的解耦点：**只要能把模型表达成一组扁平命名的 f32 参数**，
就能接入网络，不关心它是 WebGPU 还是纯 JS、是预训练还是 LoRA。

```ts
interface TrainEngine {
  spec: ModelSpec;                          // 写进房间清单，全网一致
  paramNames(): string[];                   // 如 ['emb','w1','b1','w2','b2']
  getWeights(): NamedWeights;               // 可直接上网传输
  setWeights(w: NamedWeights): void;
  trainBatch(ids, batchSize, lr): Promise<{loss, tokens}>;
  evalAt(ids, start, count): Promise<number>;   // 确定性，可跨节点对拍
  sample(prefix, n): Promise<number[]>;         // 推理
}
```

全部方法 `async` —— 因为 WebGPU 引擎的 forward/backward 需要 `await` 回读，
接口从一开始就按异步设计，避免以后推倒重来。

**当前有两个引擎位置：**

| 引擎 | 状态 | 用途 |
|---|---|---|
| `mlp`（纯 JS 字符级 LM） | ✅ 已实现 | Demo 默认。任何设备可跑，**局域网 http 也能跑**（不依赖 WebGPU 的安全上下文要求） |
| `gpu-tinygpt` | 接口预留 | 把工程内已有的 WebGPU `Trainer` 适配进来。需要 HTTPS 或本机访问 |

> 为什么 Demo 默认用纯 JS 而不是现成的 WebGPU 引擎？因为 **WebGPU 要求安全上下文**，
> 手机通过 `http://192.168.x.x` 访问时拿不到 WebGPU。要让「同一 WiFi 下手机就能参与」
> 这个体验成立，默认引擎必须是零依赖的。这是产品体验倒逼的技术选择。

### 3.2 通信层（已经落地）

```
     信令服务器（无状态，零依赖，可自建）
        │  只做 SDP / ICE 牵线，不碰任何训练数据
        │
   ┌────┴────┐
   │  Host   │  房间创建者 = 汇聚节点（开轮、校验、FedAvg、广播）
   └─┬──┬──┬─┘
     │  │  │     WebRTC DataChannel（网状，直连）
   ┌─┘  │  └─┐
 Peer  Peer  Peer   各节点本地训练，只把权重给 Host
```

- **控制帧 = JSON 字符串，权重帧 = ArrayBuffer**，同一条 DataChannel，
  RTCDataChannel 本身有序可靠，所以元信息可以随权重同帧下发，不会错配。
- 权重帧格式：`[u32 魔数][u32 头长度][头 JSON][f32 载荷]`，头里带 FNV-1a 摘要。
- 实测：Demo 模型 13,521 参数，一帧 **54,300 字节** —— 一轮交换不到 60KB，
  在局域网上是毫秒级，在 4G 上也完全可行。
- 信令服务器刻意**不引入 `ws` 依赖**，用 Node 原生 `http`+`crypto` 手写 RFC 6455。
  理由：约 200 行、可全文审计、离线可用 —— 这对「公共产品」的信任定位是加分项。
  （这条链路有独立自检：`npm run verify:signal`，7 项全过，含跨 64KB 长帧。）

### 3.3 聚合策略演进

| 阶段 | 方案 | 解决的问题 |
|---|---|---|
| v0（已实现） | 同步 FedAvg，按样本数加权，星形拓扑 | 跑通闭环 |
| v1 | 分层聚合（树形）、断线续训、节点掉队只跳过不阻塞 | 规模与稳定性 |
| v2 | 异步 FedAvg / 带延迟补偿（staleness-aware） | 节点算力差异大（手机 vs 4090） |
| v3 | 参数高效：只交换 LoRA 增量（体积 ÷100） | 让 0.5B~3B 模型在浏览器可参与 |
| v4 | 梯度压缩（量化 / top-k / 误差反馈） | 移动网络带宽 |

**v3 是让「大模型也能考虑」真正落地的关键一步**（你的要求 5）：
LoRA 增量只有原模型的百分之几，交换量从 MB 级降到几十 KB，
浏览器节点的价值立刻从「只能玩小模型」提升到「能参与 7B 微调」。

#### 3.3.1 算法箱：低通信联邦训练是这类系统的正解

上面的 v1–v4 其实是同一件事的四个侧面。业界已经收敛到一条清晰路线，值得直接用：

| 算法 | 一句话 | 对我们的价值 |
|---|---|---|
| **DiLoCo / OpenDiLoCo** | 外层低频同步（每几百步交换一次），内层各节点独立跑多个 local step | 通信量降 2 个数量级；**现有 `src/train/trainer.ts` 可直接当内层优化器复用** |
| **Streaming DiLoCo** | 外层梯度用流式方式聚合，容忍节点掉队 | 解决「手机算力弱、经常掉线」 |
| **SparseLoCo** | 梯度 top-k 1–3% + 2bit 量化 | 通信再降 ~97%，实测已用在 72B 级 |
| **DisTrO** | 训练器间通信量降 1000–10000× | 超长距离 WAN 场景 |

> 这意味着：**别再从零设计聚合算法，直接站在 DiLoCo 系列的肩膀上。**
> v0 的同步 FedAvg 是「为了先跑通闭环」的教学版，M-N2 就应该切到 DiLoCo。

#### 3.3.2 一个反直觉但关键的结论：规模由**上传带宽**倒推，不是显存

消费级网络的**上行**通常只有下行的 1/10。所以「浏览器节点能训多大的模型」，
瓶颈几乎从来不是显存，而是**一轮同步要上传多少字节**。

举例：100M 参数 fp32 全量上传 = 400MB/轮 → 上行 5Mbps 要 11 分钟，完全不可行；
换成 SparseLoCo 式 top-1% + 2bit ≈ 1MB/轮 → 十几秒，可行。

**结论：浏览器节点的公共前训练规模应锁定在 30M–300M 参数区间**
（这个量级上，LoRA/全量微调与小型预训练都成立，且通信量可控）。
要上更大规模，必须靠 §4 的验证层 + §3.3.1 的压缩算法，而不是靠堆浏览器。

### 3.4 数据层：任务数据 + 用户数据（你的要求 4）

两种来源并存，这是我设计上的一个明确立场：

```
任务提供的数据 ──┬─→ 按房间分片切给各节点（连续分片，各节点看到不同文本区间）
                │
用户贡献的数据 ──┴─→ 过滤到房间字符表 → 并入自己的本地训练池 → 只参与本地训练，不上传
```

- **不强制上传数据**：用户贡献的数据永远留在本地，出去的只有权重。
- **贡献可记账**：贡献了多少字符、参与了多少轮，都进账本（用于后续激励/署名）。
- **字符表必须全网一致**：否则各节点 logits 维度不同、权重无法聚合。
  所以字符表由房间语料唯一确定并写进清单指纹。这是硬约束，值得写进文档而不是藏在代码里。

### 3.5 Harness（你的要求：包含 harness）

「harness」我理解为**让模型能被评测、复现、使用的整套配套**。分层如下：

| 组件 | 现状 | 说明 |
|---|---|---|
| 数据 | ✅ `src/fed/corpus.ts` | 内置语料 + 贡献数据 + 分片 + 指纹 |
| 训练 | ✅ `src/fed/engine.ts` + 工程内 WebGPU Trainer | 预训练 / SFT / DPO 都已存在 |
| 评测 | ✅ 共识探针 + 探针 loss | 目前是语言建模 loss；需扩展为标准评测集 |
| 推理 | ✅ `sample()` 贪心解码 | 后续接 KV cache / 批量 |
| 模型卡 | ✅ `ModelCard`（含账本、贡献者、摘要） | 一次训练就是一张可下载的卡 |
| 服务化 | ❌ 未做 | 需要一个「把公共模型一键跑成 API」的形态 |
| 复现 | ✅ 清单指纹 + 固定种子 + 确定性评估 | 同清单 → 同模型 |

### 3.6 小模型 vs 大模型的差异化路径（你的要求 5）

```
小模型（<100M）      浏览器完整训练     ✅ 本 Demo 验证的路
中模型（0.5B~3B）    浏览器 LoRA 微调   ⚠️ 需 WebGPU + LoRA 交换
大模型（7B+）        只贡献数据/评测    重型节点训练，浏览器参与标注与评测
```

调度上统一：房间清单里写 `model.engine` 与 `model.tier`，
网络自动决定「哪些节点能接这个活」，够格的才被分配分片。

## 4. 信任层（你说的「先做信任训练」）

> **我对「信任训练」的理解**：先把「多个互不认识的节点，凭什么相信彼此提交的东西」
> 这件事做扎实，其余（市场、激励、规模）先放后面。
> 如果理解偏了，这是第一个要纠正的地方。

### 4.1 威胁模型

| 攻击 | 具体表现 | v0 能防吗 |
|---|---|---|
| 白嫖 | 不上报权重，只白拿全局模型 | ✅ 账本标记 `timeout`，不计贡献 |
| 谎报 | 上报权重但伪造 loss 数字 | ✅ 探针复算，抓得到 |
| 掉包 | 提交与训练无关的权重（投毒） | ⚠️ 只能靠探针 loss 异常间接发现 |
| 数据投毒 | 用恶意数据训出有害更新 | ❌ 未做（需异常检测/鲁棒聚合） |
| 女巫 | 一个人开 N 个假节点刷贡献 | ❌ 未做（需身份成本 / 质押） |
| 隐私反推 | 从梯度反推原始数据 | ❌ 未做（需 DP + 梯度裁剪） |

**v0 只解决前两项 + 留痕。这是我刻意划的界线 —— 不假装它是完整的信任层。**

### 4.2 v0 已实现（本次 Demo 里可以现场看到）

1. **清单指纹**：房间的模型规格、语料指纹、超参、分片数打成一个指纹。
   所有节点对「训什么、用什么数据」达成一致，事后可复核。
   节点侧还会拿本地语料重算指纹并告警 —— 数据不一致会当场亮红。
2. **共识探针**：房间固定一段 1024 字符的数据窗口，所有节点都能读到。
   每个节点上报自己权重在该窗口上的 loss；
   主机**用提交的权重自己复算一遍**，差值超过阈值 → 判为异常并剔除本轮聚合。
   这是真正的交叉验证，不是"信任声明"。
3. **贡献账本**：每节点每轮的样本数、token 数、探针 loss、Δ 范数、聚合份额、裁决，全部留痕，
   随模型卡一起下载。
4. **可复现**：固定种子 + 确定性评估（`evalAt` 无随机性）。
   同清单、同贡献顺序 → 逐位相同的全局模型。

### 4.3 验证手段分级（这是命门）

**第一原则：验证先于激励。** 一个默认不可验证的任务，不进激励层 ——
否则激励会立刻变成攻击面（作弊的收益 > 老老实实算的收益）。

| 手段 | 强度 | 成本 | 抓什么 | 阶段 |
|---|---|---|---|---|
| 确定性执行契约（固定种子 + 确定性评估） | 弱 | 极低 | 环境漂移、配置不一致 | ✅ v0 |
| **共识探针复算** | 中 | 低 | 谎报 loss、掉包权重 | ✅ v0 |
| 贡献账本留痕 | — | 极低 | 事后审计、声誉基础 | ✅ v0 |
| 清单/数据版本签名与哈希链 | 中 | 低 | 篡改任务定义、偷换数据 | v1 |
| 抽样重算（随机挑节点复算他人提交） | 中高 | 中 | 大范围造假 | v2 |
| k-of-n 冗余执行 | 高 | n 倍算力 | 关键验收环节 | v2 |
| 鲁棒聚合（Krum / Trimmed-mean） | 中高 | 中 | 数据投毒、拜占庭节点 | v2 |
| 质押 + 罚没 | 经济层 | — | 提高作弊成本 | v2 |
| 乐观挑战 + 欺诈证明 | 高 | 低（无人作弊时几乎免费） | 长期正解 | v3 |
| 激活承诺（TOPLOC 式） | 中 | 低 | 证明「确实跑过前向」 | v3 |
| 防女巫（身份成本 / PoW 门槛） | — | — | 一人开 N 个假节点 | v3 |
| 隐私（DP-SGD + 梯度裁剪） | — | 略损精度 | 从梯度反推原始数据 | v3 |
| zkML 密码学证明 | 最高 | 极高 | 前沿，暂不实用 | v4 |

> **⚠ 一个必须避开的陷阱（前次调研的关键结论）**
> 跨设备的 WebGPU 浮点计算**不保证逐位一致**（不同 GPU 的 FMA/归约顺序不同）。
> 因此验证**不能靠哈希对拍**，必须：① 用容差比较；② 用 LSH 类概率承诺代替精确哈希。
>
> 这条直接约束本仓库：Demo 的共识探针用的是 `1e-3` 相对容差，正是为跨设备差异留的余量。
> 而自检里「同 seed 初始权重逐位一致」这条断言之所以成立，是因为两端跑的是**同一份纯 JS
> 实现、同一条浮点路径**。**M-N1 接入 WebGPU 引擎后，这条断言必须降级成容差断言 ——
> 这是 M-N1 的必改项，不是可选项。**

**另一个必须坚持的原则：摘要算法在文档和 UI 里都要标清「非密码学安全」。**
把 v0 的边界说清楚，比吹成完整的信任层更能积累信任。

### 4.4 分水岭

**先跑通「跨网任务 → 验证 → 联邦微调」这三步，后面的激励与治理才有意义。**
在这三步跑通之前，任何代币/激励设计都是空中楼阁 —— 因为没有可信的结算依据。

## 5. 与现有方案的对比

| 方案 | 它是什么 | 我们的差异 |
|---|---|---|
| HuggingFace | 模型/数据集仓库 | 我们多了「协作训练现场」（房间）与公共算力 |
| WebLLM / transformers.js | 浏览器**推理** | 我们是浏览器**训练**（已有从零实现的前向+反向+优化器） |
| FedML / FATE | 企业级联邦学习框架 | 重部署、要装环境；我们是零安装网页 |
| Bittensor / Gensyn | 币驱动的算力网络 | 门槛高、金融化；我们走公共品路线，不发币 |
| BOINC / Folding@home | 志愿者计算 | 非 ML 原生，无模型仓库与 harness |
| 各类众包标注平台 | 人力标注 | 我们不只标注，能真的训 |

**真正的空白是「零安装 + 浏览器训练 + 公共模型仓库」这个组合。** 目前没有人把三者打通。

### 5.1 2026 年的具体格局（前次调研结论）

去中心化训练**已经跨过「可信」门槛**，不再是纯概念：

| 项目 | 规模 | 关键机制 |
|---|---|---|
| Prime Intellect INTELLECT-1 / 2 | 10B / 32B | OpenDiLoCo |
| Nous Research Psyche / Consilience | 40B | Solana 协调 |
| Pluralis Node0 | 7.5B | 模型并行，1642 GPU |
| Gensyn | — | 乐观执行 + 欺诈证明（Verde） |
| Templar Covenant | 72B | Bittensor 协调，SparseLoCo，MMLU 67.1 |

**但有一个必须正视的「诚实天花板」**：Prime Intellect 的旗舰 INTELLECT-3（106B MoE）
最终仍然是在**中心化的 512×H200 集群**上训出来的；>100B 稠密模型在广域网上做预训练
至今没有被证明可行。

**所以战略上不要与之正面竞争前沿规模。** 我们的位置是：
**浏览器长尾 + 零安装体验 + 小模型/微调的公共网络** —— 这恰恰是大玩家不做的市场。

### 5.2 治理：公共产品需要的是治理，不是口号

「公共产品」在经济学上有一整套成熟答案（Ostrom 的公共资源治理八原则），
而不是「免费开放」四个字就够了。对我们最有用的几条：

1. **边界清晰**：谁能加入哪个房间、贡献怎么算，规则必须显式且可查
2. **规则由参与者共同制定**：不是平台单方面定，否则就是伪公共
3. **分级制裁**：先警告、再降权、最后剔除 —— 而不是一上来就封禁
4. **冲突解决机制低成本可及**：申诉与复核通道
5. **对组织权的最低位承认**：允许社区自建房间与自建信令
6. **嵌套式治理**：房间 / 社区 / 全网三层，各自自治

这些会体现在 M-N5（任务市场）与 M-N6（公共 Hub）的设计里，而不是事后补一层「治理模块」。

## 6. 市场

### 6.1 需求侧（谁会付钱/谁会来）

1. **垂直行业的小模型微调**：法律、医疗、教育、电商客服、方言/少数民族语言。
   特征是「数据敏感 + 预算有限 + 只要小模型」。
2. **企业内网**：数据不能出内网 → 私有房间部署（这是最清晰的付费点）。
3. **研究/教学**：低成本做联邦学习实验，一次房间就是一次实验。
4. **长尾开发者**：想训个小模型玩，但不想配环境。

### 6.2 供给侧

- 浏览器长尾（任何人，开机即参与）
- 闲置 GPU（公司夜间空转、家用显卡、网吧）
- 关键：**供给侧不缺算力，缺的是「可信地组织算力」** —— 这也是为什么信任层必须先做。

### 6.3 商业模式（公共品如何活下去）

> 公共品 ≠ 不能有收入。关键是**核心协议与公共仓库保持中立与免费**，
> 收入来自「托管与专业服务」，而不是「抽算力税」。

| 收入来源 | 说明 | 是否伤害公共性 |
|---|---|---|
| 企业私有房间（私有部署 + 支持） | 最清晰，客单价高 | 否 |
| 托管信令 / TURN 中继（SaaS） | 公共网络免费额度 + 企业配额 | 否 |
| 认证与审计服务 | 给模型出「训练过程可复现」的报告 | 否 |
| 赠款 / 基金会 / 高校合作 | 公共品常见的可持续路径 | 否 |
| 算力信用记账（**不发币**） | 贡献可累积、可兑换服务 | 需谨慎设计 |

**明确不做**：不发币、不炒算力、不把公共模型锁在付费墙后。

### 6.4 冷启动

网络效应的冷启动是最大难题。我的判断是**不要一上来做开放网络**，而要：
1. 先做「单机可用」的工具（我打开网页就能训我的模型）—— 本身就有价值
2. 再加「两人可用」（我和我的手机，本 Demo 就是这一步）
3. 再做「熟人房间」（同一个团队/微信群）
4. 最后才是「开放网络」

**每一步都独立有价值，不依赖下一步成功。** 这是反脆弱的关键。

## 7. 路线图

| 里程碑 | 内容 | 判定标准 | 状态 |
|---|---|---|---|
| **M-N0** | 协议 + 最小房间 + 信任 v0 | PC 与手机同 WiFi 完整训完一个小模型，账本可下载 | ✅ **本次已落地** |
| M-N1 | 引擎分级：WebGPU tiny-GPT 接入 + 采样/推理复用 | 同一个房间能选 GPU 引擎，探针 loss 曲线一致 | 待做 |
| M-N2 | 拓扑与鲁棒性：**切到 DiLoCo 式低通信联邦**、分层聚合、断线续训、掉队不阻塞 | 3 节点中拔掉 1 个，训练不中断且账本正确标记 | 待做 |
| M-N3 | 信任 v1：SHA-256 + 身份签名 + 清单签名 | 篡改任一权重帧都能被拒绝并溯源 | 待做 |
| M-N4 | LoRA 引擎：浏览器参与 0.5B~3B 微调；引入 SparseLoCo 式 top-k + 量化压缩 | 交换量降到 100KB 以内，微调效果可评测 | 待做 |
| M-N5 | 任务市场：发布/发现/加入/数据贡献/榜单 | 陌生人能独立完成一次完整协作 | 待做 |
| M-N6 | 公共 Hub：模型仓库 + 派生关系图 + 评测榜 | 房间产物自动汇入公共仓库 | 待做 |
| M-N7 | 信任 v2/v3：鲁棒聚合、质押惩罚、DP | 能抵抗一次有预谋的投毒 | 待做 |

### M-N0 的实际验收结果（本次已跑）

无头自检 `npm run verify:fed`，16/16 通过，语料用真实的 Tiny Shakespeare（1,115,394 字符）：

```
初始模型探针 loss = 4.182   （ln(65) = 4.174，符合未训练模型的预期）
联邦训练 6 轮后     = 2.824   （降 1.357）
单节点独训同总步数   = 2.979   （A 2.908 / B 3.051）
→ 联邦 2.824 < 独训均值 2.979   ← 联邦确实优于各自独训
```

其它验证：权重帧 54,300 字节逐位无损往返、篡改 1 字节即被摘要拦下、
同 seed 初始权重逐位一致、探针评估两次结果完全相等、分片拼回等于原文。
信令链路 `npm run verify:signal` 7/7 通过。

## 8. 风险与对策

| 风险 | 严重度 | 对策 |
|---|---|---|
| **合规**：数据/模型内容、跨境、生成内容备案 | 高 | 私有房间优先；公共房间加内容策略与举报机制；境内节点/信令自建 |
| **经济不可持续** | 高 | 收入来自托管服务而非算力税；避免币化；先做有独立价值的单机工具 |
| **恶意节点投毒** | 中高 | 鲁棒聚合 + 抽查 + 质押；v0 阶段不接入陌生人网络 |
| **隐私反推** | 中高 | 梯度裁剪 + DP-SGD；对敏感场景只允许私有房间 |
| 浏览器限制（后台节流、WebGPU 可用性、内存顶） | 中 | 已处理：训练循环不依赖 rAF；默认引擎不依赖 WebGPU |
| 冷启动失败 | 中 | 分四步走，每步独立有价值 |
| **过度承诺**（"浏览器训练大模型"） | 中 | 本文档第 1.2 节就是防线：明确分级，明确边界 |

## 9. 决策与开放问题

### 9.1 已定基调（前次调研已收敛，不必反复讨论）

| 结论 | 理由 |
|---|---|
| **不发币**，先做「签名贡献账本 + 不可转让声誉」 | 有真实结算刚需再上链（EVM L2 或 Solana），不自建 L1；不首发代币、不设固定通胀 |
| **验证先于激励** | 不可验证的任务不进激励层，否则激励即攻击面 |
| **不竞争前沿规模** | >100B 稠密在 WAN 上预训练未获证明；大玩家最终仍回中心化 |
| **浏览器公共预训练锁 30M–300M** | 规模由上行带宽倒推（§3.3.2），不是显存 |
| **通信优先用 DiLoCo 系列**，不从零设计 | OpenDiLoCo / SparseLoCo 已被 72B 级验证 |
| **跨设备浮点不可逐位一致** → 容差 + LSH 承诺 | 验证设计的硬约束（§4.3） |

### 9.2 需要你拍板

1. **「信任训练」我理解对了吗？** 我按「多方互信机制」来做（第 4 节）。
   如果你指的是别的（比如「先建立信任关系再训练」「trustless 训练」），这是首要修正点。
2. **开放网络还是熟人网络优先？** 我建议先熟人（同一个 WiFi / 同一个团队），
   把体验做扎实再开放。这直接决定 M-N5 的优先级。
3. **要不要先做「单机也爽」的形态？** 即：不联机也能在网页上训个自己的小模型。
   我强烈建议要 —— 它是冷启动的救命稻草，也让项目在没有网络效应时依然有人用。
4. **合规边界**：公共房间是否允许上传任意文本？还是只允许结构化/模板化数据？这会影响数据层设计。
5. **是否先把现成的 WebGPU 引擎（M-N1）接进来？** 它是这个工程已有的最强资产，
   接进来后 Demo 的「训练」才是真正意义上的 LLM（而不是 MLP 语言模型）。
   代价是需要 HTTPS 或本机访问，牺牲一点「手机开箱即用」；
   并且必须同步把「逐位一致」断言降级为容差断言（§4.3 的陷阱）。
