## 1. 定位

算子层是**唯一碰 GPU 的层**。它对外只暴露 `op` 契约，对内藏 WGSL 实现。
设计目标：**有界、可寻址、能力可查、可受信扩展**。

## 2. op 契约

```jsonc
{
  "op": "RMSNorm",
  "version": "1.0",                     // op 版本；进 specHash 的 opRef
  "props": { "dim": { "type": "int", "required": true }, "eps": { "default": 1e-5 } },
  "io": { "in": ["B","T","dim"], "out": ["B","T","dim"] },
  "caps": ["forward","vjp","jvp","perturbable"],
  "phase": ["train","prefill","decode"],
  "pure": true,
  "cost": { "flops": "6*B*T*dim", "mem": "O(B*T*dim)" },
  "writesReads": { "reads": ["weight"], "writes": ["act"] },   // arena 区段读写 → 自动 passBreak，见 §6
  "rng": { "counterScope": "sample", "shape": "B" },           // 仅需 RNG 的 op 才写，见 §6
  "impl": { "kind": "kernel", "entry": "kernels/norm/rmsnorm.wgsl" }
}
```

**规则**：
- `opRef := op.name + "@" + op.version` —— 同一名字不同版本是**不同 op**
  （`specHash` 因此把实现差异也纳入，避免"同名不同实"的静默错配）。
- `writesReads` 声明 op 读/写哪些 arena 区段（`weight`/`act`/`state`）；`plan()` 据此**自动插 passBreak**，
  把"同 pass 内禁 RAW/WAR/WAW"从人肉遵守变成机器计算（§6、06 §3）。
- `rng` 声明确定性 RNG 的 `counterScope`（与可选 `shape`）；`plan()` 为各 RNG op 分配**互不重叠**的
  counter 段（06 §5，INV-10）。不需要 RNG 的 op 不写此字段——`infer()` 据"全图是否有 rng 声明"判定
  `UNREPRODUCIBLE_RNG`（03 §5.2）。
- `impl` 除 `kind`/`entry` 外还带 **`codeHash`** 与 **`depVersions`**，二者**进 `specHash`**（03 §4.1，Marin 教训）。
- 契约中的 `io`/`caps`/`cost` 必须与实现**测试对齐**（P1 逐 op 对拍 + gradcheck）。
- 改实现不改契约 ⇒ 不算新 op（性能优化自由）；改契约 ⇒ 新版本。

## 3. 能力位完整定义（8 位）

| 位 | 定义（精确语义） | 需要策略 | 实现要求 |
|---|---|---|---|
| `forward` | `y = f(x;θ)` 可求值，fp32 确定性 | 全部 | 必需 |
| `vjp` | 给定 `ȳ` 可求 `x̄` 与 `θ̄`，满足 fp32 精度与确定性 | Backprop | 每参数唯一写者 + 规约（INV-1） |
| `jvp` | 给定 `ẋ` 可求 `ẏ` | Forward-mode | 输出维低时优先 |
| `logprob` | 对 `Dist` 输出 `log p(y)`，重参数化可微 | REINFORCE / VI | 支持 Gumbel/ST |
| `localGrad` | 可算**不依赖全局反向**的层内更新（如目标传播误差、对比度） | 局部规则/FF | 相位可控 |
| `perturbable` | 对 θ 加扰动 `θ+σδ` 后目标可重估；**无隐藏状态影响** | ES / SPSA | 扰动需可复现 RNG |
| `invertible` | 可由 `y` 重建 `x`（≤ 常数因子信息损失） | EqProp / flow | 相位 nudge/free |
| `nondiff` | **明确无任何梯度**；进入可微路径即 `CAPABILITY_MISSING` | 黑盒/离散/符号 | 需 `effects` 声明 |

### 3.1 能力位的动态查询（策略层怎么用）

```
strategy.requires ⊆ 图上所有节点的 caps   ⇒  相容
否则 infer() 报 CAPABILITY_MISSING，fix ∈ {
  switch-strategy(降级到要求更低的策略),
  insert-op(把 nondiff 节点换成带 vjp 的等价 op)
}
```

**降级不是失败**：这正是"手机跑 SPSA、PC 跑反传"的把柄——同一个 IR，
`plan()` 对不同设备问不同问题，得到不同策略。

## 4. defineOp：受信逃生门（INV-12）

WGSL 逃生门必须存在，但**必须改变性质**：

| | v2 的设想 | v3.1 的设计 |
|---|---|---|
| 谁能写 | 任何人 | **受信贡献者** |
| 何时进图 | 运行时字符串 | **构建期 / 版本发布期** |
| 分发给集群 | eval 一段字符串 | **代码哈希 + 签名**，随 manifest 校验 |
| 审核 | 无 | code review + 数值对拍 + gradcheck |

```
Contribution := { name, version, code (WGSL/JS), codeHash,
                  signature, reviewId, tests: [reference 对拍] }
```

**AI 起草的演进路径（★ 第三轮评审补水位）**：KernelBench（ICML 2025）证明 LLM
写 GPU kernel 已到"能编译、错不少、慢很多"的水位 ⇒ 本设计立场不变
（**对端只执行签名过的受信内核**，INV-12），但流程可分两段：

```
AI 起草（自由） ──► CPU reference 对拍 ──► 形式化契约检查 ──► 人类 review + 签名 ──► 进版本
       ↑                                                                          │
       └────────────────── 失败样本回流为 Skill（11 §3.4 经验层）◄─────────────────┘
```

即 AI 把"从零写 kernel"变成"改错 kernel"，但**进图的闸门仍是对拍 + 签名**。
这与 04 §6 的自主性分层同构：L4 执行 / L2 架构——kernel  correctness 属执行层，
可以无人值守迭代；specHash 进 manifest 属签订契约，必须人审。


**这条是联邦安全的地基**（见 10）：如果任意用户能向对端塞 WGSL 并执行，
"公共网络"就退化成"公共远程代码执行"。

## 5. 第一批算子清单（分层组织）

### 5.1 叶原语（无子节点，直接映射 kernel）

| 原语类 | op | 备注 |
|---|---|---|
| ① 变换 | `Matmul` `Einsum` `Conv2d` `Pool` `PatchEmbed` `RMSNorm` `LayerNorm` `GELU` `SiLU` `Softmax` `Embed` `Gather` `Scatter` `Reshape` `Transpose` `Concat` `Split` `Cast` `Quant` `Dequant` **`RoPE`** **`Attention`** | 现有 kernels 的包装 |
| ① 稳定化 | **`QKNorm`** **`ZLoss`** | 深层网络防 logits 爆炸，见 §5.3 |
| ① 损失 | **`CrossEntropy`** | 前向出标量、反向出 dlogits；`caps: [forward, vjp]`；与 `ZLoss` 同属损失侧 |
| ① 探针 | **`Probe`** | 统一能力/质量探针（11 §2.4 / 14 §7.2）；**effectful**，`phase: [free]` |
| ⑤ 随机 | `Sample`（重参数化/Gumbel） `Dist` `Discretize`（ST） | 需 RNG |
| ⑥ 循环 | `Scan`（解释档） `FusedScan`（融合档） `Solve`（ODE/定点/argmin） | `Solve` 需隐式 backward |
| ⑦ 交互 | `Env` `Tool` | **effectful** |

> **实现补注（2026-10-08 核对，src/ir/ops.ts）**：初版清单漏了三个**一等叶算子**——
> `RoPE`（`kernels/rope/rope.wgsl`）、`Attention`（`kernels/attention/attention.wgsl`）、
> `CrossEntropy`（`kernels/misc/ce_softmax_bwd.wgsl`）：三者都有**仓库内真实存在的 kernel** 且已注册进
> 注册表，属**清单缺口**，现补入。`Probe` 同理（其来源在 11 §2.4 / 14 §7.2，原只在后置文档出现）。
>
> **权重绑定的实现倒逼（src/ir/ops.ts:95）**：`Matmul` 契约新增 **`props.n`**（输出特征数）——
> 当权重经 `props.bind` 约定绑定、第二个操作数不在图里时，`infer()` 看不到它的形状，只能靠 `props.n`
> 推出输出 `[…, n]`。这是"实现倒逼设计"的一处细节：**被绑定的参数需在 props 里显式声明形状**。

### 5.3 来自前沿实证的两个稳定化算子（★ Marin）

Marin 32B 在 70k 步损失爆炸，重启与换优化器都失败，最终靠 **Qwen3 架构的 QK-Norm**
才稳定；冷却阶段另用 **Z-Loss** 正则防 logits 爆炸（14 §8.6）。
"8B（32 层）没问题，32B（64 层）就崩溃了"——这是"小规模有效、大规模崩溃"的
**第三个独立实证**（前两个：soft-MoE v2、ZGCM 的条件性结论）。

| op | 语义 | 契约 |
|---|---|---|
| `QKNorm` | 对 Q/K 做 RMSNorm，抑制注意力 logits 爆炸 | 可作为 `Attn.qkNorm: bool` 内嵌，或独立节点 |
| `ZLoss` | 对 log-sum-exp(logits) 加平方惩罚，防 logits 爆炸 | 损失侧正则，`caps: [vjp, jvp]` |

**由此产生的静态启发式**：`infer()` 应在**层数/宽度超阈值**时发出
`STABILITY_HINT`（warn 级）提示考虑 `QKNorm`——这是静态检查唯一能对
"训练会不会崩"说的话（仍然只是提示，不是保证；R-23 的边界不变）。

**MoE 的两个参数化**（同样来自 Marin）：

```
Moe.balance:       'aux-loss' | 'quantile-bias'
                   // quantile-bias：全局直方图 + per-expert bias，下一步生效、
                   // stop-grad ⇒ 无需辅助损失、不干扰主训练目标
Moe.capacityFactor: 1.15                // 超容 token 丢弃；明确的设计权衡
```

> **数量核对**：核心 op ≈ 29（叶）+ 14（组合）= 43 个**概念**，其中约 32 个需进
> AI 上下文。若超预算，把 `Fan/Residual`、`Map/Repeat` 合并同类项；
> **验收线 LANG-V1 用"概念数"而非"符号数"度量，防止钻空子**。
>
> **实现补注（2026-10-08 核对，src/ir/ops.ts）**：内置注册表实际落地 **47** 个 op
> （**34 叶 + 13 组合**，含后补的 `Probe`/`CrossEntropy`/`RoPE`/`Attention`）——
> 比初版估算多 4 个，差异主要在"① 变换"补 `RoPE/Attention` 与新增"① 损失/① 探针"两行。
> 概念数口径需与 04 语言层对齐 ★待定。

## 6. 内核约束 → 算子契约约束

| WebGPU 约束 | 对 op 的要求 |
|---|---|
| 单 kernel ≤ 4 bind group | op 实现必须经由 arena + offset 寻址，**不得按张量绑** |
| 无 fp32 atomicAdd | op 的 `vjp` 对参数梯度必须用"每输出元素唯一线程 + 规约" |
| 同 pass 内禁 RAW/WAR/WAW | op 声明 `writesReads` 依赖，由 plan() 排 pass |
| 2 GiB maxBufferSize | op 提供 `mem` 成本，供 plan() 做分片决策 |
| 无整型 atomic 之外的原语 | `Scatter` 的 reduce 用两段式（局部累加 + 合并） |

**这五条全部从"写 kernel 时人肉遵守"变成"op 契约里可声明、plan() 可检查"**。

## 7. 融合规则（双层融合策略）

```
融合层级 1（op 内）：   norm+act、qkv 投影、softmax+attn、adagrad+update
融合层级 2（pass 内）： 无 RAW 依赖的相邻 dispatch 合并进同一 compute pass
```

- **不融合的**：跨 `Bus` 读写、`Solve` 迭代内部、任何 effectful 节点边界。
- **验收**：tiny-gpt 组件树实现相对手写 trainer **吞吐退化 <10%**（来自 v2/v3 的验收线，
  保留 —— 它是"抽象有没有打散融合"的唯一硬指标）。

## 8. 验收线

| 编号 | 标准 |
|---|---|
| OP-V1 | 每个 op 逐个对拍 CPU reference（forward + 可用 backward） |
| OP-V2 | 每个 op 的 gradcheck（解析 vs 数值差分）通过 |
| OP-V3 | `caps` 声明与实现一致（一致性测试：声明有 vjp 的必须真的能反传） |
| OP-V4 | 单 kernel bind group ≤ 4（自动化检查，不依赖人） |
| OP-V5 | 新 op 接入路径：`defineOp` 贡献 + 对拍 + 审核 ⇒ 可进注册表 |
